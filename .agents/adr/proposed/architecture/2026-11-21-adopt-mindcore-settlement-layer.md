# ADR: Adopt MindCore as Nexus's Embedded Settlement Layer

Status: proposed — Nexus has no MindCore dependency (`Cargo.toml`) and still pins `LocalMemoryProvider` (`crates/nexus-core/src/service.rs:CoreService::pin_memory_provider`); this records the adoption boundary and order before either changes
Date: 2026-11-21
Scope: Embedded MindCore recall, absorb, and cognition settlement; the `MemoryPort` and Spoke `KnowledgeEntry` boundaries; SQLite transaction and DDL ownership; dependency selection and its exit condition. References prefixed `mindcore@f89cb83:` name paths on `/Users/worker/workspaces/master/mindcore` branch `origin/iteration/v07-store-protocol-schema` at `f89cb83d6c98c8a12df517b7d221e690ffdf08bc`; other paths are Nexus-relative.

## Problem

Nexus has adopted SPOKE memory behind `spoke_operations::MemoryPort`, but its only in-repository production implementation is `LocalMemoryProvider` (`crates/nexus-memory-provider/src/lib.rs:impl MemoryPort for LocalMemoryProvider`; `crates/nexus-core/src/memory_binding.rs:MemoryProviderBinding.port`). That provider owns its pool and writer admission (`crates/nexus-memory-provider/src/storage.rs:MemoryStore`), while Nexus Core's `MemoryAdapter` separately holds the workspace pool (`crates/nexus-core/src/memory.rs:MemoryAdapter`). Thus one `state.db` already has two pool handles.

Nexus deliberately refuses cognition-filtered reflections (`crates/nexus-memory-conformance/src/reflections.rs:cognition_filter_unsupported`), has no `TrustedScope` or `MindId` use under `crates/`, and stores `mind_states` only as non-authoritative projections whose authority remains holder knowledge (`crates/nexus-local-db/migrations/20260814000002_create_mind_states.sql:mind_states`). Its memory migrations contain no embedding/vector columns (`crates/nexus-local-db/migrations/`). The missing capabilities are therefore settlement and recall machinery, not another wire protocol: both repositories already pin SPOKE `=0.17.0` (`Cargo.toml`; `mindcore@f89cb83:Cargo.toml`).

MindCore supplies those missing pieces on the named branch: `SpiMindWorkflows` implements `recall_context`, `absorb`, and `deliberate` (`mindcore@f89cb83:crates/mindcore-spi/src/workflows.rs:SpiMindWorkflows`); exact hybrid scoring runs over an authorized page with a revision-checked vector cache (`mindcore@f89cb83:crates/mindcore-spi/src/workflows.rs:hybrid_scores`; `mindcore@f89cb83:crates/mindcore-sqlite/src/vectors.rs:read_record_vectors`); cognition has per-record history and derived `MindStateView` (`mindcore@f89cb83:crates/mindcore-base/src/cognition.rs:derive_mind_state`; `mindcore@f89cb83:.agents/adr/implemented/architecture/2026-11-21-cognition-per-record-and-vector-cache.md`); and a storage-independent IR sits above a caller-transaction repository (`mindcore@f89cb83:crates/mindcore-base/src/ir.rs:MemoryRepository`; `mindcore@f89cb83:crates/mindcore-sqlite/src/repository.rs:SqliteMemoryRepository`).

A wholesale swap would discard working Nexus behavior rather than fill those gaps. Nexus memory tables are cooperative writer-protocol tables with `guard_*`, `outbox_*`, `core_changes`, and `nexus_writer_*` enforcement (`crates/nexus-local-db/migrations/20261101000001_memory_control_metadata.sql`; `crates/nexus-local-db/migrations/20260912000001_core_writer_protocol.sql`). The provider also owns legacy bearer bridges and SQL/file publication (`crates/nexus-memory-provider/src/storage.rs:MemoryStore`; `crates/nexus-memory-provider/src/journal.rs:publish`), and `nexus-creator-memory` owns the bearer Markdown pipeline (`crates/nexus-creator-memory/src/memory_io.rs`; `crates/nexus-creator-memory/src/soul_io.rs`). Knowledge has a separate standing rule: Spoke `KnowledgeEntry` is content SSOT, `nexus-spoke-adapter` is its sole conversion seam, and `nexus-local-db` owns every `kb_key_blocks` write (`.agents/adr/implemented/architecture/2026-11-10-knowledge-ir.md`; `crates/nexus-spoke-adapter/src/conversion/knowledge_entry.rs:knowledge_record_to_spoke`; `crates/nexus-local-db/src/kb_store.rs:SqliteKbStore`).

The dependency is not release-ready. All five MindCore crates are `publish = false` at `0.1.0`, and its pre-release migration is rewritten in place with checksum mismatch requiring recreation (`mindcore@f89cb83:.agents/adr/implemented/architecture/2026-11-21-single-migration-store-bootstrap.md`; `mindcore@f89cb83:crates/mindcore-sqlite/src/store.rs:MindStore::open`). Adoption must gain the new workflows without importing that migration policy or weakening Nexus's append-only, `DB_SCHEMA_VERSION`-checked schema (`crates/nexus-local-db/src/version.rs:DB_SCHEMA_VERSION`; `crates/nexus-local-db/src/lib.rs:validate`).

## Proposal

1. **Adopt the workflow surface, in settlement order, not a replacement provider.** Nexus will bind `mindcore_spi::SpiMindWorkflows` through a Nexus-owned `WorkflowBinding` (`mindcore@f89cb83:crates/mindcore-spi/src/workflows.rs:WorkflowBinding`). The first adopted surface comprises `recall_context`, then `absorb`, then `deliberate`: first prove authorized exact-scored recall and vector-cache revalidation; next reuse the existing capture/review and journal publication behavior for absorb; finally enable per-record cognition appends and derived mind state. Each workflow lands with its own append-only migration and test slice, and stage N+1 starts only after stage N's acceptance cases pass. The workflows land as engine capability with test-only consumers; choosing and wiring the first Nexus caller is a separate caller-facing ADR, not a hidden stage of this one. `LocalMemoryProvider` remains the `MemoryPort` of record at `CoreService::pin_memory_provider`; existing memory callers, legacy bearer bridges, and their file pipeline do not move. MindCore's inherent `MemoryAdapter` methods may serve only inside this workflow binding (`mindcore@f89cb83:crates/mindcore-spoke/src/lib.rs:MemoryAdapter`). This adoption will not construct `MindcoreServe`, open a listener, register `tools.mindcore.*`, or add an `impl MemoryPort` around MindCore (`mindcore@f89cb83:crates/mindcore-runtime/src/lib.rs:MindcoreServe`; `mindcore@f89cb83:crates/mindcore-runtime/src/lib.rs:ServeFaces.memory`).

2. **Decompose cognition storage without creating a second knowledge authority.** Carrier content remains a Spoke `KnowledgeEntry` persisted in `kb_key_blocks`; `mind_states` remains derived and non-authoritative. New `cognition_records` rows are the storage decomposition of that carrier's `modules.cognition.records`, not a second document or SSOT. A Nexus-owned append will insert one history row and CAS the carrier revision/current-judgment head by applying `nexus-local-db`'s `cas_update_key_block_fields` directly in the same transaction; in `2026-11-10-knowledge-ir.md` terms, this is the second named `KnowledgeEntryPort`-entry exception beside promotion merge, not a new port operation. Reads will rehydrate the module through `knowledge_record_to_spoke` / `spoke_to_knowledge_record`. MindCore's `carrier_record_violation` and `derive_mind_state` are reusable domain operations (`mindcore@f89cb83:crates/mindcore-base/src/cognition.rs:carrier_record_violation`; `mindcore@f89cb83:crates/mindcore-base/src/cognition.rs:derive_mind_state`). MindCore SQLite's `write_entry` and `append_cognition` will not be called by Nexus because their statements target its `knowledge_entries` carrier (`mindcore@f89cb83:crates/mindcore-sqlite/src/knowledge.rs:write_entry`; `mindcore@f89cb83:crates/mindcore-sqlite/src/knowledge.rs:append_cognition`). Nexus dropped that table and must not recreate it (`crates/nexus-local-db/migrations/20261111000001_retire_user_and_reference_stores.sql`). All `kb_key_blocks` and cognition-row SQL remains in `nexus-local-db`; MindCore's memory IR/wire codec does not become a second knowledge conversion mapper.

3. **Embed only through the borrowed transaction seam.** The Nexus `WorkflowBinding` will drive `SqliteMemoryRepository` and MindCore's inherent `MemoryAdapter` operations with the caller's `&mut sqlx::Transaction<'_, Sqlite>` from the existing guarded workspace pool. Nexus retains admission, `BEGIN IMMEDIATE`, commit/rollback, and recovery (`crates/nexus-local-db/src/lib.rs:begin_immediate`; `mindcore@f89cb83:crates/mindcore-sqlite/src/repository.rs:SqliteMemoryRepository`). Composite citation revalidation, memory effects, carrier revision/head movement, and cognition append therefore share one writer boundary. Absorb file effects will reuse Nexus's `memory_journal` staging/publication/recovery and bearer file pipeline, not a second publisher (`crates/nexus-local-db/migrations/20261101000005_memory_journal.sql:memory_journal`; `crates/nexus-memory-provider/src/journal.rs:publish`). `MindStore::open` is not a Nexus store path: it creates a standalone one-connection pool, runs its own migrator, and installs no Nexus writer guards or UDFs (`mindcore@f89cb83:crates/mindcore-sqlite/src/store.rs:MindStore::open`; `mindcore@f89cb83:crates/mindcore-sqlite/migrations/0001_init.sql`). The pool-owning `MemoryWorkflowBinding::new` is equally excluded from embedded use (`mindcore@f89cb83:crates/mindcore-spoke/src/workflows.rs:MemoryWorkflowBinding::new`). Adoption adds no third `state.db` pool and removes none: the existing provider and Core workspace handles remain, with no atomicity assumed across them.

4. **Make Nexus the sole DDL owner for every adopted table in `state.db`.** `nexus-local-db/migrations/` will add the vector cache, per-record cognition history, and carrier-head storage in new append-only migrations, with writer-registration guards and a `DB_SCHEMA_VERSION` bump; the existing ten `memory_*` tables remain Nexus-owned (`crates/nexus-local-db/src/version.rs:DB_SCHEMA_VERSION`; `crates/nexus-local-db/migrations/20261101000001_memory_control_metadata.sql`; `crates/nexus-local-db/migrations/20261101000002_memory_content_metadata.sql`; `crates/nexus-local-db/migrations/20261101000005_memory_journal.sql`). MindCore's `0001_init.sql` is a parity reference for standalone MindCore stores only and will never run against Nexus `state.db` (`mindcore@f89cb83:crates/mindcore-sqlite/migrations/0001_init.sql`). On schema divergence, the Nexus append-only schema wins for Nexus files: CI must fail the schema/behavior parity check until a new Nexus migration and a reviewed MindCore dependency update restore agreement. No existing Nexus migration will be edited to chase MindCore's rebuildable `0001`, and no checksum-mismatch recovery will delete or recreate a Nexus database.

5. **Take a commit-pinned workspace Git dependency, with a release-and-upgrade exit.** Nexus's workspace `Cargo.toml` will declare `mindcore-base`, `mindcore-spi`, `mindcore-spoke`, and `mindcore-sqlite` with `git = "https://github.com/42ch-dev/mindcore.git"` and `rev = "f89cb83d6c98c8a12df517b7d221e690ffdf08bc"`. `mindcore-runtime` is not a dependency of this surface. CI will verify the revision resolved in `Cargo.lock` and by `cargo metadata`, not a sibling checkout. The commit currently exists only on `origin/iteration/v07-store-protocol-schema`, which must be retained until it is merged to `main`; long-term reproducibility requires that merge or a permanent tag. CI and clean checkouts will need network access to fetch the Git dependency, and updates will require changing `rev` rather than following local sibling edits. The Git edge exits only when all four consumed crates have a published release that includes an append-only migration and the named upgrade test in criterion 9 passes in that exit change's CI; Nexus will then replace the Git edges with versioned dependencies and remove the revision check in the same change. A release number alone is insufficient while in-place migration remains the upgrade policy.

6. **Extend the standing records; supersede none.** This record extends `2026-10-28-spoke-memory-adoption-plan.md` with an in-process MindCore workflow consumer beside the established provider. The Nexus-owned `WorkflowBinding`, entered only through `CoreService`, is the single stated consumer beside the `MemoryPort` path; it is not a `MemoryPort` client, and the consumer-convergence rule otherwise holds. `MemoryPort` remains the public provider boundary, protocol adoption still means no data merge, and N4-T transfer remains unsupported: no export/import, cross-provider transfer, existing-store migration, or provider cutover is authorized here (`.agents/adr/implemented/architecture/2026-10-28-spoke-memory-adoption-plan.md`). It extends `2026-11-10-knowledge-ir.md` only with a per-row storage representation of cognition already carried by Spoke `KnowledgeEntry`; it does not replace the content SSOT, conversion seam, or `nexus-local-db` write ownership (`.agents/adr/implemented/architecture/2026-11-10-knowledge-ir.md`). Remote serving, wholesale provider replacement, pool consolidation, per-principal served `deliberate` routing, and a published MindCore release are later decisions, not hidden stages of this one.

Accepting this record buys the three settlement/recall capabilities on Nexus storage under one writer boundary. It costs a dependency pinned to an unmerged upstream branch commit, so Nexus cannot publish buildable packages until the exit; ongoing parity-check maintenance against a rebuildable upstream schema; and no user-visible memory behavior change in this record—the workflows land as engine capability with test-only consumers until caller wiring is separately decided.

## Alternatives considered

1. **Replace `LocalMemoryProvider` wholesale with `MindcoreServe` / `MemoryAdapter`.** Rejected. This is not a drop-in substitution: MindCore has no `MemoryPort for MemoryAdapter` implementation; its adapter exposes inherent transaction methods, while `MindcoreServe` accepts a host-supplied `RemoteMemoryService` (`mindcore@f89cb83:crates/mindcore-spoke/src/lib.rs:MemoryAdapter`; `mindcore@f89cb83:crates/mindcore-runtime/src/lib.rs:ServeFaces.memory`). Nexus would first owe a new in-process `MemoryPort` wrapper and its complete conformance proof. It would also have to preserve writer guards, legacy bearer projection, journal/file recovery, and `nexus-creator-memory`, while reconciling MindCore's carrier table with the standing `kb_key_blocks` ownership rule. That cost buys replacement of working memory behavior instead of the missing cognition and recall capabilities.

2. **Adopt only the storage-independent IR and borrowed repository beneath the existing provider.** Rejected as the whole adoption, retained as its substrate. This minimizes protocol-policy duplication, but it delivers no `SpiMindWorkflows`, no absorb/deliberate settlement, no cognition history, and no exact-scored vector recall (`mindcore@f89cb83:crates/mindcore-base/src/ir.rs:MemoryRepository`; `mindcore@f89cb83:crates/mindcore-spi/src/workflows.rs:SpiMindWorkflows`). It leaves the owner's actual capability gap unchanged.

3. **Vendor the four MindCore crates.** Rejected. Vendoring would make the source tree self-contained, but it would fork an unreleased, still-moving implementation, duplicate its review and update history, and make schema drift harder to attribute. It does not solve the absent upgrade path; the same append-only-release exit would still be required. A commit-pinned Git edge preserves one upstream repository and one reviewable source of changes at lower carrying cost, while requiring upstream to retain the pinned object.

4. **Wait for a published MindCore release.** Rejected. Waiting avoids an unreleased Git edge but delivers none of the missing workflows and does not remove any Nexus integration work. Publication without append-only migrations would also fail this proposal's exit condition. The contained Git dependency allows adoption now without pretending the dependency is stable.

5. **Use `MindStore::open` or the stock `MemoryWorkflowBinding` for convenience.** Rejected. Both own their transaction boundaries; `MindStore::open` also owns a pool and migrator (`mindcore@f89cb83:crates/mindcore-sqlite/src/store.rs:MindStore::open`; `mindcore@f89cb83:crates/mindcore-spoke/src/workflows.rs:MemoryWorkflowBinding`). On `state.db` this would bypass the existing writer admission/effect boundary and add a third pool handle. A standalone MindCore database would not be a Nexus `state.db` because the Nexus-only guards, UDFs, and control objects are absent (`mindcore@f89cb83:crates/mindcore-sqlite/migrations/0001_init.sql`; `crates/nexus-local-db/migrations/20260912000001_core_writer_protocol.sql`).

6. **Run MindCore's migration and carrier storage verbatim.** Rejected. It would put DDL ownership in two repositories, import a recreate-on-checksum-mismatch policy into append-only Nexus storage, and recreate the dropped `knowledge_entries` table beside `kb_key_blocks` (`mindcore@f89cb83:.agents/adr/implemented/architecture/2026-11-21-single-migration-store-bootstrap.md`; `crates/nexus-local-db/migrations/20261111000001_retire_user_and_reference_stores.sql`). The result would be both a schema-version conflict and a second knowledge authority/conversion path.

## Acceptance criteria

1. **The dependency edge is exactly the reviewed one.** The implementation change will add the four workspace Git dependencies in Proposal 5. `cargo metadata --locked --format-version 1` must resolve only `mindcore-base`, `mindcore-spi`, `mindcore-spoke`, and `mindcore-sqlite` from `https://github.com/42ch-dev/mindcore.git` at `f89cb83d6c98c8a12df517b7d221e690ffdf08bc`, with no `mindcore-runtime`; `Cargo.lock` must record the same resolved revision. The implementation change will add a CI check comparing those metadata and lockfile revisions, replacing any sibling-checkout check.

2. **The public provider boundary is unchanged.** `rg 'impl\s+MemoryPort\s+for' crates/nexus-memory-provider` still finds `LocalMemoryProvider` as the only production implementation in that crate; `crates/nexus-core/src/service.rs:CoreService::pin_memory_provider` still opens it for `MemoryProviderSelection::Local`; and `rg 'MindStore::open|MemoryWorkflowBinding::new|MindcoreServe' crates` returns no matches.

3. **Every embedded effect uses the guarded caller transaction.** The implementation change will add `crates/nexus-core/tests/mindcore_workflows.rs` and its `cognition_settlement_uses_guarded_writer` case, proving that an unregistered raw writer receives `WRITER_FENCED` and that citation effects, carrier revision/head, and cognition append advance or roll back together; `cargo test -p nexus-core --test mindcore_workflows cognition_settlement_uses_guarded_writer` must pass. The primary no-third-pool evidence is the Nexus `WorkflowBinding` type contract: it holds no pool and every write accepts only the caller's `&mut sqlx::Transaction<'_, Sqlite>`, with no pool acquisition or transaction commit/rollback. A search for pool-construction APIs in the new binding is auxiliary, not proof.

4a. **Recall lands first on Nexus storage.** The implementation change will add the recall migration and `recall_context` test slice to `mindcore_workflows`, including `recall_context_revalidates_exact_vectors`; warm and freshly computed vectors must produce bit-identical page ranking, and stale revisions must not hit. `cargo test -p nexus-core --test mindcore_workflows recall_context_revalidates_exact_vectors` must pass before absorb work starts. Its consumer is the test slice only.

4b. **Absorb lands second without changing publication behavior.** After criterion 4a passes, the implementation change will add the absorb migration and `absorb_replays_and_recovers_journal` to `mindcore_workflows`; absorb replay and crash recovery must preserve the existing receipt/journal behavior. `cargo test -p nexus-core --test mindcore_workflows absorb_replays_and_recovers_journal` must pass before deliberate work starts. Its consumer is the test slice only.

4c. **Deliberate lands last with singular carrier ownership.** After criterion 4b passes, the implementation change will add the cognition/carrier-head migration and `deliberate_appends_and_rehydrates_cognition` to `mindcore_workflows`; two cognition appends must retain both rows, stale carrier CAS must leave all rows unchanged, and the rehydrated Spoke `KnowledgeEntry` must preserve record order. `cargo test -p nexus-core --test mindcore_workflows deliberate_appends_and_rehydrates_cognition` must pass. Its consumer is the test slice only. These are Nexus-local checks; MindCore's standalone measurements are not accepted as substitutes.

5. **Nexus alone versions and migrates its schema.** `cargo test -p nexus-local-db --test migrations_apply` passes with a `DB_SCHEMA_VERSION` greater than the current `39` (`crates/nexus-local-db/src/version.rs:DB_SCHEMA_VERSION`). The implementation change will add a schema-parity case to the new `mindcore_workflows` target that compares `PRAGMA table_info` for the ten shared memory tables plus `memory_embedding_vectors` and checks the Nexus carrier/cognition mapping; a divergence fails rather than selecting a fallback schema. No migration invokes `MindStore::open` or MindCore's embedded migrator.

6. **Knowledge ownership remains singular.** The implementation change will extend `migrations_apply` to assert that the final migrated database's `sqlite_master` contains no `knowledge_entries` table, rather than searching append-only historical migrations; it will also assert that no new production write path targets that table. The new binding's carrier read/write path calls `crates/nexus-spoke-adapter/src/conversion/knowledge_entry.rs:knowledge_record_to_spoke` and `spoke_to_knowledge_record`; all production-runtime `kb_key_blocks` mutation SQL remains under `crates/nexus-local-db`, with test/fixture SQL explicitly exempt. `cargo test -p nexus-spoke-adapter knowledge_entry` and the cognition round-trip case in criterion 4c pass.

7. **Existing memory behavior and the borrowed seam remain conformant.** `cargo test -p nexus-memory-conformance` passes, including legacy bearer/file cases. From a MindCore checkout resolved at the pinned revision, `cargo test -p mindcore-sqlite --test borrowed_memory_repository --test embed_parity` and `cargo test -p mindcore-spoke --test memory_adapter --test workflows` pass, while criteria 4a–4c supply the required proof against a Nexus-migrated `state.db`.

8. **No transfer or remote-serving capability appears incidentally.** The workflow tests assert that memory export/import remains unsupported. Criterion 1 excludes `mindcore-runtime`; the implementation change will add a service-registration manifest test asserting that no MindCore serving face is registered, and `rg 'MindcoreServe|RemoteMemoryService' crates --glob '!**/tests/**' --glob '!**/*test*'` introduces no production construction or registration.

9. **The release exit proves an append-only upgrade.** The exit change will add `crates/nexus-local-db/tests/mindcore_release_upgrade.rs::adopted_store_upgrades_without_recreation` and run `cargo test -p nexus-local-db --test mindcore_release_upgrade adopted_store_upgrades_without_recreation` in its CI. The test migrates a store created at the adopted Nexus schema to the release schema and verifies no data loss, recreation, or checksum-mismatch refusal; the exit PR must link its passing CI run before the Git dependencies and revision check are removed.

## Risks

| Risk | Concrete breakage | Containment |
| --- | --- | --- |
| Unreleased Git dependency | The pinned object exists only on an unmerged upstream branch; losing that branch breaks clean fetches, CI needs network access, and Nexus cannot publish buildable packages while the four crates remain `publish = false` (`mindcore@f89cb83:.agents/adr/implemented/architecture/2026-11-21-single-migration-store-bootstrap.md`). | Pin `rev` and CI-check the `Cargo.lock`/`cargo metadata` resolution; retain `origin/iteration/v07-store-protocol-schema` until merging to `main` or creating a permanent tag; review every `rev` update; retire the Git edge only for a published release with the upgrade proof in criterion 9 (Proposal 5). |
| In-place MindCore migrations | A changed `0001` checksum can refuse an existing MindCore file and require recreation (`mindcore@f89cb83:crates/mindcore-sqlite/src/store.rs:MindStore::open`). | Never open Nexus `state.db` through `MindStore`; use only new Nexus migrations and `DB_SCHEMA_VERSION`; never treat database deletion as recovery (Proposal 4). |
| Writer-protocol divergence | MindCore adapter code could pass protocol tests yet bypass Nexus writer registration, `core_changes`, or SQL/file settlement (`crates/nexus-local-db/migrations/20261101000001_memory_control_metadata.sql`; `crates/nexus-memory-provider/src/journal.rs:publish`). | Keep the adapter internal, borrow only the guarded transaction, reuse Nexus journal/publication, and require the raw-writer, rollback, crash-recovery, and full memory-conformance checks in criteria 3 and 7. |
| Existing dual pool | A workflow split between the provider pool and workspace pool could look atomic when it is not (`crates/nexus-memory-provider/src/storage.rs:MemoryStore`; `crates/nexus-core/src/memory.rs:MemoryAdapter`). | Add no third handle and perform every new composite effect on the workspace transaction; do not claim cross-pool atomicity or consolidate the existing two under this ADR (Proposal 3). |
| Shared-schema divergence | MindCore can rewrite `0001` while Nexus can only append migrations, leaving identical table names with different meanings (`mindcore@f89cb83:crates/mindcore-sqlite/migrations/0001_init.sql`; `crates/nexus-local-db/src/version.rs:DB_SCHEMA_VERSION`). | Nexus owns Nexus DDL; fail the `PRAGMA`/behavior parity check until a reviewed dependency update and append-only Nexus migration restore agreement (criterion 5). |
| Knowledge authority regression | Recreating `knowledge_entries` or using MindCore's carrier SQL would bypass the sole conversion seam and split content between two stores (`crates/nexus-local-db/migrations/20261111000001_retire_user_and_reference_stores.sql`; `.agents/adr/implemented/architecture/2026-11-10-knowledge-ir.md`). | Keep carriers in `kb_key_blocks`, reuse only MindCore domain validation/derivation, and enforce the no-table/no-second-mapper checks in criterion 6. |
| Transfer gap | Treating adoption as a provider cutover could strand existing records or imply N4-T export/import that neither standing decision supports (`.agents/adr/implemented/architecture/2026-10-28-spoke-memory-adoption-plan.md`; `mindcore@f89cb83:crates/mindcore-spoke/src/lib.rs:MemoryAdapter.create_export`). | Keep the current provider and data in place, add no migration/transfer path, and require the unsupported-operation assertion in criterion 8. |

unverified: MindCore's append-cost and warm-recall measurements have not been reproduced on a Nexus-migrated `state.db`; this proposal claims capability and transactional correctness, not Nexus performance, until criteria 4a–4c run.
