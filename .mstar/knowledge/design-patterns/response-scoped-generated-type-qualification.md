# Response-scoped type qualification for generated DTOs

## Context

The Rust wire types are generated by `typify` from `schemas/**/*.schema.json` into per-schema files, then re-exported up a chain of barrel modules:

```
crates/nexus-contracts/src/generated/core/orchestration_presets/preset_profile_state.rs   ← declares PresetProfileState (+ its own inline copies of siblings)
crates/nexus-contracts/src/generated/core/orchestration_presets/mod.rs                    ← pub use preset_profile_state::PresetProfileState;
crates/nexus-contracts/src/generated/core/mod.rs                                          ← pub use orchestration_presets::*;
crates/nexus-contracts/src/generated/mod.rs                                               ← pub use core::*;
crates/nexus-contracts/src/lib.rs                                                         ← pub use generated::*;
```

Each generated file embeds its **own copy** of every referenced sibling type, so the same wire shape exists as several distinct Rust structs. `preset_profile_response.rs` declares all ten members of its family; `preset_profile_state.rs` declares `PresetProfileState` *plus* its own copies of `ConditionalRule`, `EnterAction`, `ExitWhen`, `LabeledNext` and `Next`. Both are individually self-consistent — but `preset_profile_response::PresetProfileState` and the crate-root `PresetProfileState` (which resolves through the barrel to `preset_profile_state::PresetProfileState`) are **different types with the same name and the same wire shape**.

The crate root therefore has two paths to the same name, one of which is wrong for any given consumer. A consumer that imports the crate-root name, builds a value, and assigns it into a field of the response DTO gets a type-mismatch error on code that looks obviously correct.

## Guidance

**Import the whole family from the module that owns the composite** whenever you construct a response DTO from its parts:

```rust
// The canonical preset profile DTOs live in the generated `preset_profile_response`
// module; the crate-root names resolve to per-DTO duplicates that are wire-identical
// but distinct Rust types from the ones `PresetProfileResponse` actually holds.
// Import the family from the owning response module.
use nexus_contracts::generated::core::orchestration_presets::preset_profile_response::{
    PresetProfileConditionalRule, PresetProfileEnterAction, PresetProfileExitWhen,
    PresetProfileLabeledNext, PresetProfileLanes, PresetProfileNext, PresetProfileResponse,
    PresetProfileRole, PresetProfileSignal, PresetProfileState,
};
```

Rules that follow from the generated layout:

1. **Pick the path by what you do with the value, not by how it reads.**
   - *Constructing or matching a composite's child* → the composite's own module (`…::preset_profile_response::…`), because that is the only module whose fields are typed with those copies.
   - *Naming a top-level DTO as a standalone type* (a function parameter, a return type, a drift-test entry) → the crate root is correct and unambiguous, because a top-level DTO has exactly one generated declaration.
2. **The qualification is per consumer file, and it must cover the whole family used together.** Qualifying three of four child imports leaves the fourth mismatched; if a file constructs `PresetProfileResponse`, import *all* the types it puts into it from the same module.
3. **Duplicate names are normal here, not a defect to fix locally.** 80 type names are declared in more than one generated file at this revision (the `$ref`-target families: `NexusActorKnowledgeViewItem*`, `CharacterActorRef*`, `BindingKnowledgeOwner*`, …). Do not "fix" a mismatch by editing a generated file or by widening the schema — the remedy belongs to the generator lane (see §Generator fix, below).
4. **Verify with a build, not with reading.** The mix compiles nowhere: any accidental cross-family assignment is a hard error, never a silent coercion. That is the property that makes qualification safe — and the reason this class surfaces as compile errors rather than wire corruption.
5. **A `Vec<T>` element type is a distinct case worth naming.** A response's list item type is often the *response module's* inline copy (`work_inspiration_list_response::WorkInspirationItem`), not the barrel's standalone `work_inspiration_item::WorkInspirationItem`. Iterating a page and mapping into the response must use the response module's type.

### Generator fix (owned by the codegen lane, not consumers)

The durable remedy is to make `$ref` targets reuse the standalone module type instead of re-declaring them, so the crate root is unambiguous and consumers can import one path. Until that lands, qualification at the consumer is the correct, mechanical workaround — and it is strictly better than a type alias or a `#[allow]`, because it keeps the mismatch impossible rather than hidden.

## Why This Matters

- **The failure is a compile error, which is the good case** — but only if consumers are written against the right path from the start. A file written with the crate-root imports compiles fine *until* it tries to construct the composite, at which point the error points at a field assignment and looks like a domain bug rather than an import-path problem.
- **The barrel hides the duplication.** `pub use generated::*` means the "obvious" import is the one that resolves through several globs to whichever declaration wins; nothing at the import site signals that a sibling copy exists.
- **Qualifying documents the ownership.** `…::preset_profile_response::PresetProfileState` states "this value belongs to that response", which is exactly the relationship that broke. A type alias would erase it.
- **It is the cheapest correct move while the generator gap is open.** The generator change touches every schema family; the consumer qualification is local, reviewable, and reversible when the generator is fixed.

## When to Apply

- Writing a new consumer (core module, native adapter, CLI, service) that builds a generated response DTO or maps into its list item type.
- Chasing a "mismatched types" error where both sides print the *same* type name — check the import paths before suspecting the domain.
- Reviewing a diff that adds crate-root imports of a generated response family: ask whether the file ever constructs the composite.
- Deciding whether to touch the generator: if a consumer cannot name a unique path to the type it needs, that is a generator-lane gap, not a local naming choice.

## Examples

### Before — crate-root import, distinct type at the assignment

```rust
// crate-root path resolves through `pub use generated::*` → core::* → orchestration_presets::*
use nexus_contracts::{PresetProfileLanes, PresetProfileResponse};

fn profile(id: String, lanes: PresetProfileLanes, source_hash: String) -> PresetProfileResponse {
    PresetProfileResponse {
        id,
        lanes,
        required_capabilities: Vec::new(),
        roles: Vec::new(),
        signals: Vec::new(),
        source_hash,
        states: Vec::new(),
        version: 1,
    }
    // error[E0308]: expected `preset_profile_response::PresetProfileLanes`,
    //               found `preset_profile_lanes::PresetProfileLanes`
}
```

### After — response-scoped family import

```rust
use nexus_contracts::generated::core::orchestration_presets::preset_profile_response::{
    PresetProfileLanes, PresetProfileResponse,
};

fn profile(id: String, lanes: PresetProfileLanes, source_hash: String) -> PresetProfileResponse {
    PresetProfileResponse {
        id,
        lanes,                       // same module: one type identity
        required_capabilities: Vec::new(),
        roles: Vec::new(),
        signals: Vec::new(),
        source_hash,
        states: Vec::new(),
        version: 1,
    }
}
```

### List-item variant (response module owns the element copy)

```rust
// list item type: the response module's copy, not the standalone item module
let items: Vec<
    nexus_contracts::generated::core::works::work_inspiration_list_response::WorkInspirationItem,
> = page.items.into_iter().map(/* … */).collect();
```

## Evidence

- Generated layout — `crates/nexus-contracts/src/generated/core/orchestration_presets/preset_profile_response.rs` declares the full ten-type family; `…/preset_profile_state.rs` declares `PresetProfileState` plus five sibling copies; both are re-exported by `…/orchestration_presets/mod.rs`, then `core/mod.rs` (`pub use orchestration_presets::*;`), `generated/mod.rs` (`pub use core::*;`) and `lib.rs` (`pub use generated::*;`).
- Same-shape list-item case — `…/core/works/work_inspiration_item.rs` and `…/core/works/work_inspiration_list_response.rs` both declare `WorkInspirationItem`; the native adapter's list path names the response module's copy explicitly while its archive path uses the standalone one.
- Scale of the duplication — 80 type names are declared in more than one generated file at this revision (measured over `crates/nexus-contracts/src/generated/**/*.rs`, excluding the per-file `ConversionError` helper).
- Consumer fixups recorded in the iteration — the response-scoped import was applied in `crates/nexus-core/src/presets.rs`, `apps/nexus42/src/commands/preset/mod.rs` (production and its `#[cfg(test)]` block) and the daemon preset handler during the P3/P5 contract integration; the core-node family adapter uses response-scoped DTO paths for the same reason.
- Generator-lane gap — registered as the codegen residual for `$ref` targets re-emitted inside response modules (owner: the codegen lane; scope `tooling/codegen/rust-gen/src/main.rs`, `tooling/codegen/src/ts-gen.ts`).
