## Architect lock (Seat 2) — hard delete, cascade, confirm dialog

> Locked 2026-07-21. See `.mstar/iterations/v1.129/specs/dogfood-nit-closeout.md` § Interfaces for full rationale.

1. **Hard delete (not soft delete):** `DELETE` routes with confirm dialog. No `status` column, no query-filter blast radius. Confirm dialog is the safety net; undo is not a V1 goal.
2. **Cascade rules:**
   - Delete Work → cascade-delete: Manuscripts, Outlines, Timelines, KB entries under that Work.
   - Delete World → cascade-delete: KB entries, Timelines under that World. Set `world_id` to NULL on Works referencing that World (do NOT delete Works).
   - Implementer (T2): verify actual SQLite FK constraints; prefer explicit cascade queries for visibility.
3. **Confirm dialog contract:**
   - Title names the item (e.g., "Delete 'My Novel'" or "Delete 'Fantasy World'").
   - Body names cascaded items + irreversibility ("This will permanently remove… This cannot be undone.").
   - Primary CTA: "Delete" (destructive); secondary: "Cancel".
   - Product copy polished by writing-specialist (Seat 3).
4. **Residual discipline:** Triage T1 classifies each scanned residual as `visible` or `quality-only`. Visible → fix or `decision: defer` with rationale. Quality-only → stay `open` with deferral note. Closed rows → `archived/residuals/<plan-id>.json`.
5. **Task order:** T1 (triage) → T2 (daemon DELETE) → T3 (web submenu) → T4 (i18n) → T5 (other visible nits) → T6 (archive). T3 may wire with mock DELETE before T2 completes for parallel dev — but integration merge requires both T2 + T3 done.
