# P1 — Track B: Findings Batch Triage

## 1. specify

### Problem statement (P1 companion)

V1.77 made individual findings editable via PATCH. When an author finishes a review pass and has twenty (or more) findings to triage — mark as `resolved`, or assign all to the `write` executor — they must click, edit, and save each one individually. This is high-friction for power users.

### User value (P1 companion to P0 headline)

Authors with N findings complete routine triage (status transition + target_executor assignment) in roughly one multi-select action instead of N separate edits. They can also export a snapshot of the currently filtered list to CSV directly from the browser without leaving the review surface. This is a companion improvement to the V1.91 headline (profile-specific reading chrome); the two tracks are deliberately separated.

### Scope (P1 companion — additive only)

- Backend: one additive bulk PATCH helper endpoint (`PATCH /v1/daemon/findings/batch`). Implementation reuses existing `update_finding` DAO in a loop per-ID (partial success model, not all-or-nothing transaction).
- Schema/codegen: two new JSON Schema files under `schemas/daemon-api/findings/` for cross-language type sharing with `apps/web` (TypeScript).
- Frontend (`apps/web` findings list): multi-select checkboxes, bulk action bar (status + executor), client-side CSV export of the current filtered result set.
- Reuses existing `FindingStatus` enum and single-finding authz/DAO patterns.
- `@42ch/nexus-contracts` version bump: `0.19.0` → `0.19.1` (additive minor).

P1 is the **companion** track. P0 (reading chrome) is the headline and must not be touched by this plan. After P-1, P0 and P1 use separate worktrees.

### Non-goals (strict — cross-reference compass §6)

- No findings auto-generation, LLM fix suggestions, or remediation workflow.
- No complex filter DSL or new query capabilities beyond the existing list filter.
- No backend export jobs, scheduled reports, or server-side CSV generation.
- No OCC, conflict-resolution UI, or multi-author semantics (single-author last-writer-wins, consistent with V1.77).
- No email/push notifications or external integrations.
- No changes to findings state machine or new status values.
- No overlap with P0 reading chrome components or DESIGN tokens.
- See compass §6 for the full enforced non-goals list.

## 2. clarify

### Endpoint contract (locked by P-1; this is the implementation bar)

- `PATCH /v1/daemon/findings/batch`
- **Path**: creator-scoped — no `work_id` in URL. Follows the V1.48 P2 pattern of `GET /v1/daemon/findings/{finding_id}`. The daemon reads `creator_id` via `read_active_creator_id` and scopes all operations to that creator.
- **Request body**: `{ finding_ids: string[] (capped at 100), patch: { status?: FindingStatus, target_executor?: string } }`
- **Response (HTTP 200)**: `{ updated: number, not_found?: string[], conflict?: string[] }`
  - `updated`: count of findings successfully updated (status or target_executor).
  - `not_found`: IDs that don't exist or don't belong to the active creator. Each `not_found` ID was skipped; `updated` count does not include these.
  - `conflict`: IDs where the patch's `status` transition was illegal per the lifecycle table (`findings-lifecycle.md` §2.2). Each `conflict` ID was skipped; `updated` count does not include these.
  - If `patch` is empty (no `status` and no `target_executor`), the handler returns HTTP 200 with `updated: 0` and no `not_found`/`conflict` arrays.
- **Authz**: creator-scoped (identical to existing single-finding PATCH). Uses `read_active_creator_id`.
- **Schema files** (committed under `schemas/daemon-api/findings/`):
  - `batch-update-findings-request.schema.json` — `BatchUpdateFindingsRequest`
  - `batch-update-findings-response.schema.json` — `BatchUpdateFindingsResponse`
- **Semantics**: additive helper; calls existing `update_finding` DAO in a loop per-ID (not a transaction — partial success model). Each individual call reuses the full DAO validation stack: enum membership check (`VALID_SEVERITIES`, `VALID_STATUSES`, `VALID_TARGET_EXECUTORS`), lifecycle transition enforcement (`enforce_status_transition`). No OCC (last-writer-wins, consistent with V1.77 §4.4).
- **Error responses (HTTP 4xx/5xx)**: only cap breach or internal DB failures surface as HTTP errors:
  - `finding_ids.length > 100` → `NexusApiError::BadRequest { code: "too_many_findings", message: "..." }` (HTTP 422)
  - Internal DB error → `NexusApiError::Internal { code: "DATABASE_ERROR", ... }` (HTTP 500)
  - No active creator → `NexusApiError::AuthRequired` (HTTP 401)
  - Invalid `patch.status` enum value → `NexusApiError::BadRequest { code: "invalid_input", ... }` (HTTP 422) — caught by the first `update_finding` call's enum validation
- **Design rationale (loop, not transaction)**: partial success is intentional. A bulk triage operation where 47 of 50 findings succeed and 3 have illegal transitions should report the 3 failures so the author can fix them, rather than rolling back all 47. This aligns with the single-author, last-writer-wins model where each finding is independent.

### Multi-select UI (P1)

- Checkbox column (or equivalent) in the findings list.
- Bulk action bar appears when ≥1 item selected.
- Actions (at minimum): "Set status to…", "Assign target_executor…", "Export CSV".
- Selection state is local to the list view; does not affect other surfaces.

### CSV export (client-side only)

- Generated from the currently loaded + filtered rows in the browser.
- Columns (stable order): id, title, status, kind, severity, target_executor, created_at, rule_suggestion (truncated to ~200 chars).
- No backend endpoint, no server-side file, no scheduling.

### Intent gate

Real goal (P1 companion): reduce repetitive triage friction for authors with many findings via multi-select batch actions + client CSV snapshot. Not to build a full review workflow, remediation pipeline, reporting system, or any LLM-assisted features. P0 (profile-specific reading chrome) is the separate headline for this iteration.

## 5. notes

- **Additive and minimal**: endpoint is a helper only. Do not refactor the existing single-finding PATCH unless strictly required for reuse. Do not introduce new findings state machine semantics.
- **Error model alignment with `NexusApiError`**: the bulk handler returns `NexusApiError` (or types converting into it) through the standard daemon error envelope. `not_found` and `conflict` IDs are NOT errors — they are inline fields in the HTTP 200 response body. Only cap breach (`too_many_findings`), internal DB failures, auth failures, and invalid enum values surface as HTTP 4xx/5xx.
- **Implementation pattern**: the bulk handler calls the existing `update_finding` DAO function in a loop. Each per-ID call returns `Result<bool, LocalDbError>`. The handler collects results:
  - `Ok(true)` → increment `updated`, continue.
  - `Ok(false)` → push ID to `not_found`, continue.
  - `Err(IllegalTransition { .. })` → push ID to `conflict`, continue.
  - `Err(other)` → return HTTP 500 (first internal error aborts the batch to avoid cascading failures).
- If `update_finding` is awkward to call in a loop, extract a thin shared validation helper — but single-finding behavior and tests must remain unchanged.
- P1 is **companion (P1)**; P0 (reading chrome) is **headline (P0)**. After P-1 lands, use separate worktrees. Coordinate on truly shared table/list primitives only if P-1 already anticipated it; never touch reading chrome components or DESIGN reading-chrome tokens.
- See compass §2.2 (companion outcome), §5 AC, and §6 non-goals for the full bar.
