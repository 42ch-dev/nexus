# P-1 — Prepare: Reading Chrome + Findings Batch Triage

## 1. specify

### Problem statement

V1.89 shipped a generic manuscript reading surface. The read-only view is profile-agnostic: a novel chapter, an essay section, a game-bible entry, and a script scene render identically, losing the typographic and structural cues that help authors stay in the right mental model for the work they are reading.

V1.77 made findings editable one-by-one. Power users with dozens of findings still pay a high per-item click cost for routine triage (status + executor assignment) and lack a fast way to capture the current filtered list.

### User value (P0 headline + P1 companion)

- **P0 (primary)**: Authors open a Work and immediately perceive its profile identity through the reading surface (novel vs script vs essay vs game-bible), reducing context-switching friction.
- **P1 (companion)**: Authors with N findings complete status triage or executor assignment in ~1 action instead of N separate edits; they can also snapshot the current filtered list to CSV without leaving the browser.

### Scope (P-1 Prepare only — contracts & tokens)

- Lock the `apps/web/DESIGN.md` `## Reading Chrome` token section (typography, spacing, separators, cross-reference links, role/scene formatting). Tokens are additive; no renames of existing tokens.
- Lock a concise per-profile chrome element checklist for the four shipped profiles (`novel`, `essay`, `game-bible`, `script`) with ≥2 distinct visual markers per profile (examples in compass §2.2 and P0 plan). This checklist becomes the acceptance bar for P0.
- Lock the findings bulk PATCH helper contract: `PATCH /v1/daemon/findings/batch`, request `{ finding_ids: string[] (≤100), patch: { status?: FindingStatus, target_executor?: string } }`, response `{ updated: number, not_found?: string[], conflict?: string[] }`, creator-scoped, no OCC (last-writer-wins consistent with V1.77), cap enforcement.
- The bulk PATCH endpoint's request and response shapes are consumed cross-language by `apps/web` (TypeScript), therefore they require JSON Schema entries under `schemas/daemon-api/findings/`:
  - `batch-update-findings-request.schema.json` — request DTO (`BatchUpdateFindingsRequest`)
  - `batch-update-findings-response.schema.json` — response DTO (`BatchUpdateFindingsResponse`)
- Codegen pipeline: `pnpm run codegen` must be run after schema creation; `@42ch/nexus-contracts` bumps from `0.19.0` to `0.19.1` (additive minor).
- Client-side CSV export columns are locked: id, title, status, kind, severity, target_executor, created_at, rule_suggestion (truncated to ~200 chars).
- Document profile reading conventions either in `knowledge/specs/` (if the tree exists) or directly in this plan + DESIGN.md section. If `knowledge/specs/` tree is absent, note the location in the plan and do not block on directory creation.

P-1 produces **no implementation code**, only the token contract, per-profile checklist, and bulk PATCH spec.

## 2. clarify

### High-impact ambiguities (resolved in P-1)

1. **Where does the profile chrome live?**
   - Decision: presentational chrome components under `apps/web/src/components/reading/` (or adjacent) that read `work_profile` from the already-loaded Work object on the existing reading page. No new route. Purely read-only.

2. **How does chrome map to profile?**
   - Decision: small profile switch (e.g. `ReadingChrome` component) driven by `work_profile` string value. Explicit fallback to `novel` chrome for unknown values. No dynamic module loading in V1.91.

3. **Bulk PATCH contract (locked)**
   - `PATCH /v1/daemon/findings/batch`
   - Request: `{ finding_ids: string[] (capped at 100), patch: { status?: FindingStatus, target_executor?: string } }`
   - Response: `{ updated: number, not_found?: string[], conflict?: string[] }`
   - Authz: creator-scoped (same as single PATCH via `read_active_creator_id`).
   - Semantics: additive helper; calls the existing `update_finding` DAO function in a loop per-ID (not a transaction — partial success model). Each individual update reuses the full DAO validation stack (enum membership, lifecycle transition enforcement).
   - No OCC (single-author last-writer-wins, consistent with V1.77 §4.4).
   - Cap enforcement: cap at 100 IDs; >100 → `NexusApiError::BadRequest { code: "too_many_findings" }` (HTTP 422).
   - Error model: `not_found` and `conflict` IDs are returned inline in the success response (HTTP 200), NOT as HTTP error responses — this allows callers to handle partial success. Only cap breach or internal DB errors surface as HTTP 4xx/5xx.
   - `not_found`: IDs that don't exist or don't belong to the active creator → listed in `response.not_found`.
   - `conflict`: IDs where the patch's `status` transition is illegal (per the lifecycle table in `findings-lifecycle.md` §2.2) → listed in `response.conflict`.
   - Schema: request and response shapes live in `schemas/daemon-api/findings/` with codegen for Rust + TypeScript consumption.

4. **CSV export (locked)**
   - Purely client-side from the currently loaded/filtered rows in the findings list.
   - Columns (order stable): id, title, status, kind, severity, target_executor, created_at, rule_suggestion (truncated to ~200 chars).
   - No backend endpoint or scheduled job.

### Intent gate

Real goal: make the reading surface feel profile-native and remove friction from findings triage, without opening new write surfaces or backend infrastructure.

### Still-open assumptions

- `work_profile` values are stable (`novel`, `essay`, `game-bible`, `script`).
- Existing `FindingStatus` enum covers the batch transitions.
