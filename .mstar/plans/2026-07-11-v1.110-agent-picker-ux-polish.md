## Problem statement (specify)

Two `AgentPicker` ergonomics issues reported from dogfooding:

- **FB-D2** — The picker renders the full registry list unsorted
  (`apps/web/src/components/setup/agent-picker.tsx:177-197`, plain
  `agents.map(...)`). Common agents are buried mid-list and the list is long.
  Requested: common agents first, in this **exact** priority order —
  **Codex CLI, Claude Code, Cursor CLI, OpenCode, Hermes, Kimi Code, Qoder,
  GitHub Copilot CLI, Pi, Kiro CLI** — then a **More** button that, once
  clicked, reveals the remaining agents sorted by **last-updated desc**.
- **FB-D4** — The custom-path `Input` (default size) and `Verify Agent`
  `Button` (`size="small"`) sit in a `flex flex-wrap gap-2` row
  (`agent-picker.tsx:422-449`) at different heights. Fuse them into one
  coherent component.

## User value

A trustworthy, scannable picker: the agents the author is most likely to use
are on top, the long tail is progressively disclosed, and the escape hatch
looks like a single deliberate control instead of two misaligned pieces.

## Scope / Non-goals

In scope:

- **FB-D2** ordering + **More** progressive disclosure inside `AgentPicker`:
  - Common-first partition by a locked priority list (match by
    `registry_agent_id` then `name`).
  - **More** button after the common list; on click, render the remaining
    agents sorted by registry order (the scan-response order; `lastUpdated` desc
    is blocked by `wire_contracts_changed: false` — see residual
    `R-V110P2-001`).
  - Graceful degradation: unknown common ids fall back to registry order
    within each partition.
- **FB-D4** fused custom-path/verify component:
  - One visually coherent control with aligned height; Verify is an inline
    affordance of the field, not a sibling button of a different size.
  - Preserve the existing `AgentVerifyStatus` state machine
    (`idle`/`loading`/`success`/`no-match`/`error`) and helpers.
- Keep `AgentPicker` presentational (no daemon client, no wire DTOs) — the
  `lastUpdated` data flows in via `AgentPickerItem` / props.
- Tests for ordering, More-toggle, and the fused component a11y.

Non-goals:

- Settings-shell IA rework beyond the `AgentPicker` component.
- Reordering the underlying ACP registry (read-only consumer).
- Full keyboard navigation audit inside the More expansion (basic reach in
  scope; deep a11y audit deferred).
- Custom-path **command parsing / validation** logic changes (UI fusion only).

## Long-term target state

`AgentPicker` is a progressively-disclosed, common-first picker whose escape
hatch is a single fused field — the same component serves Setup and Settings
without per-host fork.

## Proposed approach (locked — architect §5.2; Q1 copy pending product)

- **FB-D2:**
  - Add an optional `lastUpdated?: string` (ISO) to `AgentPickerItem`
    (forward-compatible view-model field; **unsourced in V1.110** — see Q2 lock
    + residual `R-V110P2-001`).
  - Partition `agents` into `common` (intersect with priority list, sorted by
    priority) and `rest` (sorted by **stable registry order** in V1.110 — the
    scan-response order; `lastUpdated` desc is blocked by
    `wire_contracts_changed: false`). Render `common` always; render `rest`
    only after **More** clicked (local `useState` toggle inside `AgentPicker`).
  - Priority list lives in a named constant `COMMON_AGENT_PRIORITY` so it is
    adjustable without touching render logic. Match by `registry_agent_id`
    first, then `name`.
  - **More** button: plain `<button>`, `aria-expanded` + `aria-controls` on the
    rest region. Collapsed label deferred to product (architect preference:
    "More agents" / "Fewer agents").
- **FB-D4:**
  - Refactor `CustomLaunchField` into a trailing-inline-button **input-group**:
    one `relative`/`flex` container defines a single shared height; the `Input`
    fills width; the Verify `Button` sits at the trailing edge sized to match
    the Input (drop the current `size="small"` mismatch).
  - Keep `variant="secondary"`, the `AgentVerifyStatus` state machine, and
    test-ids `agent-picker-verify` / `agent-picker-verify-success` /
    `agent-picker-verify-error`.

### Per-task Interfaces

- **T1 produces** `COMMON_AGENT_PRIORITY: readonly string[]` + a partition helper (`common`, `rest`). **Consumes** `AgentPickerItem[]` from the host. **No host API change** — partition is internal to `AgentPicker`.
- **T2 produces** the optional `lastUpdated?: string` field on `AgentPickerItem` + the rest-partition sort (registry order). **Consumes** nothing wire-side (field unsourced in V1.110). The two hosts (`setup-step-agent.tsx`, `settings-agent-section.tsx`) do NOT need to map `lastUpdated` in V1.110 — it stays `undefined`.
- **T3 produces** the refactored `CustomLaunchField` (input-group wrapper). **Consumes** existing `Input` + `Button` from `@42ch/nexus-ui`. Preserves `AgentVerifyStatus` + `agent-picker-verify*` test-ids. No new `@42ch/nexus-ui` primitive.
- **T4 produces** component tests. **Consumes** T1–T3. Covers: common-first order matches priority; More toggles rest; fused control renders one height; verify state machine still drives test-ids.

## Global Constraints

- **No wire/schema change** (`wire_contracts_changed: false`) — `AgentScanEntry` is `additionalProperties: false`; `lastUpdated` stays an optional unsourced view-model field.
- **`AgentPicker` stays presentational** — no daemon client, no wire DTOs; ordering data flows in via `AgentPickerItem` props. The two hosts need no change for V1.110 ordering (registry order = scan-response order).

- **Priority list is match-tolerant** — unknown common ids degrade gracefully to registry order; no crash on missing agents.
- **Residual `R-V110P2-001`** — FB-D2-001 "desc by last-updated" blocked on upstream ACP registry `updated_at` (external) or a V1.111+ scan-response wire change; PM registers it in `status.json` root `residual_findings`.
