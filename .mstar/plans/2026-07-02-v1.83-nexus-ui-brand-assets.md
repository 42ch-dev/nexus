> Package the first Nexus shared UI asset surface: npm package shape, Git LFS for PNG sources, canonical SVG logo variants, and usage guidance.

## 1. Problem Statement

Nexus has app-level design tokens in `apps/web`, but no reusable package for brand assets that can be consumed by `apps/web` now and future product surfaces later. The user has supplied PNG logo references under `packages/nexus-ui/assets/logos/`; this plan turns that directory into a durable package boundary instead of an ad hoc asset dump.

For authors, the asset package is not visible by itself, but it protects the visible experience: every Nexus surface should be able to show the same mark, choose the right light/dark variant, and avoid one-off logo or palette drift as the product grows.

## 2. Scope

### 2.1 Package Scaffold

- Create `packages/nexus-ui/package.json` using npm package name `@42ch/nexus-ui`.
- Add minimal source/export structure for assets, token data, and optional CSS/theme entry points without introducing a React component library.
- Add `README.md` documenting current consumers, future cross-surface compatibility constraints, and asset usage.
- Add `AGENTS.md` documenting package purpose, boundaries, and dependency rules as required by root new-package policy.
- Keep the package dependency-light and framework-neutral in V1.83. It must not import from `apps/web`, require React, or depend on private `nexus-platform` internals.

### 2.2 Git LFS and Binary Asset Policy

- Enable Git LFS patterns for source binary brand assets, starting with `packages/nexus-ui/assets/logos/*.png`.
- Keep canonical SVG assets as regular text files in git.
- Document source vs derived asset ownership:
  - Supplied PNGs are source/provenance references and belong in Git LFS.
  - Hand-authored canonical SVGs are app-consumable text assets and belong in normal git.
  - Any generated raster previews, if added later, must be either reproducible from SVGs or explicitly documented as derived artifacts before commit.

### 2.3 Logo SVG Family

- Use the supplied PNGs as references and produce deterministic SVG redraws of the rounded-square network `N` mark.
- Required variants:
  - default color mark for light backgrounds
  - cyan mark for dark backgrounds
  - white mark for dark/hero surfaces
  - monotone/current-color mark for inline UI usage
  - optional wordmark lockup only if the design review approves it
- Include accessible usage guidance: minimum size, clear space, background contrast, and alt text expectations.

### 2.4 Public Exports and Consumption

- Export stable asset paths and lightweight token/theme constants if useful for consumers. Allowed first-slice entry points:
  - package root for documented token/theme metadata
  - `./tokens` for machine-consumable token data
  - `./theme.css` or equivalent CSS variable entry point if implemented
  - `./assets/logos/*` for SVG logo variants
- Document every public entry point in `README.md`; consumers must not rely on undocumented package-internal paths.
- Treat future `nexus-platform` consumption as a public API design constraint only: package names, export paths, and docs should not assume Web-only internals, but no private platform integration is in scope.
- Avoid moving existing `apps/web` primitives into this package in V1.83.
- Do not expose React components, shadcn wrappers, app shell components, route-aware helpers, or Web-only CSS assumptions in this plan. If a future component library is needed, it should be a later plan with its own API review after P2 proves stable usage.

## 4. Acceptance / DoD

- `packages/nexus-ui` is a valid workspace package under `packages/*`.
- PNG source logo files are matched by Git LFS rules.
- SVG variants are committed as text assets and documented.
- Package exports are explicit in `package.json`, documented in `README.md`, and stable enough for `apps/web` now and future cross-surface use without requiring private platform code changes.
- Package exports remain assets/tokens/theme-only; there are no React component or Web app primitive exports in V1.83.
- Logo guidance lets an implementer pick the correct mark for navigation, dark hero surfaces, inline UI, and accessible alt text.
- No React component library extraction occurs in this plan.

## 5. Non-Goals

- Moving `apps/web/src/components/ui/*` into `packages/nexus-ui`.
- Publishing to npm during this iteration.
- Implementing or validating a `nexus-platform` consumer.
- Redesigning the logo concept beyond faithful vector refinement.

## 6. Validation

- `git lfs track` / `.gitattributes` verification for PNG assets, plus `git lfs ls-files` or equivalent evidence that supplied PNGs are LFS-managed once staged.
- Package metadata review: `name`, `version`, `type`, `files`, and `exports` expose only documented assets/tokens/theme entry points.
- `pnpm --filter @42ch/nexus-ui run typecheck`, `build`, or equivalent package check if scripts exist.
- Workspace install/link check so `apps/web` can resolve `@42ch/nexus-ui` by package name in P2.
- `pnpm --filter web run typecheck` after `apps/web` consumes the package in P2.

## 7. Risks

- SVG geometry may need designer review if the manual redraw differs from the PNG reference.
- Package export shape may need one follow-up after the first platform consumer appears.
- Accidentally exporting React primitives now would freeze a premature API; keep component extraction deferred and documented as roadmap only.
- Git LFS can be configured locally but missed in review; P-last must verify `.gitattributes` and staged LFS pointers before PR.
