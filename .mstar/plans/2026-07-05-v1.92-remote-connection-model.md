## Context

`BrowserClient` / `TauriClient` (`apps/web/src/lib/nexus/`) use same-origin relative paths + send no `X-API-Key` — they rely on loopback keyless-localhost bypass. V1.90's remote bind requires the key, which cannot live in a public SPA bundle. P1 makes a GUI client on a trusted network connect to a remote daemon: parameterise the client transport by base URL + `X-API-Key`, add a "Connect to Daemon" setup screen with TOFU cert-fingerprint confirmation, and persist the connection config client-side. Local same-origin mode stays the backwards-compatible default. Folds in R-V191P1-001 + R-V191P1-002 (same frontend files).

## Scope (plan locked → tasks → implement)

### Tasks (coverage IDs)
- [ ] **T1 — Client transport parameterisation** (`apps/web/src/lib/nexus/`): `BrowserClient` / `TauriClient` accept a configurable base URL (default: same-origin relative → backwards compat) + optional `X-API-Key` header injected on every request. `client-context.tsx` provides the active connection config; the default provider keeps current behaviour when no remote config is set.
- [ ] **T2 — Fingerprint fetch + TOFU pinning** (`apps/web/src/lib/nexus/` + a hook): fetch the cert fingerprint from the P-1/P0 read-only endpoint (no auth) when the user enters an endpoint; display it for first-use confirmation; pin it per-endpoint in client storage; on subsequent connects, compare pinned vs served fingerprint and surface a re-pin warning if they differ. **This is the P0↔P1 seam consumption side** — the ONLY cross-track dependency. See P-1 "P0↔P1 Seam" section for the contract boundary. The fingerprint value format is `SHA256:aa:bb:cc:...` (lowercase colon-hex) per the `CertFingerprintResponse` schema; the fetch hook must parse the codegen'd TS type, not a hand-written shape.
- [ ] **T3 — "Connect to Daemon" setup screen** (`apps/web/src/pages/` or settings section): implement the exact flow and copy locked in P-1 T4 (the "Setup-screen design + DESIGN.md tokens" section). The screen must support all four author-visible states:
  1. First-use (no prior remote config) — calm optional framing, all fields, "Trust this certificate and connect".
  2. Subsequent connect to same endpoint (pinned fingerprint matches) — pre-filled, "Reconnect with these settings".
  3. Fingerprint changed on a pinned endpoint — **blocking warning box** (not auto-accept) with two explicit actions: "Trust the new certificate and continue" vs "Cancel and keep using the old certificate".
  4. "Revert to local" — always-visible secondary action that de-activates the remote config without deleting it; restores default same-origin client; shows success toast.
  The implementation consumes the P-1 T4 DESIGN.md tokens and the exact helper/warning copy. Persists `{ endpointUrl, apiKey, pinnedFingerprint?, label? }`. Sets the active connection config so that `useNexusClient()` returns a client pointing at the remote endpoint with `X-API-Key`. No deviation from the P-1 UX spec without a plan amendment.
- [ ] **T4 — Client storage backends**: web → `localStorage`; desktop (Tauri, `apps/desktop/`) → OS keychain via Tauri plugin where available, fallback to app-data dir. Documented as a deliberate local-first trade-off (web `localStorage` trust boundary == SPA itself).
- [ ] **T5 — Origin allowlist consumption**: ensure the connecting client's origin is accepted by the daemon per the P-1 T3 §16.4 rule. The daemon's Origin allowlist (§13.1) already covers: own-origin, Tauri webview origins (`tauri://localhost`, `http://tauri.localhost`), Vite dev origin, and `NEXUS_DAEMON_ALLOWED_ORIGINS`. The Tauri webview origins are hardcoded — a remote desktop app using Tauri is therefore automatically allowed. A remote web-app (browser SPA connecting to a remote daemon) needs its serving origin added to `NEXUS_DAEMON_ALLOWED_ORIGINS`. There is **no magic auto-allowlisting** of remote origins. Document in the setup-screen UX that authors connecting a remote web-app must ensure their origin is in the daemon's allowlist. No daemon-side runtime change beyond P-1 T3 spec documentation.
- [ ] **T6 — Component tests** (`*.test.tsx`): cover the full author-facing flow locked in P-1 T4 / P1 T3. At minimum:
  (a) local same-origin default still works (no key sent, loopback bypass) — no regression.
  (b) remote config → every request carries `X-API-Key` header + absolute base URL (not relative).
  (c) TOFU first-use flow: user enters endpoint → fingerprint fetched and displayed → "Trust and connect" stores config + switches active client → subsequent renders use the remote client.
  (d) **Fingerprint-change re-pin warning (highest-stakes case)**: when a stored endpoint's pinned fingerprint differs from the newly fetched value, the warning box is shown, "Trust the new..." does **not** auto-proceed, and only an explicit re-pin action updates the stored fingerprint and allows connection. Test both the warning surface and that data operations are blocked until choice.
  (e) "Revert to local" de-activates remote config, restores default client, does not delete the saved remote entry (future multi-endpoint can list it).
  (f) Error states from P-1 spec: unreachable endpoint, fingerprint fetch failure (network / non-2xx / malformed body), and key rejection (401/403) all surface the exact author copy defined in P-1 T4. **Loopback-only daemon (200 with `fingerprint: ""`)** surfaces the info-note copy from P-1 T4 fingerprint state (2), NOT the fetch-failure error copy — the two states are distinct and asserted separately.
  (g) API key is never logged or rendered in plain text in the UI (masking + password field).
  These tests must be runnable in isolation (no real daemon required) using the existing test-provider pattern (`ClientProvider` with injected client) and must assert on the exact copy strings from the UX spec so that copy changes are caught.
- [ ] **T7 — R-V191P1-001 split CSV toast** (`apps/web/src/api/queries.ts` `useBatchUpdateFindings` + `apps/web/src/pages/findings-page.tsx`): split the bulk-PATCH toast into not_found vs conflict lines (or persistent banner listing conflict IDs separately from not_found IDs). Closes R-V191P1-001.

## Acceptance
- A GUI client connects to a remote daemon via the setup screen (endpoint URL + API key + explicit TOFU fingerprint confirmation) and thereafter operates identically to local on every author-facing surface (Strategy/Outline/World KB canvases, reading chrome, findings triage including V1.91 batch updates, memory review, SOUL, presets, chapters, etc.). Local same-origin mode is unchanged (regression tests green). The only visible surface difference is the connection-status indicator.
- TOFU pinning works exactly as specified in P-1 T4: first-use confirmation stores the fingerprint; subsequent connect with matching fingerprint is frictionless; fingerprint change on a pinned endpoint shows a blocking re-pin warning that must be explicitly accepted before any data request is issued. Key stored per-backend (localStorage web / keychain-or-appdata desktop). "Revert to local" de-activates without deleting the saved config.
- R-V191P1-001 + R-V191P1-002 closed (`lifecycle: resolved`).
- `pnpm --filter web test` + `pnpm --filter web build` + TS typecheck green; DESIGN.md tokens consumed; component tests (T6) assert on the exact author copy strings from the P-1 T4 UX spec.
