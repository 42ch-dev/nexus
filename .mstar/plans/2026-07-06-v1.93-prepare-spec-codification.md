## Context

V1.92 added TLS with a normative SAN generation rule + regenerate-on-bind-host-mismatch behaviour in `knowledge/specs/daemon-runtime.md` §15.1 (lines 749–762). The rule is **already codified** as a subsection of §15.1 ("TLS listener"): loopback always (`127.0.0.1`, `::1`, `localhost`) + the non-loopback `bind_host` (IP or DNS SAN) + wildcard skip (`0.0.0.0`, `::`); the cert lifecycle paragraph already states regeneration on bind-host mismatch with an INFO log message. The corresponding implementation (`cert_covers_bind_host` at `tls/mod.rs:228`, `try_load_existing` return-`None` fallthrough at line 95, `build_subject_alt_names` at line 191) is also landed on `main` (V1.92 PR #120).

R-V192SPEC-001 was filed because the original V1.92 spec note was a helper docstring + partial paragraph; the fix-wave expanded it into the current normative text before PR merge. **This plan therefore tightens the existing spec for precision gaps** rather than writing a new section from scratch. The gaps that survive in the current text:

1. **`bind_host` resolution** is implicit — the spec does not state that `bind_host` is the literal CLI `--host` value (no DNS resolution, no interface enumeration). The code already behaves this way; the spec must make it explicit so future implementers do not introduce DNS resolution.
2. **IPv6 encoding** is mentioned (`::1` for loopback) but no non-loopback IPv6 example is given and the interaction with the "parse as IP → IP SAN, else DNS SAN" rule for IPv6 literals (e.g. `fd00::1`) is not illustrated.
3. **Hostname character-encoding edge case**: a hostname passed to `--host` that is not a valid IA5String is omitted from the SAN (per `tls/mod.rs:210-217`). The spec should document this graceful degradation.
4. **Cross-reference to §16.2 FingerprintGate re-pin** is absent. The regenerate-on-mismatch paragraph says "the daemon regenerates the cert" but does not link to the client-side consequence (TOFU Phase 3 warning). This cross-reference is necessary for the security story to be coherent in one reading pass.
5. **Loopback-bind semantics**: the spec states loopback SANs are always present and the cert is reused on loopback binds, but does not explicitly say "loopback binds never trigger regeneration" or catalogue the full set of loopback-equivalent addresses the validator treats as covered (`127.0.0.1`, `::1`, `localhost`, any IPv4/IPv6 loopback address). The code already handles this at `cert_covers_bind_host:232-243`; the spec should match.

The P0 implementation already exists on `main` — this plan's implementer is **verifying** the spec accurately reflects the shipped behaviour and **closing the precision gaps**, not writing the rule from scratch.
