  - A: V1.87 was a small UI-maturation + security-fast-follow iteration. - **Q: Will the `fs/*` admission change remove any security boundary?**
  - A: No. Gate 4 (permissions.toml) remains in the admission pipeline. The path check is moved to the `execute_*` handlers, which still reject out-of-bounds paths before any filesystem access. This is a relocation of an existing check, not a removal.
- **Q: Do we need new tests?**
  - A: Each Rust fix (T3, T4, T5) must include a regression test or extend an existing test to demonstrate the behavior. Frontend changes (T1, T2) update existing component tests or add type assertions. Tracker cleanup (T7) is doc-only and verified by inspection + grep. T6 is verification only.
- **Q: Are there any schema/contract changes?**
  - A: No. `wire_contracts_changed: false` is locked in frontmatter and compass.
- **Q: Which exact rows move in tracker hygiene?**
  - A: Only the 8 explicitly listed in compass §2 SP-4 and plan T7: BL-10, BL-12, PF-ESSAY, PF-GAME-BIBLE, PF-SCRIPT, FEAT-WORLD-KB-RELATIONSHIPS, REL-01, DF-49. No other rows are touched. Destination: `.mstar/archived/shipped-features-tracker.md`. Active tracker must contain zero of these after the move.
- **Q: What is the success bar for "resolved" residuals?**
   - A: Each residual must have a clear closure note in `status.json` (or plan notes) plus evidence: test run output, diff link, or inspection record. "Marked done" without evidence is insufficient for QA.
- **Q: `resolve_guarded_path_async` is a private `async fn` in `host_tool_handlers.rs`. How do `outline.rs` and `chapters.rs` call it?**
    - A: Extract it to `src/api/path_guard.rs` as a `pub async fn resolve_guarded_path_async(workspace_root: PathBuf, rel_path: String, must_exist: bool) -> Result<PathBuf, NexusApiError>`. The sync `resolve_guarded_path` in the same file is unchanged and remains the canonical implementation. Both `outline.rs` and `chapters.rs` already import from `crate::api::path_guard`; changing the import to include `resolve_guarded_path_async` is a one-line diff. The existing call sites in `host_tool_handlers.rs` update their import accordingly (from local `async fn` to `path_guard::resolve_guarded_path_async`). Note: the async wrapper takes **owned** `PathBuf` + `String` (the `spawn_blocking` closure must own its values), so each migrated call site must convert `&Path` → `.to_path_buf()` and `&str` → `.to_string()`.
- **Q: Will the `resolve_guarded_path_async` error type change at migrated call sites?**
    - A: No. The async wrapper delegates to `resolve_guarded_path` inside `spawn_blocking`, so it produces the same `NexusApiError` variants (`BadRequest { code: "chapter_path_*" }`). The only new error is `Internal { code: "PATH_GUARD_PANIC" }` from a `spawn_blocking` join failure — this falls through to the `other => other` arm at every mapping site (same as any non-BadRequest error). Existing per-site `.map_err(|e| match e { ... })` patterns remain identical.
- **Q: Is `chapters.rs:174` (sync `resolve_guarded_path` probe in `to_detail`) in scope for T3?**
   - A: No. The probe runs inside a synchronous DTO mapper called from async handlers. It does one lightweight `canonicalize` per chapter row to check outline editability, with no FS content I/O or file creation. Making `to_detail` async would require threading `async` through multiple call sites for marginal benefit. This is a deliberate scope exclusion; the practical blocking impact is negligible. The sync `resolve_guarded_path` function remains available for legitimate sync contexts like this.

## risks and rollbacks

- **Risk**: Async migration subtly changes error codes returned to callers (affects `nexus.fs.*`, outline, chapters tools).
  - **Mitigation**: Preserve existing `NexusApiError` match arms exactly in each migrated site. The async wrapper delegates to the sync `resolve_guarded_path` inside `spawn_blocking`, so error variants are identical. The only new error (`Internal { code: "PATH_GUARD_PANIC" }`) falls through to the `other => other` arm at every mapping site. Add regression test in `path_guard.rs` for the async wrapper asserting both success and rejection paths. Run full `cargo test -p nexus-daemon-runtime`.
  - **Rollback**: Revert the call-site change; the sync helper remains available.
- **Risk**: Removing admission-pipeline path check for `fs/*` could bypass policy if `execute_*` is invoked directly.
  - **Mitigation**: `execute_*` are `pub(crate)` registry wrappers; the only caller is the registry dispatch path. Gate 4 (permissions) remains in admission. `execute_*` still calls `resolve_guarded_path_async` before FS access.
  - **Rollback**: Re-add the Gate 3 path check (one-line revert).
- **Risk**: `Arc<DaemonApiConfig>` breaks existing tests that construct `DaemonApiConfig` or breaks middleware state typing.
  - **Mitigation**: Do **not** change `create_router` public signature. Callers pass by value; wrapping is internal. Update only the two middleware extractors to `State<Arc<DaemonApiConfig>>`. Field access through `config.*` works unchanged via `Arc`'s `Deref`. The `build_router` test helper mirrors the same internal wrapping. Compile-time errors surface mismatches immediately.
  - **Rollback**: Remove the `Arc::new` wrapper and revert the two extractor signatures (internal change only).
- **Risk**: Tracker archive row drift (wrong rows moved, or shipped rows left in active tracker).
  - **Mitigation**: Move exactly the 8 listed rows. Post-edit verification with explicit grep + inspection before commit. QA sign-off on tracker state.
  - **Rollback**: Git revert the single doc commit; re-run the move with verification.
