# P-1 — Prepare: Daemon API rename design + remote listener security spec

## specify

**Problem statement**
The daemon HTTP surface is currently called “Local API” and exposed under `/v1/local/*`. The web UI and desktop shell are architecturally capable of connecting to a daemon on a remote host, so the name is misleading and will become more so if remote connectivity is enabled. We need a consistent new name, a full rename plan, and a security model for optional remote binds before implementation starts.

**User / author value**
- Authors who self-host the daemon on a home server or inside a VM can explicitly enable remote access without the product calling the surface “local”.
- Contributors and future clients see an API name that matches its actual capabilities.

**Scope**
- Choose canonical name and path prefix.
- Define every identifier/folder that must move.
- Define remote-listener security gate.
- Amend normative specs and AGENTS so P0/P1 have authoritative text to follow.

**Non-goals**
- No code changes beyond spec/AGENTS/plan text.
- No codegen run.
- No new TLS, auth, or cloud integration.

**DoD draft**
- Compass + all four plans written and on disk.
- Spec amendments identify every renamed file/folder/module.
- Remote-listener security rules documented.
- Phase 1 Review & Edit chain complete; compass `status: locked`.

## clarify

| # | Ambiguity | Resolution |
|---|---|---|
| 1 | Canonical name | **Daemon API** (grill-me locked). “Gateway API” rejected for implying non-existent routing/cloud layer. |
| 2 | Path prefix | `/v1/daemon/*` (no backward compat; pre-1.0 surface). |
| 3 | Remote listener gate | Non-loopback bind requires **both** `NEXUS42_DAEMON_API_KEY` and `NEXUS_DAEMON_REMOTE_BIND=1`. |
| 4 | Rename depth | Full rename: schemas folder, generated Rust/TS modules, router paths, handler docs, web client base URL/comments, specs/docs/AGENTS. |
| 5 | Codegen ownership | P0 performs the actual schema move and runs `pnpm run codegen`; P-1 only designs the mapping. |
