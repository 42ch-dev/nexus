## Specify

### Problem

The desktop onboarding flow remains brittle after V1.96. A new author can still double-click the app and get blocked before reaching the product. The latest feedback identified three P0-class problems:

1. The welcome screen still feels crowded and has right-edge/flex boundary problems.
2. Clicking Browse can fail because the Tauri command receives the wrong argument shape for `defaultPath`.
3. The daemon can still appear stuck during first launch, and the sidecar manager must not start in a false `Starting` state that suppresses a real spawn.

This plan turns the existing uncommitted prototype diff into a formal SDD-owned implementation. The prototype is useful input only: no PM-thread code counts as implementation until `fullstack-dev` inspects each relevant hunk, accepts, revises, or rejects it, and verifies the resulting hunk against this plan.

### Scope

In scope:

- Setup wizard layout containment and truncation fixes.
- Native folder picker IPC casing (`defaultPath`).
- Sidecar manager initial-state and `start_with_budget` short-circuit correctness.
- Cleanup of local-machine path literals introduced by the prototype in app code/tests.
- Regression tests covering the touched TypeScript and Rust behavior.
- Clean-state and existing-install desktop smoke evidence as a hard Done gate, including the initial state, command/environment, observed path, and final result.

Out of scope:

- New onboarding product features.
- New daemon API routes, JSON schemas, generated contracts, or `@42ch/nexus-contracts` changes.
- Signing/notarization/auto-update/multi-OS release hardening.
- Broad config/db atomicity hardening or config-file rewrite policy changes.
- Cross-crate default workspace/path resolver consolidation.
- Release packaging polish or default-path product renaming beyond fixture cleanup.

### Architecture Invariants

- **Sidecar initial state:** a newly constructed `SidecarManager` has no owned child and starts in `Stopped`; it must not default to `Starting`.
- **Meaning of `Starting`:** `Starting` is only valid while a spawn attempt is in progress or an owned child is already present and being health-probed. `Starting` with `child.is_none()` is an invalid state and must not suppress a spawn or retry.
- **Attach versus own:** attaching to an already healthy daemon is allowed and must preserve existing-install behavior, but attach must not fabricate an owned child handle. Owned-child cleanup remains limited to processes spawned by the desktop app.
- **Retryability:** `Stopped` and `Error` are retryable states. Retry/Reset paths must be able to call `start_with_budget` and either spawn a new owned child, attach to a healthy daemon, or surface a bounded error.
- **Wizard observation:** the UI may observe the state through existing desktop capabilities and status/detail fields only; V1.97 must not introduce new schema or wire-contract requirements.
