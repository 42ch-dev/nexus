## 1. Problem Statement

The Web UI has a mature functional surface but its visual identity remains generic compared with the new Nexus logo and VI palette. This plan performs a focused application pass: app shell, navigation, header/sidebar, and base components should visibly adopt the new brand while preserving existing feature behavior.

For authors, success means the workspace now feels intentionally Nexus when they open it: the mark is present, the palette is coherent, interactive states are clearer, and existing writing/review/canvas tasks still work the same way.

## 2. Scope

### 2.1 Token Consumption

- Update `apps/web/tailwind.config.ts` and `src/index.css` to consume the V1.83 brand token contract.
- Preserve existing CSS variable names when possible to avoid wide churn.
- Add or update brand-specific variables only when they are documented in DESIGN.
- Consume root brand tokens through the Web DESIGN mapping and/or public `@42ch/nexus-ui` token/theme exports. Do not introduce raw brand hex values directly in components unless the relevant DESIGN file records the exception.
- Keep app-specific token aliases for existing consumers when they reduce churn, but document the alias-to-root-token relationship in `apps/web/DESIGN*.md`.

### 2.2 Shell and Base Components

- Apply logo placement and brand surfaces in the Web shell/navigation/header/sidebar.
- Import logo assets through documented `@42ch/nexus-ui` package exports rather than relative paths into `packages/nexus-ui` internals.
- Prioritize the first-frame shell impression and repeated base primitives over deep page-specific decoration.
- Update base UI primitives as needed:
  - Button
  - Card
  - Input
  - Textarea
  - Select
  - Badge/status pills
  - Empty/loading/error states
- Keep design changes centralized and token-driven.
- Do not move primitives into `packages/nexus-ui` in this plan. If duplicated styling suggests future extraction, record the candidate and leave extraction to a later component-library plan.

### 2.3 Focused Page Touches

- Touch pages only where needed to validate shell and primitive changes.
- Avoid reworking page information architecture, data flows, canvas behavior, or SOUL/findings business logic.
- Do not introduce page-by-page redesign acceptance criteria in this slice; page polish belongs to the next iteration unless required to fix a regression caused by token changes.
- Keep file ownership narrow: P2 owns Web implementation files and Web mapping updates needed for consumption. It should not edit root DESIGN token values or package exports except to correct integration blockers agreed with P0/P1.

### 2.4 Tests and Visual QA

- Update or add tests where class names, accessible labels, or logo rendering changes affect assertions.
- Include a lightweight visual checklist for light/dark mode shell and base primitives.

## 4. Acceptance / DoD

- Web shell visibly uses the Nexus mark and brand palette in light and dark modes.
- Base primitives use DESIGN tokens, not hard-coded ad hoc colors.
- `apps/web` imports package assets through public `@42ch/nexus-ui` exports and keeps relative package-internal paths out of application code.
- Visual acceptance is satisfied by shell/navigation/header/sidebar plus common primitives; it does not require redesigning every product page.
- Existing product workflows continue to render and pass tests.
- No backend, schema, or contract changes.

## 5. Non-Goals

- Rebuilding Canvas layouts.
- Rewriting SOUL, Findings, Memory, or Work flows.
- Reworking information architecture, route structure, or product copy beyond brand-surface labels needed for logo/accessibility.
- Component-library extraction to `packages/nexus-ui`.
- Changing `@42ch/nexus-ui` package export names or root DESIGN token names without returning to P0/P1.
- Private platform integration.

## 6. Validation

- `pnpm --filter web run typecheck`
- Focused component/page tests affected by shell/base primitive changes.
- `pnpm --filter web run build`
- Package resolution/import check for public `@42ch/nexus-ui` exports from `apps/web`.
- Manual visual checklist for light/dark logo variants, nav, buttons, cards, inputs, badges, focus rings, hover/active states, disabled states, and empty/loading/error states.
- Contrast spot checks against P1's approved foreground/background and focus-ring pairings.

## 7. Risks

- Token renaming can cause broad churn; prefer preserving current Web token names and mapping them to root brand tokens.
- Logo rendering in dark/light surfaces needs explicit variants to avoid contrast regressions.
- Direct imports into package internals would couple Web to the package layout; use public exports only.
- Visual polish can hide workflow regressions; keep validation focused on existing route rendering and author flows touched by shell/base primitives.
