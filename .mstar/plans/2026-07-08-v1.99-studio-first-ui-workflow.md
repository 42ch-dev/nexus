# P2 — Studio-First UI Workflow Codification

**Goal:** Turn the validated V1.99 practice into durable guidance for future UI work: compose pure View components in `apps/design-studio`, then promote/integrate into `@42ch/nexus-ui` and `apps/web` when accepted.

**Architecture:** This plan codifies a development workflow after P0/P1 prove it. It chooses the lightest durable landing surfaces: package/app `AGENTS.md` for repo-specific rules, `.mstar/knowledge` at iteration-close for reusable Nexus patterns, and a possible skill proposal only after validation if the behavior is reusable beyond this repo and passes `mstar-skill-authoring`.

**Tech Stack:** Markdown guidance, `AGENTS.md`, `.mstar/iterations/v1.99/**`, optional `.mstar/knowledge` promotion at close, optional post-validation skill proposal only if justified.

**Execution:** inline

## Product Framing

**User value:** Future Nexus UI contributors should know when to prototype in Design Studio, when to promote to `@42ch/nexus-ui`, and when to integrate directly in Web. The workflow should reduce iteration cost without creating a second product shell.

**Problem statement:** "Use Design Studio first" is only useful if V1.99 proves where the boundary works. Premature documentation would become process theater; missing documentation would make the next UI plan relearn the same component and fixture rules.

**Target state for this plan:** P2 turns P0/P1 evidence into the lightest durable guidance that future agents can follow. It records what worked, where the workflow failed, which repo/package rules should change, and whether knowledge or a skill is justified.

**Non-goals:** Do not create `.mstar/knowledge/**` during iteration-start, do not create a new skill by default, and do not restate Morning Star dispatch/review process as UI workflow guidance.

## Global Constraints

- Do not create `.mstar/knowledge/**` content during iteration-start or before compound; use iteration workspace during execution.
- Do not create a new skill during this plan by default; skill work is conditional on PM/user approval after validation and all `mstar-skill-authoring` purpose-test criteria passing.
- Keep repo-specific rules in repo/package `AGENTS.md`; avoid duplicating Morning Star harness rules.
- Workflow guidance must be based on P0/P1 evidence, not aspiration.
- The workflow must preserve import boundaries: Studio composes pure View fixtures, `@42ch/nexus-ui` owns only approved presentational primitives, and Web owns routing, daemon data, app providers, and behavior.
- `@web-ui/*` remains transitional for unpromoted primitives only; promoted primitives should be consumed through `@42ch/nexus-ui` in Studio and Web or recorded as an intentional wrapper/non-promotion decision.
- No runtime code changes unless they support documentation examples or import-boundary checks approved by P-1.

## Acceptance Hooks

- The final workflow cites concrete P0/P1 evidence, including at least one Studio → Package → Web component path and one `/surfaces` visual iteration.

- Any skill decision includes a positive or negative purpose-test result; absence of a skill is an explicit decision, not an omission.
