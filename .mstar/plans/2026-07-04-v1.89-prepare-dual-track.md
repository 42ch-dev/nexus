### C. SQLite migration design (P-1 authors the `.sql` file; P0 implements DAO/handlers)

**Artifact**: `crates/nexus-local-db/migrations/20260704_000002_reading_progress_and_annotations.sql` (owner: `@architect`)

**Tables**:

```sql
CREATE TABLE reading_progress (
  creator_id      TEXT NOT NULL,
  work_id         TEXT NOT NULL REFERENCES works(work_id) ON DELETE CASCADE,
  chapter         INTEGER NOT NULL,
  scroll_progress INTEGER NOT NULL DEFAULT 0
                    CHECK (scroll_progress >= 0 AND scroll_progress <= 10000),
  volume          INTEGER,
  updated_at      TEXT NOT NULL,
  PRIMARY KEY (creator_id, work_id, chapter)
);

CREATE TABLE reading_annotations (
  -- annotation_id is a server-generated UUID v4; must not be client-supplied on create.
  annotation_id TEXT PRIMARY KEY,
  creator_id    TEXT NOT NULL,
  work_id       TEXT NOT NULL REFERENCES works(work_id) ON DELETE CASCADE,
  chapter       INTEGER NOT NULL,
  volume        INTEGER,
  start_offset  INTEGER NOT NULL,
  end_offset    INTEGER NOT NULL
                  CHECK (end_offset > start_offset AND start_offset >= 0),
  color         TEXT NOT NULL DEFAULT 'yellow'
                  CHECK (color IN ('yellow','blue','green','pink')),
  note          TEXT,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);
```

**Indexes**:

- `reading_progress`: `(creator_id, work_id, chapter)` covers the GET progress query.
- `reading_annotations`: `(creator_id, work_id, chapter)` covers the per-chapter list; `(creator_id)` covers future per-creator browsing (cost is negligible for a single-author local DB).

**Foreign-key note**: `reading_progress` does **not** carry an FK on `(work_id, chapter)` referencing `work_chapters(work_id, chapter)`. `work_chapters` is a metadata table that may not exist for every Work at migration time, and the reading surface is permissive (it displays progress for any chapter the UI navigates to). Cross-table integrity is enforced in handler queries via the `works` FK join.

### E. Clarify gates (converged — product decisions locked)

1. **Progress scope → per-creator, per-chapter (CONFIRMED).** Product rationale: reading progress is personal to the author and scoped to a chapter. Volume is stored as context but not part of the PK because chapter number is unique within a Work via `work_chapters` PK `(work_id, chapter)`.
2. **Annotation anchoring → character offsets with drift notice (CONFIRMED).** Product rationale: fingerprint/CRDT reconciliation is valuable but too complex for the MVP; a visible drift notice preserves author trust without blocking the feature.
3. **Body-ownership invariant preserved (CONFIRMED).** Product rationale: the V1.75 pivot made canvas the sole authoring surface. Reading annotations are metadata about the body, not mutations of `body_path` or outline files. Any future "accept annotation into manuscript" flow must go through canvas/Outline API, not the reading surface.
4. **Color model → semantic palette (CONFIRMED).** Product rationale: avoid open-ended hex inputs that complicate dark-mode contrast and future sync. Use a small enum mapped to DESIGN.md tokens (e.g., `yellow`, `blue`, `green`, `pink`).

**Decision**: all four gates are LOCKED with the recommendations adopted. P0 and P1 plans may treat these decisions as binding scope.
