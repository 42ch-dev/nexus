# P-1 — Prepare: Visual System Deepening Contract

**Goal:** Lock the product, package-boundary, and visual-direction contract for V1.99 before moving UI primitives or redesigning `/surfaces`.

**Architecture:** This plan is a product/architecture Prepare plan. It updates iteration-scoped specs/guides and any required package rules so implementation plans can work from a stable boundary instead of guessing which components belong in `@42ch/nexus-ui`.

**Tech Stack:** Markdown specs, root DESIGN pair, `@42ch/nexus-ui`, `@nexus/design-tokens`, `apps/design-studio`, `apps/web`.

**Execution:** inline

## Product Framing

**User value:** Contributors should be able to make a visual decision once, see it quickly in Design Studio, reuse it through `@42ch/nexus-ui` when it is truly shared, and integrate it into Web without redesigning or revalidating the same primitive from scratch.

**Problem statement:** V1.98 created a safe read-only studio but preserved two sources of friction: reusable primitives still belong to `apps/web`, and `/surfaces` does not yet demonstrate a compelling product-quality direction. Without a locked boundary and workflow contract, P0/P1 implementers would either over-promote app-specific code or polish fixtures that cannot graduate into real product UI.

**Target state for this plan:** P-1 must leave implementation teams with an explicit promote / keep-web / keep-studio decision model, an observable `/surfaces` quality bar, and a landing strategy for workflow guidance that does not confuse Morning Star harness process with product work.

**Non-goals:** This plan does not implement components, redesign `/surfaces`, run visual QA, create knowledge content, or create skill artifacts. It prepares the product contract those later plans must obey.

## Global Constraints

- Plans must solve real problems; Morning Star harness gates are process, not plan scope.
- Start-chain edits may use `.mstar/iterations/v1.99/**` and `.mstar/specs/**`; do not add `.mstar/knowledge/**` content during iteration-start.
- `@42ch/nexus-ui` may only accept pure presentational, token-driven components with no app state, daemon, route, or layout dependency.
- Package architecture must lock public exports, runtime dependency posture, token consumption, asset rules, and consumer wrapper strategy before P0 implementation starts.
- `apps/design-studio` remains daemon-independent and read-only.
- `wire_contracts_changed: false` unless explicitly revised by architect review.

## Prepare Acceptance Hooks

- P0 can name its first batch without using "promote more components" as open-ended scope.
- P0 can implement without deciding package exports, dependency placement, asset handling, or wrapper strategy during coding.
- P1 can evaluate `/surfaces` against concrete qualities: hierarchy, rhythm, depth, affordance clarity, theme parity, focus visibility, and fixture-to-product traceability.
- P2 can record evidence from P0/P1 rather than inventing workflow guidance before the workflow has been proven.
- `.mstar/specs/design-studio.md` reflects that V1.99 reopens the V1.98 brand-only package boundary only for approved presentational primitives.
