## Specify

### Problem

V1.94 implement plans (P0 backend + P1 frontend) need frozen, normative
contracts before they can be cut onto parallel worktrees. Four spec/design
surfaces currently lack the rules:

1. `desktop-shell.md` has no Setup Wizard section — the 4-step flow, the
   `setup_completed` marker semantics, the per-launch daemon-ready gate,
   and the `~/Documents/nexus42/default/` workspace-default rule are all
   unspecified.
2. `desktop-shell.md` has no ACP Agent Detection contract — the daemon-side
   scan endpoint, PATH-probe safety boundary, and response shape are
   undefined.
3. `web-ui.md` §Information Architecture still describes the V1.64 6-screen
   flat sidebar; it lacks the two-tab (Creator | Orchestrator) IA, footer
   profile switcher, simplified daemon status bar (running = restart-icon
   only), and Strategies unification rules.
4. `apps/web/DESIGN.md` §Component Primitives/Button does not record the
   dark-bg → light/white-text invariant; the dark primary token
   (`dark:bg-brand-cyan dark:text-brand-deep-blue`) violates it.

Without P-1, P0 and P1 would each infer the contract independently and
diverge at integration.

### User value

Implement plans can run on parallel worktrees against a frozen contract
(no mid-flight re-clarify). Authors get a coherent desktop-shell spec to
read.

## Clarify

**Closed decisions** (inherited from compass grill-me — no new ambiguity):

- Workspace default is `~/Documents/nexus42/default/` (cross-platform via
  `dirs::document_dir()`); not `~/.nexus42/workspace/`.
- The PATH scan probes only registry-known binary names; it does not
  execute user-supplied commands.
- The button invariant is a token-level rule + a documented invariant,
  not a full button-system redesign.
- Strategies unification is entry-point only; the V1.70 canvas surface is
  preserved verbatim at `/strategies/:presetId`.

**Open assumptions** (to validate during P-1 editing):

- `dirs::document_dir()` returns `~/Documents` on macOS/Linux and
  `Documents` under the user profile on Windows. (Cross-platform path
  resolution belongs in P0; P-1 only codifies the rule.)
- Existing `~/.nexus42/config.toml` is tolerant of an added
  `setup_completed` field (TOML deserialisation should accept unknown
  fields or the schema must extend gracefully). P-1 records this as a
  P0 implement contract.

## Plan

### Target state

A reader of the spec/design surfaces can implement P0 and P1 in parallel
without further clarification. The agent-scan contract is normative
enough to generate codegen types and to drive the wizard's recommendation
logic. The IA spec is normative enough to drive the sidebar rewrite. The
button invariant is normative enough to drive the audit.

### Module boundaries / interface contracts

- `POST /v1/daemon/agent-host/scan` — request/response shapes frozen here
  (see schemas). The handler is P0; only the contract is P-1.
- `~/.nexus42/config.toml` — additive `setup_completed: bool` field;
  optional, defaults to absent (= false). No breaking change to existing
  config consumers.
- Sidebar IA — `NAV_ITEMS` shape in `apps/web/src/components/layout/sidebar.tsx`
  gains a two-tab grouping; the consumer API for `NavLink` is unchanged.

### Risks / rollback

- Spec over-engineering: P-1 must stay normative + frozen-contract, not
  prescribe P0/P1 internals. The architect edits to remove prescription.
- Schema naming drift: the agent-scan schema names must match what P0
  handler + P1 client expect. The architect owns the name freeze.
