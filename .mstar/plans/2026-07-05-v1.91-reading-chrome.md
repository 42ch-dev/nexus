# P0 — Track A: Profile-Specific Reading Chrome

## 1. specify

### Problem statement (P0 headline)

The current manuscript reading surface in `apps/web` is profile-agnostic. A novel chapter, an essay, a game-bible entry, and a script scene are all rendered the same way, missing the typographic and structural cues that help authors read their own work in the right mental model.

### User value (P0 primary)

Authors open a Work and **immediately perceive the profile identity** of what they are reading (novel vs essay vs game-bible vs script) through the reading surface itself. This reduces cognitive load when switching between different kinds of creative work and makes the reading experience feel native rather than generic.

### Scope (P0 headline — strictly read-only)

- Implement profile-aware **read-only** chrome in `apps/web` for exactly the four shipped profiles: `novel`, `essay`, `game-bible`, `script`.
- Consume (do not invent) the locked `apps/web/DESIGN.md` `## Reading Chrome` token section produced by P-1. All profile differentiation is token-driven.
- Add UI/component tests that assert profile-specific rendering (≥2 distinct visual markers per profile per the locked checklist).
- Wire into the existing reading page; read `work_profile` from the already-loaded Work object.

P0 is the **headline** delivery. P1 (findings batch) is the companion and must not touch reading chrome.

### Non-goals (strict — cross-reference compass §6)

- **No writes whatsoever** to `body_path`, outline, timeline, or any manuscript state. Reading chrome is presentational only. Any diff containing PUT/PATCH/POST on body or outline is out of scope and must be rejected.
- **No backend routes, Local API changes, or wire contract modifications.** P0 adds zero crates, zero handlers, zero schemas, zero backend code. It is a frontend-only change to `apps/web`.
- **No new HTTP requests** — reading chrome reads `work_profile` from the already-loaded Work object; no additional API fetches.
- No new canvas surfaces or editor-adjacent UI.
- No mobile-specific chrome variants in V1.91.
- No new work profiles.
- No overlap with P1 findings batch work (different components, different worktree after P-1 lands).
- See compass §6 for full enforced non-goals list.

### Definition of Done (DoD) — aligned with compass §5 AC

- All four shipped profiles (`novel`, `essay`, `game-bible`, `script`) render with ≥2 distinct visual markers each, sourced exclusively from the P-1 locked `apps/web/DESIGN.md` `## Reading Chrome` token section.
- Component test for each profile asserts profile-specific classes/attributes (e.g. `data-chrome-profile="..."`) and token-derived styles.
- PR includes at least one visual artifact (screenshot or storybook capture) per profile demonstrating the differentiation.
- Reading surface exercises only GET paths for Work/body. Verified by code review + absence of write calls in the diff.
- `pnpm --filter web run typecheck` and `pnpm --filter web run test` (reading surface area) pass.
- P0 plan merges to `iteration/v1.91` only after P-1 is Done and DESIGN.md tokens are locked.

## 2. clarify

### Design source

- `apps/web/DESIGN.md` §Reading Chrome is the SSOT for tokens.
- Profile list is read from the Work object (`work_profile`).
- Unknown profile falls back to `novel` chrome.

### Per-profile chrome elements (locked by P-1; this is the acceptance bar)

P-1 produces the definitive checklist with ≥2 distinct markers per profile. The table below is the working draft that P-1 will lock (or amend) before P0 starts. All markers must be implemented via DESIGN.md tokens.

| Profile | Chrome elements (≥2 distinct visual markers required) |
|---|---|
| `novel` | Chapter/epigraph title treatment + thematic scene separator (e.g. `* * *` or rule); optional dialogue indentation cue or volume/chapter breadcrumb |
| `essay` | Section/subsection hierarchy styling + styled blockquote or footnote marker treatment; citation emphasis |
| `game-bible` | Term cross-reference link style + definition callout or category/section badge; compact line height for sidebar-friendly lists |
| `script` | Character name block + parenthetical vs action line visual distinction + scene heading treatment |

**Fallback**: unknown `work_profile` value → `novel` chrome.

**Verification**: component test + PR visual per profile. See compass §2.2 and §5 for the verifiable AC.

### Intent gate

Real goal (P0 headline): make the **read-only reading surface feel native to the work type** (profile identity is immediately perceptible). Not to build a new editor, writing mode, canvas surface, or any write path. P1 (findings batch) is deliberately separated as companion scope.

## 3. plan

### Target state (P0 implementation)

- Profile-aware read-only chrome components under `apps/web/src/components/reading/` (or adjacent reading surface module).
- Existing reading page selects and renders chrome based on `work_profile` from the loaded Work (no new route or data fetch).
- `apps/web/DESIGN.md` `## Reading Chrome` section (locked by P-1) is the single source of truth; components consume tokens only.
- Component tests + PR visuals demonstrate the four distinct experiences.
- Zero changes under `crates/`.

### Module boundaries

- Reading chrome components live under `apps/web/src/components/reading/`.
- Tokens come from `apps/web/DESIGN.md` and are applied via Tailwind/CSS variables.
- **Zero changes to `crates/`** — no backend handler, no DAO, no schema, no wire contract, no Local API route.
- **Zero new HTTP requests** — `work_profile` is read from the already-loaded Work object on the existing reading page.
- No new dependencies or npm packages.

### Roadmap / Batch Plan

Single-batch implementation within P0.

### Risks and rollbacks

- Risk: token explosion.
  - Mitigation: start with one token per distinct element; do not duplicate existing typography tokens.
- Risk: profile detection missing.
  - Mitigation: assert `work_profile` is loaded before chrome selection; fallback to `novel`.

### Verification plan

- `pnpm --filter web run typecheck`
- `pnpm --filter web run test`
- Manual/ screenshot review in PR description.
