# P1 — Design Studio Surfaces Visual Direction

**Goal:** Redesign `apps/design-studio` `/surfaces` so setup and shell compositions establish a coherent, premium Nexus visual direction rather than feeling like util-heavy static demos.

**Architecture:** Design Studio remains a daemon-independent visual proving ground. Surface fixtures are pure View compositions using shared tokens and promoted primitives where available; live routing, daemon data, and `apps/web` layout imports remain out of scope.

**Tech Stack:** React 18, Vite, Tailwind via `@nexus/design-tokens`, `@42ch/nexus-ui`, `apps/design-studio`, Vitest/jsdom.

**Execution:** mstar-sdd

## Product Framing

**User value:** Maintainers and contributors should be able to look at `/surfaces` and understand the intended Nexus setup/shell feel before touching the live daemon-backed app. The page should be a credible visual reference, not a collection of placeholders.

**Problem statement:** The current surfaces are useful as proof that fixtures can render, but they do not yet communicate a cohesive product experience. If they remain visually weak, Design Studio cannot serve as the trusted first stop for UI decisions.

**Target state for this plan:** `/surfaces` presents two polished, daemon-free compositions: setup/welcome and app shell. They should demonstrate hierarchy, rhythm, depth, actionable affordances, theme parity, and enough product context to guide future Web integration.

**Non-goals:** This plan does not implement live routing, creator bootstrap, daemon startup, desktop clean-state behavior, or full `apps/web` screen redesign.

## Global Constraints

- Read P-1 visual direction and workflow guide before implementation.
- Do not import `apps/web/src/pages/**`, `apps/web/src/components/layout/**`, `apps/web/src/lib/nexus/**`, or `@42ch/nexus-contracts`.
- Do not import `apps/web` data hooks, route definitions, app providers, Tauri IPC helpers, localStorage-backed product state, or daemon URL helpers.
- Use studio-local fixture subcomponents for setup and shell chrome. Promote only reusable primitives through P0; do not move whole surface sections into `@42ch/nexus-ui`.
- Use only registered Tailwind token scale steps from the shared preset.
- No raw one-off design values unless P-1 updates root DESIGN pair first.
- `/surfaces` must remain useful in light and dark themes.
- `wire_contracts_changed: false`; no daemon/Tauri/Rust changes.

## Acceptance Hooks

- A reviewer can describe the intended Nexus setup and shell personality from `/surfaces` alone: calm, premium, readable, and local-first.
- Setup and shell fixtures both show clear information hierarchy, visible actions, useful empty/status states, and keyboard/focus affordances.
- Light and dark themes feel intentionally designed rather than mechanically inverted.
- Every notable visual choice either uses registered tokens or feeds a documented token gap back to P-1/root DESIGN review.
- The redesign remains a View fixture: it is visually useful without daemon data and does not create hidden product behavior.
- Implementation leaves a traceable fixture-to-product decision for major sections so P2 can codify the workflow from evidence rather than aspiration.
