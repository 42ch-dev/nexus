## Goal

Extend the V1.79 manuscript reading surface with persisted progress restore/save and annotation creation/listing/editing/deletion UI. Keep the reading surface read-only for the body; all writes go through the new reading-progress and reading-annotation Local API endpoints.

## Scope

### A. Progress persistence

| Capability | Detail |
|---|---|
| `useReadingProgress(workId, chapter)` query | Fetches saved `scroll_progress` on chapter load; default 0. |
| `useSaveReadingProgress()` mutation | Debounced (e.g., 500 ms) save on scroll; also save on `beforeunload` / `visibilitychange`. |
| "Progress saved" affordance | Optional subtle toast on successful save, using the existing toast component. No new DESIGN.md token required (see §D). |

### B. Highlight / annotation UI

| Capability | Detail |
|---|----|
| Text selection handler in `ReadingProse` | On selection, show a floating toolbar with "Highlight" action (primary author-visible creation flow). |
| `useCreateAnnotation()` mutation | POST highlight with `start_offset`, `end_offset`, default color, empty note. |
| Highlight overlay | Render saved highlights as absolutely-positioned spans or inline marks over the prose. Must degrade gracefully if body text changes. |
| Annotation inspector | Side panel listing annotations for the current chapter; shows color swatch, note snippet, and created time. Author can see all highlights for the chapter without re-scanning prose. |
| Edit/delete | Inline note edit + color picker (semantic palette from DESIGN.md); delete with confirmation. Inspector actions and overlay update together. |
| Drift notice | If `end_offset` exceeds current body length, show a clear, non-blocking notice ("标注可能因正文编辑而偏移" / "This highlight may have shifted after body edits") instead of mis-rendering or silently dropping. The notice must not block reading or other highlights. |

### D. DESIGN.md token fill

| Token group | Tokens | Notes |
|---|---|---|
| Highlight backgrounds | `reading-annotation-highlight-yellow`, `reading-annotation-highlight-blue`, `reading-annotation-highlight-green`, `reading-annotation-highlight-pink` | Concrete light + dark values. Each maps to one of the four semantic colors in the `color` schema enum. Follow existing badge-mapping pattern (low-opacity background + matching text color for the contrast swatch). |
| Annotation inspector | `reading-annotation-inspector-width` (e.g., `320px`), `reading-annotation-inspector-elevation` (use `shadow-popover`), composition via existing card + button primitives | Reuse existing primitives where possible; new tokens only for reading-specific layout values. |
| Selection toolbar | `reading-selection-toolbar-bg`, `reading-selection-toolbar-border`, `reading-selection-toolbar-shadow` | Floating toolbar shown on text selection; follows existing popover/context-menu pattern. |

**Note**: the existing `reading-progress-indicator` token (with `track`, `fill`, `label` sub-tokens) already covers the scroll-progress bar. The "progress saved" affordance in §A is a transient toast using the existing toast component — no new DESIGN.md token is needed for it.

## Acceptance (DoD)

1. Reading surface restores and saves scroll progress across reloads.
2. Text selection creates highlights; highlights render on load; annotation inspector lists, edits, and deletes them.
3. Drift notice appears when annotation offsets exceed current body length.
4. No new write route for body/outline from reading UI.
5. `pnpm --filter web run typecheck/test` passes; `pnpm --filter @42ch/nexus-contracts run build` passes.
6. Component/module sizes follow repo discipline (≤250 lines where feasible; large components split).
7. DESIGN.md reading-depth tokens filled with concrete light + dark values (highlight backgrounds × 4, annotation inspector width/elevation, selection toolbar). Existing `reading-progress-indicator` token is sufficient for the progress bar; no new progress tokens needed.
