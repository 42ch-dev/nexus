## Specify

### Problem

6 real bugs in the V1.94 setup wizard block first-launch usage of the desktop app.

### Root causes (from investigation)

1. **ClientProvider `!loaded` branch**: Creates temporary `BrowserClient()` (same-origin) for ALL builds, including desktop. In Tauri webview, same-origin = `http://tauri.localhost/` → fetch to `/v1/daemon/runtime/health` hits the Tauri static-file server, not the daemon. The webview's fetch rejects with "The string did not match the expected pattern."
2. **Daemon startup failure**: `SidecarManager` starts the sidecar binary but the daemon crashes with `migration 202606070001 was previously applied but has been modified` (SQLite checksum mismatch on the user's old DB). The wizard shows a generic error without the real cause.
3. **CSS layout**: `setup-wizard-step-*` tokens may have naming mismatches between `index.css` variables and Tailwind utility generation → missing padding/max-width → broken layout.
4. **Workspace path**: Stale `~/.nexus42/config.toml` has `workspace_path = ".../nexus/local/default"` from a pre-V1.94 version.
5. **No directory picker**: Step 1 only displays the path; user cannot override.
6. **Layout**: Steps should be vertical on the left, not horizontal on top.

#### T3: Daemon error surfacing (Bug #2)

**Files**: `apps/web/src/pages/setup-step-daemon.tsx`

The wizard step 2 already subscribes to `desktop.onDaemonStatusChanged()` and shows `status.detail`. The issue is two-fold:
1. **Client-side**: The `client.health()` HTTP probe competes with the sidecar lifecycle and produces confusing errors when the daemon is not yet ready.
2. **Sidecar-side** (compass §2.2 stderr gap): The SidecarManager's `_rx` receiver from `command.spawn()` is discarded — the daemon's stderr (which contains the real crash reason, e.g., migration mismatch) is never captured. `DaemonStatus.detail` only contains generic SidecarManager messages ("Daemon did not start" / "port conflict").

Fix:
- When `desktop` is available, DON'T call `client.health()` (the HTTP probe competes with the sidecar lifecycle). Instead, **rely solely on `onDaemonStatusChanged`** for desktop builds.
- Only use the HTTP probe for browser builds (which have no sidecar).
- When the daemon fails, show `status.detail` verbatim from the SidecarManager. Note: this will show a generic error (not the SQLite migration detail) due to the stderr gap. The T4 reset button provides the recovery path regardless.
- Add a "Retry" button that calls `desktop.startDaemon()`.
- **Future enhancement (out of V1.95 scope)**: capture sidecar stderr by reading the `_rx` command-event receiver in `sidecar.rs` and appending it to `DaemonStatus.detail`.

#### T4: Migration-mismatch recovery (Bug #2 companion)

**Files**: `apps/desktop/src-tauri/src/lib.rs` (new Tauri command) + `apps/web/src/pages/setup-step-daemon.tsx`

Add a new Tauri command `reset_local_database()` that:
- Resolves the SQLite DB path via `nexus_home_layout::workspace_state_db_path()` (ADR-014 layout: `~/.nexus42/creators/<id>/workspaces/<slug>/state.db`). If `config.toml` has no `active_creator_id` (setup-wizard scenario), fall back to a glob over `~/.nexus42/creators/*/workspaces/*/state.db` to find all candidate DBs.
- Deletes the found `state.db` (and `-wal`, `-shm` files).
- Returns `Ok(())` on success.
- The wizard step 2 shows a **"Reset local database"** button **when the daemon is in Error state** (the SidecarManager's `detail` field carries a generic "Daemon did not start" message — the real daemon stderr is NOT captured; see compass §2.2 SidecarManager stderr gap). Button label and helper copy must clearly state: "This will clear the daemon's local state database (config, registry cache). Your creative files in the workspace are not affected."
- On click → call `reset_local_database()` → then `desktop.startDaemon()`.
- The button is **opt-in**; never auto-triggered.

Pre-release allows DB wipe per AGENTS.md.

**Important**: The DB already lives under `~/.nexus42/` (ADR-014: `nexus_home_layout::workspace_state_db_path()` → `~/.nexus42/creators/<id>/workspaces/<slug>/state.db`). The compass claim that the DB might be at the workspace path has been **verified false** by architecture review — the daemon runtime resolves the DB path through `crate::config::resolve_state_db_path()` which delegates to `nexus_home_layout::workspace_state_db_path()`. No DB-path move is needed. The `reset_local_database()` command must use the SAME resolution path to find the correct file.

#### T9: Workspace vs system-home separation (VERIFY only — no fix needed)

**Files**: `crates/nexus-daemon-runtime/src/config.rs` + `apps/nexus42/src/config.rs` + `crates/nexus-home-layout/src/lib.rs`

Verify and document (no code change needed — architecture review confirms this is already correct):
- `~/.nexus42/` = system home (config.toml, state.db under ADR-014 layout, registry/, tls/, agent-host/).
- `~/Documents/nexus/default/` = user workspace (Works/, Stories/, Outlines/, References/).
- The SQLite DB is resolved by `nexus_home_layout::workspace_state_db_path()` → `~/.nexus42/creators/<id>/workspaces/<slug>/state.db`. This is verified correct.
- The `WorkspaceState::initialize()` at `workspace/mod.rs:166` uses `crate::config::resolve_state_db_path()` which delegates to `nexus_home_layout::workspace_state_db_path()`.
- Migration files are embedded in the binary (`sqlx::migrate!()`); they don't live in either directory.

**Architecture note**: `crate::config::resolve_state_db_path()` requires `active_creator_id` in `config.toml`. During setup wizard (no creator yet), this returns an error. The `WorkspaceState::initialize()` uses `?` on this, which would crash the daemon. However, setup wizard runs before the daemon is fully started (SidecarManager only spawns the sidecar), so this error path is exercised only when the daemon attempts to boot with a corrupted/missing config — which is exactly the scenario T4's reset solves (wipe the DB, let the daemon recreate it with fresh schema + config).

**Add test assertion**: the resolved DB path (`nexus_home_layout::workspace_state_db_path()`) contains `.nexus42` and does NOT contain `Documents/nexus` or any workspace slug as a parent.
