> Create the cross-application Nexus brand design contract and map it into the existing Web design token layer.

## 1. Problem Statement

`apps/web/DESIGN.md` is currently the Web UI token SSOT, but V1.83 introduces a shared `@42ch/nexus-ui` package and future cross-surface consumption. The project needs a root-level brand contract that can govern shared visual identity while preserving app-specific component tokens already consumed by `apps/web`.

The product goal is an author-facing brand system, not only a token inventory. The contract should make Nexus feel calm, legible, and creation-oriented across light and dark modes while leaving current feature workflows intact.

## 2. Scope

### 2.1 Root Brand DESIGN Files

- Create root `DESIGN.md` and `DESIGN.dark.md` with YAML frontmatter as machine-readable SSOT.
- Treat root DESIGN files as the normative brand contract for shared token names, token values, logo rules, accessibility intent, and voice. Package token exports and app-specific design files must derive from these names rather than inventing parallel brand values.
- Encode the supplied VI palette:
  - brand deep blue `#1E3A5F`
  - brand cyan `#25D1E0`
  - white `#FFFFFF`
  - supporting blues and neutrals refined for contrast
- Define typography, spacing, radius, elevation, motion, focus, logo usage, and voice/content rules at Standard or Production level.
- Document the intended author experience: trustworthy workspace, low-distraction creative focus, and clear action hierarchy.

### 2.2 Web Mapping

- Update `apps/web/DESIGN.md` and `apps/web/DESIGN.dark.md` so Web tokens derive from the root brand layer while retaining app-specific component sections.
- Preserve existing token names when possible to reduce implementation churn.
- Add explicit mapping notes for Tailwind theme keys and CSS custom properties.
- Define Web files as consumption mappings, not independent brand sources. Web-specific aliases are allowed for existing Tailwind/CSS/shadcn-style consumers, but each alias should point back to a root token or explain why it is app-only.
- Preserve canvas, SOUL, findings, memory, and workflow component-token sections unless a token is directly superseded by the root brand layer.

### 2.3 Accessibility and Contrast

- Validate key color pairings:
  - deep blue on white
  - white on deep blue
  - cyan on deep blue
  - dark-mode text/background combinations
  - focus ring and interactive states
- Adjust raw VI suggestions where needed to meet WCAG 2.1 AA for the intended usage.

### 2.4 Package Contract

- Define how `@42ch/nexus-ui` exposes design tokens, theme/CSS entry points, and logo assets from the root DESIGN contract.
- Mention future `nexus-platform` consumption only as an export-stability and naming constraint; do not define private platform implementation steps.
- State that React component exports are future scope.
- Token-source hierarchy for this iteration:
  1. Root `DESIGN.md` / `DESIGN.dark.md` define canonical brand token names and values.
  2. `packages/nexus-ui` exposes package-consumable representations of those brand tokens and assets.
  3. `apps/web/DESIGN*.md` maps canonical tokens into Web CSS variables, Tailwind keys, and component tokens.
  4. `apps/web` implementation consumes the mapping; it should not introduce raw brand colors outside documented exceptions.
- After P1 locks token names and mapping notes, P2 should treat them as implementation inputs. Any later token rename or package-exposure change must be routed back through P1/P0 before Web implementation continues.

## 4. Acceptance / DoD

- Root `DESIGN.md` and `DESIGN.dark.md` exist with structured YAML frontmatter.
- Web DESIGN files remain valid and cover existing component-token consumers.
- Root DESIGN files clearly state they are the brand SSOT; Web DESIGN files clearly state they are consumption mappings and list root-token references or app-only exceptions.
- Brand colors are optimized for real UI contrast, not copied blindly from the VI brief.
- Package exposure notes align with P0 exports and do not require React component extraction.
- P2 can consume the token contract without inventing local values or renaming root tokens during implementation.
- Product guidance explains where the brand should be visible in V1.83: shell identity, navigation confidence, focus states, and base primitives, not full-page redesign.

## 5. Non-Goals

- Replacing all `apps/web` component tokens with only root tokens.
- Treating `apps/web/DESIGN*.md` as deprecated; they remain the Web implementation mapping layer.
- Designing every product page layout.
- Implementing private `nexus-platform` token consumption.
- Changing API or data behavior.

## 6. Validation

- Manual YAML/frontmatter review against `mstar-design-md` requirements.
- Token hierarchy review: root tokens, package exposure notes, and Web mapping references agree on names and responsibilities.
- Contrast checks for primary UI states: text/background, button foreground/background, logo variant/background, focus rings, hover/active states, disabled states, and dark-mode navigation.
- Check for undocumented raw VI color use in Web mapping notes; any exception must be justified as app-only or transitional.
- P2 implementation verifies Tailwind/CSS variable consumption.

## 7. Risks

- Keeping root and Web DESIGN files in sync can drift; this plan must make ownership and mapping explicit.
- Cyan `#25D1E0` may be too low-contrast for text on white and should primarily be used for accents, icons, and active states unless adjusted.
- If P1 changes token names after P2 starts, Web implementation churn increases; P1 should lock names before P2 edits Tailwind/CSS.
- Root token values that are too product-generic will weaken future platform compatibility; keep names semantic enough for multiple consumers but grounded in current Nexus brand usage.
