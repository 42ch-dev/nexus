# P1 — Native agent provider registration in daemon HostManager

> **Iteration compass:** `.mstar/iterations/v1.127/delivery-compass.md`
> **Spec:** `.mstar/iterations/v1.127/specs/native-agent-provider-registration.md`
> **SSOT status:** `.mstar/status.json`

**Goal:** Wire `CodexNativeProvider` and `ClaudeCliProvider` into the daemon's `HostManager` via `register_provider(...)` so that `create_session()` reaches the provider instead of failing with "provider not registered". This closes the `AgentHostSubsystem` "providers already registered" invariant gap (agent_host.rs:44-45) and resolves `R-V1116P0QA-001` (11-iteration roll-forward). **Note (qc1 C-001):** agent *discovery* in the AgentPicker was already working via `POST /v1/daemon/agent-host/scan` (independent PATH scan at agent_host.rs:577 — does NOT consult `HostManager`); the V1.127 fix is the **session-create prerequisite** (registration), not a discovery fix.

**Architecture:** Single edit point: `crates/nexus-daemon-runtime/src/boot.rs` constructs `HostManager::new()` (empty) at line 721 and never calls `register_provider`. Both providers already exist (`crates/nexus-agent-host/src/providers/native_cli/codex.rs:81` — `CodexNativeProvider`, `claude.rs:118` — `ClaudeCliProvider`) and are already path-scanned (`path_scan.rs::KNOWN_COMMANDS`). The fix: after `HostManager::new()`, call `manager.register_provider(Arc::new(CodexNativeProvider::default_config()))` and the same for `ClaudeCliProvider`. The existing `AgentHostSubsystem` docstring already states "with providers already registered" (agent_host.rs:44-45) — this fix finally meets the invariant. Plus end-to-end verification (path scan → register → list → session create).

## Review Gate Summary

**Plan QC:** tri-review (qc1 REQUEST_CHANGES → qc1 fix wave → re-review; qc2 APPROVE; qc3 APPROVE).

**qc1 W-001 — `HostManager::start()` marks providers available without CLI probe (document-only, intentional):**

`manager.rs:215-222` marks all registered providers `available: true` during `start()` without calling `ProviderAdapter::probe()`. This is intentional for two reasons:

1. **Separate health-check lifecycle exists.** The `/agent-host/scan` endpoint (agent_host.rs:577) performs its own PATH scan via `scan_path_in(...)` and reports accurate `available` status based on whether the CLI binary is actually found. The AgentPicker uses `/scan`, not `/providers` — so the `available` flag in `HostManager` is not the source of truth for UI discovery.
2. **`launch()` is lazy.** `CodexNativeProvider::launch()` (codex.rs:585-619) registers session state only — no process spawn. The actual CLI invocation happens in `execute()`. So marking a provider "available" without probing does not cause a `create_session()` failure; the failure (if any) would surface at `execute()` time with a clear process-spawn error.

Adding boot-time probes would add latency to daemon startup for a cosmetic improvement to the `/providers` endpoint's `available` field — a field that the primary UI flow (`/scan`) does not consume. **Closed as V1.128+ nit residual** if the `/providers` endpoint's `available` accuracy becomes important (e.g. if a future UI surface switches from `/scan` to `/providers` for agent discovery).

**qc1 W-002 — Path-scan test PATH isolation (fixed):** test now uses `PathGuard::isolate(temp_dir)` + `SCAN_PATH_LOCK` so it genuinely depends on the stubs, not on any real `codex`/`claude` that might be on the host PATH.

**qc1/qc3 S-001 — Defensive-wrapping trade-off (documented inline):** boot.rs registration block now has an inline comment explaining why straight-line registration (no `match`/`if let Ok(...)`) is safe — `default_config()` is a pure constructor that does not panic.
