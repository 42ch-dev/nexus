## Specify

### Problem

The desktop app's first-launch flow currently has no daemon-side support for:
(1) detecting locally-installed ACP agents; (2) defaulting the workspace to a
user-visible Documents path; (3) tracking that the user has completed setup;
(4) gating main-UI entry on a healthy daemon probe at every launch (not only
first launch).

### User value

The setup wizard (P1 frontend) has real daemon-backed behaviour to call
against: a scan endpoint that returns "here are the ACP agents I found on
your PATH", a workspace bootstrap that doesn't dump creative work into a
hidden `~/.nexus42/` directory, and a launch gate that prevents the "I'm in
the main UI but the daemon hasn't started" experience the author reported.

## Clarify

**Closed decisions** (inherited from compass + P-1):

- PATH scan probes registry-known binary names only; no user-supplied
  commands during scan. Bounded concurrency; ≤2s `--version` timeout.
- Workspace default applies **only when `workspace_path` is unset**. No
  forced migration.
- `setup_completed` defaults to absent (= false). Missing marker =
  first-launch semantics (fail-safe to wizard).
- Per-launch daemon-ready gate inherits the existing `HEALTH_START_TIMEOUT`
  (15s); on boot failure, the SPA lands in a setup-wizard-like error step
  (P1 owns the visual; P0 owns the gate state plumbing).

**Open assumptions** (to validate at implement):

- The agent-host router wiring is straightforward; the architect's P-1
  spec **has named the exact route** (`POST /v1/daemon/agent-host/scan` in
  `crates/nexus-daemon-runtime/src/api/handlers/agent_host.rs` — new `scan`
  handler, same router group as existing `health`, `sessions`, etc.). The
  schemas are frozen at `schemas/daemon-api/agent-host/scan-request.schema.json`,
  `scan-response.schema.json`, and `agent-scan-entry.schema.json`.
- `dirs` crate version in the workspace supports `document_dir()` on
  macOS/Linux/Windows. If not, P0 falls back to `home_dir().join("Documents")`
  on Unix and the Windows known-folder API. Documented in
  `desktop-shell.md` §13.5.

## Plan

### Target state

A P1 frontend dev can build the setup wizard entirely against the frozen
contract + the daemon-backed behaviour P0 ships. No P1 work should
require backend clarification after P0 merges.

### Module boundaries / interface contracts

- `POST /v1/daemon/agent-host/scan` — handler at `crates/nexus-daemon-runtime/src/api/handlers/agent_host.rs::scan`; wired into the existing agent-host router (same route group as `health`, `sessions`, etc.). Contract shapes frozen by P-1 in `schemas/daemon-api/agent-host/scan-request.schema.json`, `scan-response.schema.json`, and `agent-scan-entry.schema.json`. The path is `/v1/daemon/agent-host/scan` — no `/v1/local/` prefix (V1.90 Daemon API rename).
- `~/.nexus42/config.toml` additive `setup_completed: bool` — the `CliConfig` struct in `apps/nexus42/src/config.rs` gains `setup_completed: Option<bool>` with `#[serde(default)]`. TOML deserialiser tolerates unknown fields naturally (serde `deny_unknown_fields` is not set on `CliConfig`). Missing field = `None` = first-launch semantics. The Tauri shell's `resolve_workspace_root()` reads the same config file; the TOML parser there defines a local `ConfigFile` struct with `#[derive(serde::Deserialize)]` fields — it already ignores unknown fields (no `deny_unknown_fields`), so `setup_completed` is additive and non-breaking.
- Workspace default resolver shared by `apps/nexus42/src/config.rs` (CLI/daemon) and `apps/desktop/src-tauri/src/lib.rs` (Tauri shell) — both use `dirs::document_dir().join("nexus42").join("default")` when `workspace_path` is unset. Fallback: `dirs::home_dir().join("Documents").join("nexus42").join("default")` if `document_dir()` returns `None`. Both sides must agree (codified in `desktop-shell.md` §13.5).
- Tauri commands: `get_setup_completed`, `set_setup_completed` (P0 owns these — new Tauri commands in `apps/desktop/src-tauri/src/lib.rs`). The daemon-ready signal reuses the existing `SidecarManager` health-probe loop + `onDaemonStatusChanged` Tauri event — no new `is_daemon_ready` command needed; the SPA consumes the existing event. P1 only needs the `state: "running"` event as the gate signal.
- `scan_local_installations` helper lives in `crates/nexus-acp-host/src/registry.rs` alongside the existing `RegistryClient` (does not replace it). Returns `Vec<LocalInstallation { binary: String, version: Option<String> }>`.

### Risks / rollback

- PATH scan execution boundary (security): qc2 reviews. Mitigation:
  registry-known names only; no shell-expansion; bounded concurrency.
- `dirs::document_dir()` returning `None` on some platforms: P0 falls
  back to `home_dir().join("Documents")` and logs a warning.
- Health-probe gate deadlocks if the daemon fails to boot: existing
  `HEALTH_START_TIMEOUT` + error state machine handles this; the SPA
  surfaces the error (P1 visual).
- Tauri command `is_daemon_ready` vs the existing event path: P0 picks
  one to avoid duplication.
