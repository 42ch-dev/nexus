## Specify

### Problem

The current `apps/web` first-launch + main-UI experience is the source of
all five author-reported defects:

1. `App.tsx` does `Navigate to="/works"` unconditionally — there's no
   setup flow, no daemon-ready gate, no first-launch detection.
2. `daemon-status-bar.tsx` shows a 5-state pill + an always-enabled
   Start button; the default fallback state is `starting`, which the
   author perceived as "stuck".
3. `button.tsx` dark primary uses `dark:bg-brand-cyan dark:text-brand-deep-blue`
   — saturated background with dark text. The invariant "dark bg → light
   text" is not recorded anywhere.
4. `sidebar.tsx` ships a flat 10-item `NAV_ITEMS` array; no tabs, no
   nesting, no footer.
5. `/presets` and `/strategy` are separate top-level routes for what the
   author reads as one concept (Preset = the YAML; Strategy = the same
   preset's canvas visualisation).

### User value

The desktop app's first launch "just works": wizard walks the author
through workspace + daemon + agent, lands them in a two-tab sidebar with
a footer profile switcher, and never shows a "Daemon starting…" hang in
the main UI. Buttons read correctly in both themes.

## Clarify

**Closed decisions** (inherited from compass + P-1):

- Setup wizard is 4 steps (welcome+workspace → daemon-ready → agent →
  done).
- Daemon status bar is restart-icon-only when running; banner on
  degraded/error.
- Two-tab sidebar (Creator | Orchestrator) — not sectioned single column.
- Strategies unifies Presets + Strategy at `/strategies`.
- Connect leaves the sidebar for Settings.
- Footer profiles is a Slack/Chrome-style avatar switcher.
- Button contrast is a token fix + audit + DESIGN.md invariant.

**Open assumptions** (to validate at implement):

- The exact desktop shell signal for "daemon ready" is either a Tauri
  command (`is_daemon_ready`) or the existing `onDaemonStatusChanged`
  event — P0 picks; P1 consumes whichever is exposed. The signal must
  become true **only after the first successful health probe**.
- The `useCreators()` query shape (cursor pagination) is sufficient for
  a footer avatar list at typical scales (1–10 creators). Pagination
  UI is out of scope.
- The browser build (no Tauri) defaults `setup_completed` to `true`
  (i.e. browser users skip the wizard — they're already power users
  running their own daemon). The wizard and per-launch gate are
  **desktop-first**; browser must not regress (instant pass or no-op
  for the gate; no Tauri command calls assumed).
- Single-Creator case in footer: exactly one avatar + "+" is the only
  visible CTA; clicking the single avatar is a no-op (no error toast).

## Plan

### Target state

A first-time desktop user walks the wizard, lands in a two-tab sidebar
with footer profiles, sees a restart-icon-only status bar, and never
hits the "stuck starting" state. Buttons read correctly in both themes.

### Module boundaries / interface contracts

- Wizard consumes:
  - `POST /v1/daemon/agent-host/scan` (P0, route path frozen by P-1 schemas: `schemas/daemon-api/agent-host/scan-request.schema.json` + `scan-response.schema.json` + `agent-scan-entry.schema.json`). Response shape: `AgentScanEntry[]` with `name`, `registry_agent_id`, `launch_command`, `installed`, `version`, `description`, `icon_url`.
  - `set_setup_completed` (P0 Tauri command `set_setup_completed(value: bool)`) — writes `setup_completed: bool` to `~/.nexus42/config.toml`.
  - Workspace bootstrap: P0 owns the resolver; P1 reads the resolved workspace path via existing `get_workspace_root` Tauri command (or the daemon config endpoint).
  - Per-launch daemon-ready gate: P1 subscribes to the existing `onDaemonStatusChanged` Tauri event (`DaemonState::Running` = gate passed). No new Tauri command needed — P0's `SidecarManager` already emits this event. P1's daemon-ready splash polls/awaits `state: "running"`.
- Wizard step 3 UX contract: see compass §5 + `web-ui.md` §29.4 + `desktop-shell.md` §14. The scan endpoint's `AgentScanEntry[]` shape is the SSOT; P1 must render it per the UX states enumerated in §5 (scanning transient, installed badge, "Recommended" badge, "No agents found" with custom `launch_command` input, selectable cards).
- Sidebar consumes the redesigned `NAV_ITEMS` (this plan) with two-tab grouping per compass §1 E1 — no P0 dependency.
- Footer profile switcher consumes `useCreators()` query (existing `GET /v1/daemon/creators` endpoint) + new `useActiveCreatorId` client-context hook (no P0 change).
- Daemon status bar consumes `onDaemonStatusChanged` event (unchanged P0 contract — `SidecarManager` already emits `DaemonStatus { state, version, port, detail }`).
- Strategies list consumes existing `GET /v1/daemon/presets` endpoint; canvas detail consumes existing strategy endpoints. Route reshape only — no P0 change.
- Button contrast: consumes DESIGN.md tokens amended in P-1 — no P0 dependency.

### Risks / rollback

- Setup wizard scope creep (sliding into agent-client CRUD UI):
  mitigation — this plan ships the 4-step wizard only; CRUD is
  explicitly Non-Goal.
- Sidebar IA rewrite breaking existing keyboard nav: mitigation —
  vitest a11y tests cover the tab switch + nested nav keyboard path.
- Strategies route collapse regressing V1.70–V1.75 deep links:
  mitigation — redirect aliases for `/presets` and `/strategy`.
- Button contrast audit missing call sites: mitigation — the
  DESIGN.md invariant names the rule; qc1 reviews the sweep.
