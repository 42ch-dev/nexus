### Plan (locked outputs of P-1)
- [x] **T1 — TLS design locked (architect decision, binding on P0)**:

  **Choice**: `axum-server` + `rustls` (not manual `tokio-rustls` + `hyper-util` connection loop).

  **Rationale grounded in `boot.rs` §10**: The existing `axum::serve(listener, app)` at `boot.rs:819` accepts any `tokio::Listener` implementor. `axum-server 0.7` provides `RustlsConfig::from_pem(...)` + `bind_rustls(addr, config)` which returns a TLS listener. The rest of the serve block — `.with_graceful_shutdown(...)` — is completely unchanged. A manual `tokio-rustls` wrap of accepted `TcpStream`s fed through `hyper::server::conn::http1::Builder` + `TowerToHyperService` would duplicate the UnixSocket connection-handling loop (boot.rs §10 lines 847-878), adding ~30 lines of error-prone accept/upgrade/spawn code. `axum-server` keeps the diff at the bind call site to: (a) load cert config before binding, (b) branch — TLS for non-loopback, plain TCP for loopback.

  **Dep crate names + version constraints** (all compatible with axum 0.7 + hyper 1 + tokio 1.35 in workspace):

  | Crate | Version | Role |
  |-------|---------|------|
  | `axum-server` | `"0.7"` | `RustlsConfig::from_pem()` + `bind_rustls()` → drop-in `Listener` for `axum::serve` |
  | `rustls` | `"0.23"` | Transitive via `axum-server`; explicit dep only if tests need `rustls::pki_types::ServerName` |
  | `rcgen` | `"0.13"` | Ed25519 self-signed cert generation; `KeyPair::generate_for(&PKCS_ED25519)` |
  | `rustls-pemfile` | `"2"` | PEM cert/key loading for boot-time reload of persisted certs |

  **Cert storage layout** (via `nexus-home-layout` — new public functions):

  | Function | Returns |
  |----------|---------|
  | `tls_dir(home: &Path)` | `~/.nexus42/tls/` |
  | `tls_cert_path(home: &Path)` | `~/.nexus42/tls/cert.pem` |
  | `tls_key_path(home: &Path)` | `~/.nexus42/tls/key.pem` |

  Permissions: daemon creates `~/.nexus42/tls/` with `std::fs::DirBuilder` mode `0o700` on first boot. On cert generation, writes `cert.pem` + `key.pem` with `0o600` (owner-only read). Fingerprint is SHA-256 of the DER-encoded certificate, displayed as colon-hex (lowercase, consistent with SSH `SHA256:...` convention).

  **Cert algorithm**: Ed25519 via `rcgen::KeyPair::generate_for(&rcgen::PKCS_ED25519)`. Rationale: smaller public keys (32 bytes vs 65 for ECDSA P-256), faster signing, no curve negotiation drama for a single self-signed cert, rcgen 0.13 supports `PKCS_ED25519` out of the box.

  **Cert lifecycle**:
  1. **Boot**: check if `~/.nexus42/tls/cert.pem` + `key.pem` exist → load via `rustls-pemfile` → `RustlsConfig`. If not → generate via `rcgen` → persist → load.
  2. **Regeneration**: explicit user action only (delete `~/.nexus42/tls/` dir → next boot regenerates). No automatic rotation, no expiry check (self-signed local trust anchor; expiry is informational).
  3. **Startup log**: `tracing::info!("TLS certificate fingerprint: SHA256:aa:bb:cc:...")`.

  **P0 implementation outline** (included here so P0 implementer has zero ambiguity):
  1. Add `ensure_tls_config(home: &Path, host: &str) -> Option<RustlsConfig>` to `boot.rs` — returns `Some` for non-loopback hosts, `None` for loopback.
  2. Amend `ensure_remote_bind_allowed(host, tls_config)` to fail if non-loopback but no TLS config loaded (additional fail-closed check).
  3. In `Transport::Http` arm at §10: if `tls_config.is_some()` → `axum_server::bind_rustls(addr, tls_config.unwrap())`; else → `tokio::net::TcpListener::bind(&addr)` as today.
- [x] **T2 — Fingerprint endpoint contract locked** (`@architect`; this is the **P0↔P1 seam** — P0 implements the endpoint, P1 calls it):

  **Endpoint**:
  - Path: `GET /v1/daemon/runtime/cert-fingerprint`
  - Placement in router: `runtime_routes` in `api/mod.rs` — same unguarded route group as `/v1/daemon/runtime/health` and `/v1/daemon/runtime/status`. **No auth required** (fingerprint is a public trust anchor, like an SSH host key — it is what clients pin, not a secret).
  - HTTP method: `GET` only (read-only, no mutation, no side effects).

  **Response schema** (JSON Schema file: `schemas/daemon-api/runtime/cert-fingerprint-response.schema.json` — new file, additive):

  ```jsonc
  // schemas/daemon-api/runtime/cert-fingerprint-response.schema.json
  {
    "$schema": "http://json-schema.org/draft-07/schema#",
    "$id": "https://nexus42.invalid/schemas/daemon-api/runtime/cert-fingerprint-response.schema.json",
    "schema_version": 1,
    "title": "Nexus CertFingerprintResponse",
    "description": "Response for GET /v1/daemon/runtime/cert-fingerprint. Returns the SHA-256 fingerprint of the daemon's TLS certificate for TOFU pinning. No authentication required.",
    "type": "object",
    "required": ["fingerprint", "algorithm"],
    "properties": {
      "fingerprint": {
        "type": "string",
        "description": "SHA-256 fingerprint of the DER-encoded TLS certificate, colon-hex format (lowercase). Example: 'SHA256:aa:bb:cc:dd:ee:ff:...'"
      },
      "algorithm": {
        "type": "string",
        "enum": ["sha256"],
        "description": "Hash algorithm used for the fingerprint. Always 'sha256' for the initial implementation."
      },
      "created_at": {
        "type": "string",
        "format": "date-time",
        "description": "ISO 8601 timestamp of when the TLS certificate was generated/booted. Optional — present when cert exists."
      }
    },
    "additionalProperties": false
  }
  ```

  **Fields rationale**:
  - `fingerprint` (required): the colon-hex SHA-256 of the DER cert — the value clients pin. Always present when the daemon has a cert.
  - `algorithm` (required): always `"sha256"` — a stable enum so clients can detect algorithm upgrades in future iterations before parsing the fingerprint value.
  - `created_at` (optional): ISO 8601 timestamp — present only when the cert exists. Omitted when daemon has no TLS cert (loopback-only mode), in which case the endpoint still returns 200 with no `created_at` field. This allows the setup screen to distinguish "remote daemon has no cert" from "endpoint unreachable" before attempting a TLS connection.

  **Behaviour when no cert exists (loopback-only daemon)**: The endpoint returns HTTP 200 with `{ "fingerprint": "", "algorithm": "sha256" }` (no `created_at`). The setup screen treats an empty `fingerprint` as "this daemon is not configured for TLS — it must be local loopback". This avoids a confusing 404/500 for what is a valid daemon state.

  **npm version impact**: `@42ch/nexus-contracts 0.19.1 → 0.20.0` (additive schema, new DTO, no breaking renames). Pre-1.0 convention: bump MINOR for additive wire contracts. Note: `schema_version` field in the new schema stays `1` (consistent with all current V1 schemas); `LATEST_SCHEMA_VERSION` in codegen is unchanged. `wire_contracts_changed: true`.

  **P0 handler implementation note**: The handler reads the fingerprint from a shared `Arc<Option<TlsFingerprint>>` injected into `WorkspaceState` at boot (no filesystem I/O per request). The fingerprint string is computed once at cert generation/boot and cached.

  **§15 Transport Security (TLS)** — subsections:

  1. **15.1 TLS listener** — normative: daemon auto-generates Ed25519 self-signed cert via rcgen; persists under `~/.nexus42/tls/`; TLS listener via `axum-server` + `rustls` for non-loopback binds; loopback stays plain HTTP. Cert lifecycle (generation on first boot, reuse across restarts, explicit regeneration only). Deps: `axum-server 0.7`, `rustls 0.23`, `rcgen 0.13`, `rustls-pemfile 2`.

  2. **15.2 Remote-bind gate with TLS** — amendment to §14.2: non-loopback bind now requires **three** conditions (adds TLS cert presence to the existing key + flag conditions). Fail-closed: if remote bind is requested but no TLS cert can be loaded/generated, daemon refuses to start with a clear error. Verbatim error message spec for the boot log.

  3. **15.3 Certificate fingerprint** — normative: fingerprint is SHA-256 of DER-encoded cert, colon-hex format. Fingerprint is a **public trust anchor** (like an SSH host key), not a secret. Logged at startup; served by the unauthenticated `GET /v1/daemon/runtime/cert-fingerprint` endpoint (see §15.4). No auth required — the endpoint is in the same unguarded runtime route group as `/v1/daemon/runtime/health`.

  4. **15.4 Fingerprint endpoint** — normative: path, HTTP method, response schema (cross-reference to `schemas/daemon-api/runtime/cert-fingerprint-response.schema.json`).   **§16 Remote Client Connection Model** — subsections:

  1. **16.1 Client transport parameterisation** — `BrowserClient` / `TauriClient` accept base URL + optional `X-API-Key` header. Local same-origin mode is the backwards-compatible default. The connection config shape (`{ endpointUrl, apiKey, pinnedFingerprint?, label? }`) is stored client-side only — it is NOT a wire contract.

  2. **16.2 TOFU trust model** — normative: on first connection to a remote endpoint, the client fetches the fingerprint (no auth), displays it for explicit user confirmation ("Trust this certificate and connect"), and pins it per-endpoint in client storage. On subsequent connects, the client compares the pinned vs served fingerprint. If they differ → **blocking re-pin warning** (no automatic acceptance, no silent fallback). The user must explicitly choose "Trust the new certificate" or "Cancel". This is the highest-stakes security UX moment; the spec codifies the exact flow so implementers do not soften it into auto-accept.

  3. **16.3 CSRF defence by header-key (normative non-goal)** — **normative rationale**: the remote connection model authenticates via a custom `X-API-Key` request header. Cross-origin JavaScript cannot set a custom header without triggering a CORS preflight, which the §13.1 Origin allowlist already gates. A separate CSRF token framework (double-submit cookie, synchronizer token, SameSite session cookie) is therefore **redundant** — it would add maintenance surface without closing an attack vector that the header-key + Origin allowlist combination already closes. This rationale is codified here so that a future agent or contributor does not "add" a CSRF token framework thinking it is missing. The non-goal is deliberate and traceable to this section; any future proposal to add CSRF tokens should engage with this rationale explicitly (rather than layering tokens on top silently), so reviewers can weigh the added surface against a concrete new threat.

  4. **16.4 Origin-allowlist evolution for remote clients** — the daemon's Origin allowlist (§13.1) already covers: own-origin, Tauri webview origins, Vite dev origin, and `NEXUS_DAEMON_ALLOWED_ORIGINS` escape hatch. When a remote web-app or desktop-app client connects from a non-loopback origin, the connecting client's origin MUST be added to `NEXUS_DAEMON_ALLOWED_ORIGINS` — there is **no magic auto-allowlisting** of remote origins. The daemon does not automatically trust the remote bind address as a browser origin; the author controls the allowlist explicitly. This rule is unambiguous: a remote client that sends an `Origin` header not in the allowlist will receive `403 Forbidden` (consistent with §13.1.2), regardless of whether it holds a valid API key or a pinned TLS fingerprint. The Tauri webview origins (`tauri://localhost`, `http://tauri.localhost`) are already hardcoded; a future remote-desktop-app using Tauri will use those same origins and therefore be automatically allowed. A remote web-app (browser SPA connecting to a remote daemon) needs its serving origin in `NEXUS_DAEMON_ALLOWED_ORIGINS`.

  5. **16.5 Client key storage** — web: `localStorage` (SPA trust boundary equal to the app itself); desktop (Tauri): OS keychain via Tauri secure-store plugin where available, fallback to app-data dir. Documented as a deliberate local-first trade-off; full secret-store hardening is a future concern. The API key is always user-entered, never compiled in.

  6. **16.6 Raw-browser-tab remote navigation** — explicit non-goal (see compass §6). A remote daemon URL typed directly into a browser tab will encounter a self-signed certificate warning. The supported remote-access path is always through the app's "Connect to Daemon" screen with TOFU fingerprint confirmation. Codified here so it is not treated as a bug to be "fixed" by removing TLS or requiring a public CA.

  **UX spec (author-facing, SECURITY-sensitive, non-technical tone)**

  The screen lives under Settings → "Daemon Connection" (or a top-level "Connect to Daemon" entry for discoverability on first remote use). It is a single, focused form — **not** a multi-tab wizard. Goal: make a non-technical author feel they are "pointing the app at the right computer" rather than "configuring TLS".

  **Fields (in visual order, all required except label):**
  - **Endpoint URL** (text, required): placeholder `https://192.168.1.42:8420` or `https://my-nexus-server.local:8420`. Label: "Daemon address". Helper: "The address shown when you start the daemon on the other machine (look for the log line that begins 'Daemon listening on'). Must start with https:// for remote connections."
  - **API Key** (password, required): label "API key". Helper: "The value of NEXUS42_DAEMON_API_KEY on the daemon machine. Keep this private — it is your password to that daemon." Never pre-filled; cleared on "revert to local".
  - **Label (optional)** (text): label "Connection name". Helper: "A short name you will recognise in the header (e.g. 'Home server', 'Laptop'). Defaults to the hostname if left blank."
  - **Certificate fingerprint** (read-only display + actions): when the user tabs out of Endpoint URL (or presses "Fetch fingerprint"), the client fetches `GET /v1/daemon/runtime/cert-fingerprint` (no auth). Three distinguishable outcomes:
    1. **Fingerprint present** (remote daemon over TLS) — non-empty `fingerprint` in the 200 response. Show:
       - A monospace block: "SHA-256 fingerprint: AA:BB:CC:..." (the exact value the daemon logged at startup).
       - Primary action: "Trust this certificate and connect" (enabled only after the fingerprint is shown and the user has read the warning).
       - Secondary: "Cancel / don't trust".
       - Small, calm security note (DESIGN.md "security-note" token): "This fingerprint is how your app makes sure it is talking to the real daemon and not someone pretending to be it. Compare it to the value printed on the daemon machine's screen. If they match, it is safe to trust."
    2. **Endpoint reachable but has no TLS cert** (loopback-only daemon; 200 response with empty `fingerprint: ""` per P-1 T2 semantics) — treat this as an information state, not an error. Show an inline note (DESIGN.md "info-note" token): "This daemon is only accessible locally on its own machine. It does not have a TLS certificate, so you cannot connect to it from here. Use the Nexus app on that machine instead." Primary "Trust and connect" stays disabled; only "Cancel" is offered. Do NOT surface the "we could not retrieve the certificate" copy — the daemon is reachable, it is just not configured for remote access.
    3. **Endpoint unreachable / fingerprint fetch failed** (network error, DNS failure, non-2xx, malformed body) — treat as an error state (see "Error states" below). This is distinct from state (2): the app could not talk to the daemon at all.

  **Flow states (numbered, author-visible):**

  1. **First-use / no prior config** (local default active):
     - Screen header: "Connect to a remote daemon (optional)".
     - Body: "Most authors run everything on one machine. If you have a headless daemon on another computer on your home network, fill this form to use it from here."
     - Form as above.
     - On "Trust and connect": client stores `{endpointUrl, apiKey, pinnedFingerprint, label?}`, switches the active client to the new config, shows a success toast "Connected to <label or host>. All your work is now using that daemon." Header indicator changes from "Local" to the label.

  2. **Subsequent connect to same endpoint** (pinned fingerprint matches):
     - Endpoint + key pre-filled from storage (key masked).
     - Fingerprint shown as "Previously trusted fingerprint (matches)". Button label becomes "Reconnect with these settings".
     - No scary re-confirmation; just "Connect".

  3. **Fingerprint changed on a pinned endpoint** (highest-stakes moment — explicit blocking warning):
     - Form shows the new served fingerprint.
     - A prominent but calm warning box (DESIGN.md "warning" surface, not red "danger"):
       - Title: "The certificate for this daemon has changed."
       - Body: "This can happen if the daemon was reinstalled or its certificate was deliberately rotated. It can also mean someone is intercepting your connection."
       - Two clear actions:
         - Primary (danger-tone but not panic): "Trust the new certificate and continue" (requires explicit click; records new pinned value).
         - Secondary: "Cancel and keep using the old certificate (safer if you did not expect this change)".
     - Nothing proceeds until the author chooses. The client does **not** auto-accept the new fingerprint.

  4. **"Revert to local" / disconnect**:
     - Always-visible secondary action (even when remote is active): "Use local daemon instead".
     - On click: clear the remote config (or mark it inactive), restore the default same-origin BrowserClient/TauriClient, show toast "Reverted to local daemon. Remote settings are still saved if you want to switch back later."
     - Remote config is **not** deleted on revert — only de-activated. A future multi-endpoint manager can surface the saved list.

  **Copy tone principles (locked for this security-sensitive surface):**
  - Never use "TLS", "certificate authority", "pinning", "TOFU", or "fingerprint" without an immediate plain-English gloss.
  - Treat the author as a careful non-technical person, not a sysadmin. The mental model is "this is the secret handshake between my two computers".
  - "Trust this certificate" is always paired with "compare the number on the other screen".
  - Warnings are informative and actionable, never alarming or condescending.
  - Every field has a one-sentence helper that answers "why do I need to know this?"

  **Error states (author-visible):**
  - Endpoint unreachable or not https: "Could not reach that address. Make sure the daemon is running on the other machine and that you typed https:// (not http://)."
  - Fingerprint fetch fails (network error / non-2xx / malformed body — daemon is not reachable at all): "We could not retrieve the certificate fingerprint from that daemon. Check the address and that the daemon is reachable, then try again."
  - Endpoint reachable but daemon has no TLS cert (200 response with `fingerprint: ""` — see the "Certificate fingerprint" state (2) above): NOT an error; surface the info-note copy instead. Distinguish this in the implementation from the fetch-failure case so authors are not told to retry when the daemon is deliberately loopback-only.
  - Key rejected (401/403 on first real request after connect): "The API key was not accepted. Double-check the key on the daemon machine."
  - Fingerprint mismatch on re-pin: the warning box above; no silent fallback.

  - All inputs have visible labels (no icon-only).
  - Password field for API key has "show/hide" toggle.
  - The fingerprint block is selectable + copyable (clipboard button).
  - The "Trust and connect" button is disabled until fingerprint is fetched and user has interacted with the confirmation control (prevents accidental enter-key trust).
  - On desktop, the key should prefer the OS keychain via Tauri secure-store when available; the UI is identical.

## P0↔P1 Seam (CONTACTUAL — do not extend)

The **ONLY** shared dependency between P0 (backend) and P1 (frontend) is the **cert-fingerprint endpoint contract** defined in T2 above:

| Artifact | P0 (implements) | P1 (consumes) |
|----------|----------------|---------------|
| `GET /v1/daemon/runtime/cert-fingerprint` | Handler in `api/handlers/runtime.rs`, router in `runtime_routes` (P0 T4) | Fetch + display + pin in setup screen (P1 T2) |
| `CertFingerprintResponse` (Rust) | Used by handler, codegen from schema | N/A |
| `CertFingerprintResponse` (TS) | N/A | Used by fetch hook, codegen from schema |
| `schemas/daemon-api/runtime/cert-fingerprint-response.schema.json` | Truth source for handler output (this plan T2) | Truth source for TS type (this plan T2) |

No other wire contract, shared state, module import, or runtime dependency crosses the P0↔P1 boundary. Specifically:

- The **connection-config DTO** (`{ endpointUrl, apiKey, pinnedFingerprint?, label? }`) is client-side storage only — NOT a wire contract, not consumed by the daemon.
- The **Origin allowlist** rule (P-1 T3 §16.4) is a daemon-side concern only; P1 documents the client expectation in T5 but does not alter the daemon allowlist.
- The **TOFU flow** is client-side logic; P0 has no awareness of client pinning, re-pin warnings, or "Revert to local" — its contract ends at serving the fingerprint value.
