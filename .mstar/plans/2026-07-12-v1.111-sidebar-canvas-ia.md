## Problem

The Control Room sidebar (`apps/web/src/components/layout/sidebar.tsx`) ships the
V1.94 flat two-tab IA (Creator + Orchestrator). The canvas has grown to three
rich surfaces but the IA does not nest them under Work context. V1.108/V1.109
compasses name "Sidebar canvas IA" as next.

## Scope

Restructure the sidebar to nest canvas surfaces (Strategy / Outline+Timeline /
World KB) under the active Work context, preserving V1.94 responsive behavior.

### Must

- FB-SB-000: Sidebar nests canvas surfaces under active Work context
- FB-SB-001: Surface selection navigates with Work context preserved
- FB-SB-002: Active surface highlight + collapse state consistent
- FB-SB-003: Narrow viewport behavior preserved (no V1.94 regression)

## Non-goals

- Top-level IA redesign beyond canvas nesting; customizable sidebar; cross-session
  persistence; backend changes.

## Architecture locks (architect — finalized 2026-07-12, code-evidenced)

> Investigated against `sidebar.tsx`, `shell-sidebar-chrome.tsx`,
> `sidebar.test.tsx`, and `App.tsx` routes.

1. **Nesting model — reframed (evidence-based).** The three canvas surfaces
   use **different route params**, so they CANNOT all nest under one "active
   Work" ID:
   - Outline → `/works/:workId/outline` (work-scoped)
   - World KB → `/worlds/:worldId/kb` (world-scoped — not work-scoped)
   - Strategy → `/strategies/:presetId` (preset-scoped — not work-scoped)
   - **Verdict:** the sidebar nests a **"Canvas" nav group** (via the existing
     `ShellNavGroup` disclosure — the chrome already supports collapsible
     groups with `defaultOpen`/chevron/`aria-expanded`) exposing the three
     canvas-surface entry points. **Active-surface highlight derives from route
     pattern matching** (`pathname.startsWith('/works/') &&
     pathname.includes('/outline')`, etc.), not from a single Work param.
   - **Long-term target (deferred, not in P1):** resolving the active
     Work/World/Preset *name* inline in the sidebar requires the sidebar to
     fetch entity data from route params — a larger scope. P1 ships the
     surface-entrypoint nesting + route-pattern active highlight now; the
     "active Work context name inline" is roadmap-next.
   - **Non-canvas items stay put:** Setup/Settings/Findings/Memory/SOUL remain
     in their current positions (Memory under Creator; Settings as footer
     utility; Findings reachable via current routes). Settings footer utility +
     profile switcher are untouched (chrome-owned).
2. **P0 coordinator** — P1 **consumes P0's `useRegisterCommand` hook** (from
   `lib/canvas/command-registry.ts`): registers "Go to Strategy / Outline /
   World KB" commands in a `useEffect`. Integration direction: **P1 → P0
   contract** (one-way). Parallel-safe: **file-disjoint** (P0 = new files +
   `root-layout.tsx`; P1 = `sidebar.tsx`). The only serial dependency is P1's
   T5 importing P0's registry contract — **P0 T1 must land before P1 T5**.
3. **State** — collapsed/expanded is **in-session only** via the chrome's
   existing internal `useState(group.defaultOpen ?? true)` (shell-sidebar-chrome.tsx:206).
   No persistence (matches V1.109 viewport discipline). No new state added.
4. **Responsive contract — clarified.** The "V1.94 responsive rules" the spec
   names are actually in `root-layout.tsx` (sidebar hidden below `lg`; horizontal
   top nav shown) — **P1 does NOT touch `root-layout.tsx`**, so narrow-viewport
   behavior is structurally preserved. `sidebar.test.tsx` tests **IA structure**
   (7 tests: tab defaults, tab swap, no Connect/Daemon links, tablist/tabpanel
   roles, footer profile switcher, Settings footer utility, active-highlight
   soft-fill + thin bar) — **not** viewport breakpoints. P1 preserves all 7;
   link-label assertions are updated with a documented reason if the Canvas
   group changes visible link names.
