**Status**: active (Phase 1 in flight — Review & Edit chain pending). Headline:

## 0. Context

V1.95 was supposed to fix the 6 setup-wizard bugs blocking first launch. PR
#124 merged with QC tri Approve (6 residuals deferred to V1.96). The author
then did a real wipe-and-relaunch smoke test (`~/.nexus42/` cleared) and
reported 3 issues, quoted verbatim from the feedback round:

1. **Layout is still ugly.** "这个布局真难看，太丑了，你必须提升高级感。
   可以考虑Steps 和右边内容呈现一体化设计，现在 steps 和步数文字都没对齐。
   整体我认为需要居中呈现。" The V1.95 left-sidebar layout landed but is
   visually unrefined: the wizard is left-aligned (no centering), the
   `StepIndicator` circle sits at the top of a 56px row while the label is
   vertically centered → circle and number do not align horizontally with
   the label, and the sidebar + content card read as two disconnected blocks
   (no integrated feel). The V1.95 token-pipeline fix was necessary but not
   sufficient — the layout IA itself needs a redesign, not a CSS-variable
   patch.
2. **Step 1 Browse button shows `[object Object]`.** "点 Browse 按钮报错
   `[object Object]`." Root cause: `setup-step-welcome.tsx:54` uses
   `err instanceof Error ? err.message : String(err)`. Tauri invoke errors
   arrive as plain objects (with a `message` field), not `Error` instances,
   so `String(err)` returns the literal string `[object Object]`. The daemon
   step already has the correct `errorMessage()` helper
   (`setup-step-daemon.tsx:85-90`) that checks `'message' in err` — but it
   was never extracted to a shared module. Author also requested: Browse
   button inline with the location display (stronger association), errors via
   unified hint/notification (not inline `<p>`), Continue as a large bottom
   button (visual prominence).
3. **Step 2 daemon never leaves "Starting daemon…".** "依然一直处于
   'Starting daemon…'的状态，长时间没反应。属于极其严重P0 级别的 blocker。
   （注意：我测试时已经清空了 ~/.nexus42/ 目录，没有任何残余）" This is
   **not** the V1.95 migration-mismatch scenario — `~/.nexus42/` was wiped.
   Multiple root causes confirmed by code reading:
   - **React subscription race**: `setup-step-daemon.tsx` `useEffect`
     subscribes via `desktop.onDaemonStatusChanged`. The callback only
     branches on `'running'` / `'error'` / `'stopped'` — there is **no
     `'starting'` branch**. The daemon auto-starts at Tauri boot
     (`lib.rs:529-538`) and enters `DaemonState::Starting` **before** the SPA
     subscribes. The first status the SPA receives is `state: 'starting'` →
     the callback does nothing → the wizard stays in the "Starting daemon…"
     UI forever (no state update).
   - **Stderr discarded** (V1.95 residual `R-V195-ARCH-STRERR-GAP`, medium):
     `sidecar.rs:246` does `let (_rx, child) = command.spawn()...` — the
     `_rx` receiver is dropped, so the daemon's real stderr (the actual crash
     reason — migration error, missing config, port bind failure) is never
     captured. `DaemonStatus.detail` only ever carries generic SidecarManager
     strings ("Daemon did not start. Check the logs…"). Even when the wizard
     does receive an Error status, the message is unhelpful.
   - **No wizard-side timeout** (V1.95 residual `R-V195QC3-S001`, low): if
     the sidecar never emits a terminal status event (e.g. SPA subscribes
     after the only `notify()` fired, or the daemon process is alive but
     hung), the wizard waits indefinitely. `useEffect` cleanup only
     unsubscribes; there is no hard timeout that forces a probe or surfaces
     "Taking longer than expected".
   - **First-launch daemon boot path** (suspected, needs RCA during
     implement): with a wiped `~/.nexus42/`, there is no `config.toml` and no
     `active_creator_id`. Per the V1.95 plan T9 architecture note,
     `crate::config::resolve_state_db_path()` requires `active_creator_id`;
     `WorkspaceState::initialize()` uses `?` on it → daemon may crash or hang
     on boot. The SidecarManager would normally detect a quick exit via
     `process_alive(pid)` and transition to Error — but if the daemon process
     stays alive (hung in initialization) the 15s `HEALTH_START_TIMEOUT`
     applies and then Error fires. Either way the wizard **should** eventually
     see Error — the fact that it does not is the React subscription bug
     above. Capturing stderr will confirm the true daemon-side cause.

## 2.2 Architecture review (architect, Phase 1 Review & Edit chain)

**Date**: 2026-07-07. **Author**: architect.

### React subscription race confirmed as primary wizard-side cause

The daemon auto-starts at Tauri boot (`lib.rs:529-538`) and enters
`DaemonState::Starting` **before** the SPA subscribes. The first status event
the SPA receives is `state: 'starting'`. The `onDaemonStatusChanged` callback
in `setup-step-daemon.tsx` (lines 41–48) has no `'starting'` branch — the
callback is a no-op → `setReady` stays false → the wizard stays in "Starting
daemon…" forever. This is the **primary mechanism** for the P0 hang.

A secondary race: on a clean `~/.nexus42/` first launch, the daemon crashes
within milliseconds (see below), `wait_for_first_health` returns `None`,
SidecarManager transitions to `Error` and fires `notify()`. If the SPA has not
yet subscribed, the Error event is lost. The SPA must call `getDaemonStatus()`
on mount to check the current state, not rely solely on the event listener for
initialization. This is the **secondary mechanism** — even after adding the
`'starting'` branch, the mount-time probe is needed to catch the "event already
fired" case.

**Conclusion**: the daemon does NOT hang — it crashes immediately. The wizard
just never learns about it. This is a React subscription race, not a daemon-side
hang.

### Stderr-capture implementation strategy

The `_rx` receiver at `sidecar.rs:246` is dropped, so daemon stderr is never
captured. The fix (T3) spawns a bounded async task that drains the event
receiver from `command.spawn()`, accumulates a tail capped at 2 kiB (nearest
newline-boundary), and appends the captured text verbatim to
`DaemonStatus.detail` on the Error transition in `start_with_budget`. The
stderr-reading task runs concurrently with `wait_for_first_health` — the spawn
path is not blocked. Existing generic SidecarManager messages are preserved as
fallback when stderr is empty. No schema change — the existing `detail:
Option<String>` field carries the combined message. Full strategy and code
sketch: `.mstar/iterations/v1.96/guides/daemon-startup-rca.md` §3.

### First-launch daemon boot path: no separate fix needed

With a wiped `~/.nexus42/`, `Config.toml` does not exist → `CliConfigSnapshot`
defaults to `active_creator_id: None` → `resolve_state_db_path()` (config.rs:98)
returns `Err("No active creator…")` → the `?` at workspace/mod.rs:166
propagates → `WorkspaceState::initialize()` returns `Err` → the daemon exits
immediately (crash, not hang). The SidecarManager's `wait_for_first_health`
detects the exit, transitions to `Error`, and fires `notify()` — but (1) the SPA
may miss the event (race), (2) the error message is generic (stderr discarded),
(3) there is no timeout escape. All three are wizard-side bugs.

**No daemon-side fix is needed.** The daemon correctly refuses to start without
an active creator. The wizard's job is to create the environment and retry. A
daemon that started silently without a creator would have undefined behavior
for every API route. **No T9 addition** — existing 8 tasks suffice.

## 5. Acceptance Criteria

- Desktop app opens without "The string did not match the expected pattern."
  (V1.95 regression check — must still pass on clean `~/.nexus42/` and on
  existing installs).
- **Step 1 Browse button no longer shows `[object Object]`.** Any Tauri
  invoke error from `pickDirectory` or `setWorkspacePath` (including the
  object-shaped errors Tauri returns) produces a readable message in the
  unified toast. The literal string `[object Object]` never appears for
  these failures.
- **Step 1 layout & error surface**: The Browse button appears inline with
  the workspace location display (icon + label + path + button grouped on
  one row or two tightly-coupled rows inside the same visual block). No
  wizard step renders an inline `<p role="alert">` for Tauri invoke
  failures; all such errors appear only via the global toast (variant
  "error"). The primary "Continue" button is a wide, prominent bottom CTA
  inside the card.
- **Step 2 wizard never hangs in "Starting daemon…" forever.** On every
  first-launch path (including clean `rm -rf ~/.nexus42/`), within a
  bounded timeout (≤30 s after step entry or subscription) the wizard
  either:
  - transitions to the "running" / success state and allows Continue, **or**
  - surfaces a real error whose text contains verbatim sidecar stderr (not
    only the generic SidecarManager wrapper), **or**
  - surfaces a "Taking longer than expected" state exposing visible
    Retry and Reset actions.
  The subscription callback explicitly handles `state === 'starting'`.
- **Step 2 surfaces the real daemon error.** When the daemon reaches
  `error` on boot (migration failure, missing config, port conflict,
  binary issues, etc.), the wizard `detail` contains the actual stderr
  captured from the sidecar process (clearly distinguishable from
  generic fallback text). Closes `R-V195-ARCH-STRERR-GAP`.
- **Setup wizard layout is centered + integrated.** The wizard card is
  centered in the viewport (horizontal + vertical). The step indicator
  list and the step content share a single card chrome container (one
  bordered/shadowed/background block). In every `StepIndicator` row the
  circle/marker and the label text align on the same horizontal baseline
  (no vertical offset).
- **DESIGN.md "Setup Wizard Surface" section exists** at Level 3 Production
  (light + dark tokens for spacing, hierarchy, motion, primary bottom CTA,
  inline row, toast surface, step indicator alignment). All setup wizard
  components consume tokens from this section for the audited surface; no
  ad-hoc Tailwind utilities replace the audited values.
- The author can complete a real wipe-and-relaunch smoke test
  (`rm -rf ~/.nexus42/` → launch desktop app → Step 1 shows inline Browse
  row + wide bottom Continue, no `[object Object]` on any error path →
  Step 2 exits "Starting daemon…" within ≤30 s with real output or
  timeout state → wizard completes → lands in `/works`) without manual
  recovery or console intervention.
- `pnpm --filter web test` green; `pnpm --filter web typecheck` clean;
  `pnpm --filter web build` green; `cargo test --all` green;
  `cargo clippy --all -- -D warnings` green;
  `cargo +nightly-2026-06-26 fmt --all --check` green.
