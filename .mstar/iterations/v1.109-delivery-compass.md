## Product Story

**Who:** Authors steering Works via Outline/Strategy canvases; the outline is their structural map and the strategy is their workflow graph. Contributors protecting spatial canvas quality in CI.

**Problem:** The Outline canvas stops at Chapter granularity — authors cannot see scene-level pacing or beat density on the map (master §3.3 already names Scene/Beat). The Strategy canvas renders the graph but edge creation/rewiring is inspector-only — authors cannot draw transitions where they reason about the DAG, unlike World KB connect and Outline foreshadow gestures. Toggling graph↔list loses pan/zoom; selection sync over-fires on drag; orchestrator tests mock away React Flow — all three become more painful as C2 nesting and Strategy edge gestures land.

**Narrative:** Deepen the Outline graph to Scene/Beat (C2) as **read-projection first** (write deferred unless architect proves otherwise), give Strategy the same spatial edge-editing class as Outline/World KB via draft→inspector→`strategy.patch_transition`, and invest in viewport/selection/test reliability so expanded graphs stay usable on real Works.

**Iteration complete when:** All three Must plans Done (or non-blocking residuals documented); P0 FB-C2-000..004 accepted in App; P1 FB-SE-000..003 accepted and FB-SE-004 accepted or residual-tracked; P2 FB-GS-000..002 accepted + FB-GS-003 disposition applied (fix closed / defer re-tracked).

### Five architecture questions — resolved with code/schema evidence

#### Q1 — Scene/Beat data source

**Verdict: NO scene/beat data exists in the outline model.** Confirmed against four sources:

| Source | Scene/Beat fields? |
|--------|--------------------|
| `schemas/daemon-api/canvas/outline/work-outline.schema.json` | **No** — `volumes[]`, `timeline_events[]`, `foreshadows[]`, `chapter_titles{}` only |
| `schemas/daemon-api/works/chapters/chapter-summary.schema.json` | **No** — title/slug/wc/status/outline_path/body_path only |
| `schemas/daemon-api/works/chapters/chapter-outline.schema.json` | **No** — opaque `content: string` markdown prose (V1.75 canvas-pivot chapter outline notes) |
| `crates/nexus-local-db/src/work_chapters.rs` `WorkChapterRecord` | **No** — same fields as ChapterSummary |

The "scene" / "beat" mentions elsewhere are **different concepts**: World KB `block_type: "scene" | "beat"` (entity taxonomy, not outline nodes); narrative crate `Works/<ref>/Beats/beat-sheet.md` (screenwriting Script Beat Sheets for `work_profile: script`, not novel-outline beats). Neither is the outline Scene/Beat from master spec §3.3/§3.4.

**Decision:** P0 ships as **fixture-driven read-projection** — Scene/Beat nodes render from Design Studio / test fixtures that inject scene/beat payloads at the UI projection layer. On real Works with no scene/beat data (the current state of every Work), chapters show honest empty chrome (*No scenes in this chapter yet.*). `wire_contracts_changed: false` holds: no wire is needed because the projection simply emits zero scene/beat children when the model has none. The fixture path lets Design Studio and tests exercise the full nesting/inspector/alt-view UI honestly. Additive read DTOs (`scenes[]`/`beats[]` on `WorkOutline`) are deferred to a future iteration when the daemon actually models scenes/beats — tracked in the P0 spec roadmap.

#### Q2 — Beat parent model

**Verdict: Scene→Beat nesting** (matches master spec §3.4 `WorkNodeData.nodeKind: "scene" | "beat"` and the product thesis "beats inside scenes inside chapters"). Since there is no daemon data, the **fixture contract** defines the hierarchy: Scene is a child of Chapter (`parentId = chapter:<n>`, `extent: "parent"`); Beat is a child of Scene (`parentId = scene:<id>`, `extent: "parent"`). Flat-under-chapter is NOT the model. The new `OutlineSceneNodeData` / `OutlineBeatNodeData` interfaces in `rf-projection.ts` enforce Scene→Beat nesting.

#### Q3 — `strategy.patch_transition` sufficiency for spatial create + reconnect

**Verdict: PARTIALLY sufficient — escape hatch FIRES for P1 create path.**

Read of `crates/nexus-daemon-runtime/src/api/handlers/strategy.rs` `patch_transition_inner` + `apply_transition_patch` (lines 660–878):

| Product bar | DTO + daemon support? | Evidence |
|-------------|----------------------|----------|
| **FB-SE-003 reconnect existing edge** | **YES — fully covered** | `source_state_id` + `old_target` + `new_target` + `condition` matches existing `next`/`rules`/`default`/`go`/`nogo` and replaces atomically. Single reconnect payload; no delete+create needed. |
| **FB-SE-000/001/002 create brand-new transition** | **NO — daemon rejects** | Source state with no `next` field → `strategy_transition_missing` (400). Source state with `next` but no matching `old_target` branch → `strategy_transition_not_found` (400). The DTO is **rewire-only**. |

**Escape hatch (locks P1 wire change):** Additive `op: "create" | "update"` field on `StrategyPatchTransitionRequest` (default `"update"` for backward compatibility). When `op: "create"`:
- Source state with no `next` → set `next: <new_target>` (linear) or `next: { rules: [{ to: new_target, when: condition }] }` (branch, when `condition` present).
- Source state with `next` as a map → append a new rule `{ to: new_target, when: condition }`.

This is an **additive, backward-compatible** wire change → `wire_contracts_changed: true` for P1. `@42ch/nexus-contracts` minor bump only (new optional field; default preserves existing rewire behavior; no breaking change to shipped V1.71 callers). This overrides the PM `false` default with code evidence — the PM default was set before reading the daemon handler.

#### Q4 — Reconnect shape

**Verdict: Single reconnect payload.** The DTO already supports reconnect atomically (`source_state_id` + `old_target` + `new_target` + `condition`). Delete-old + create-new is NOT needed for reconnect. P1 plan Task 3 uses the single reconnect path directly. (Delete-old + create-new semantics apply only to the Q3 create escape hatch when appending a new branch, not to reconnect.)

#### Q5 — R-V1108P0QC1-S001 `useOutlineCanvasGraph()` extract

**Verdict: P0 owns the extract.** The current `outline-canvas.tsx` (361 lines) already mixes projection memo + RF state sync + selection-sync effect (the R-V1108P0QC3-W001 overfire) + conflict state + 3 patch handlers + layout. Adding Scene/Beat (2 new node types, 2 new selection resolutions, 2 inspector panels, alt-view rows) would push it past 450 lines and make the selection-sync effect harder to fix cleanly. Extracting `useOutlineCanvasGraph()` (projection + RF state + selection sync) in P0 keeps the orchestrator thin, closes R-V1108P0QC1-S001, and unblocks R-V1108P1QC1-S002 (studio import of node chrome). **The extract is architect-locked into P0**, which changes FB-GS-003's disposition for R-V1108P0QC1-S001 from "Fix if P0 needs it; else defer" → "Fixed in P0".
