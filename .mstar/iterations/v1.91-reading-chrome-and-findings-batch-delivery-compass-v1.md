**Status**: active — Phase 1 Review & Edit chain pending.

## 0. Context

V1.90 shipped the Daemon API remote-ready rename (`/v1/local/*` → `/v1/daemon/*`, opt-in remote bind). The codebase is in a clean state with zero open residuals and no active plans.

V1.91 returns to product-experience work on two fronts with a clear P0 + P1 split:

1. **Profile-specific reading chrome (BL-13, headline P0)** — the V1.89 deeper-manuscript-reading MVP left the actual read-only manuscript surface profile-agnostic. V1.91 makes the reading view feel native to each shipped work profile: `novel`, `essay`, `game-bible`, and `script`. Authors immediately recognize "this is a novel chapter" vs "this is a script scene" via typography, separators, and structural cues — all driven by DESIGN.md tokens. Reading chrome is strictly read-only.
2. **Findings batch triage companion (P1)** — V1.77 made findings editable one-by-one. Authors with dozens of findings still pay a high click cost. V1.91 adds multi-select batch status transition + `target_executor` assignment + client-side CSV export of the current filtered list. One additive bulk PATCH helper endpoint only.

## 2. Scope

This iteration locks four delivery items:

- **SP-1: P-1 Prepare**. Lock the reading-chrome design: per-profile chrome elements, DESIGN.md token contract, where each profile reads its styling cues from, and the bulk PATCH helper contract for findings.
- **SP-2: Reading chrome (P0)**. Implement differentiated read-only rendering in `apps/web` for the four shipped work profiles, driven by new DESIGN.md reading-chrome tokens. Add or update UI component tests for each profile.
- **SP-3: Findings batch triage (P1)**. Add a backend bulk PATCH helper endpoint for findings status + target_executor, and wire the `apps/web` findings list with multi-select, batch actions, and client-side CSV export.
- **SP-4: Closure (P-last)**. QC tri-review + QA + spec/AGENTS/DESIGN.md hygiene + update deferred-features tracker (mark BL-13 in progress/complete) + compound + Profile B compaction + PR to `main`.

### 2.1 Architecture Hierarchy and Ownership

- **P-1 (Prepare) produces contract artifacts only**: `apps/web/DESIGN.md` new `## Reading Chrome` token section (SSOT for typography, spacing, separators, cross-refs, role/scene formatting); per-profile chrome element checklist (locked in this compass or prepare plan); findings bulk PATCH schema + contract (request/response shapes, idempotency, limits, error model, codegen step).
  - **Explicit decision**: V1.91 reading chrome is a presentational/read-only concern driven by DESIGN.md tokens. No amendments are made to `knowledge/specs/{essay,game-bible,script}-profile.md`, `novel-writing/` subtree, or `findings-lifecycle.md`. Profile reading conventions for chrome remain in the P-1 plan + DESIGN.md section. The domain profile specs continue to own workflow, artifacts, stage chains, and completion semantics.
  - **Architecture decision (schema/codegen)**: The bulk PATCH endpoint is consumed by `apps/web` (TypeScript, external client boundary), therefore it requires JSON Schema entries under `schemas/daemon-api/findings/` and a `pnpm run codegen` run. The schemas are additive only; no existing schema files are modified. See prepare plan §3 for the full DTO specification.
- **P0 lives in `apps/web` only (headline)**: profile-aware read-only chrome components, consumption of DESIGN.md reading-chrome tokens, UI/component tests for each of the four profiles. Zero backend, zero write paths, zero canvas changes.
- **P1 lives in `crates/nexus-daemon-runtime` (one additive handler) + `apps/web` findings list (companion)**: `PATCH /v1/daemon/findings/batch` helper + multi-select + batch actions + client-side CSV export. P1 may reuse existing DESIGN tokens but adds no reading-chrome tokens.
- **Strict separation**: P0 never touches findings; P1 never touches reading chrome or `body_path`. Both preserve the read-only body-ownership invariant established in prior iterations.

### 2.2 Product Success Criteria

**Primary outcome — Reading chrome (P0 headline, user value)**:
- Authors opening a Work immediately perceive the profile identity through the reading surface (reduced cognitive load when moving between novel / essay / game-bible / script work).
- Each of the four shipped profiles renders with at least two distinct, token-driven visual markers (examples below). Markers are implemented via new `apps/web/DESIGN.md` reading-chrome tokens (no ad-hoc CSS or Tailwind duplication).
  - `novel`: chapter/epigraph title treatment + thematic scene separator (e.g. `* * *` or rule).
  - `essay`: section hierarchy + styled blockquote or footnote markers.
  - `game-bible`: term cross-reference links + definition callout or category badge.
  - `script`: character-name block + parenthetical/action line distinction + scene heading treatment.
- Reading surface is strictly read-only: no route, component, or test writes `body_path`, outline, or timeline state. Body ownership invariant preserved.
- Verifiable: component test asserts profile-specific classes/attributes derived from DESIGN tokens; PR includes per-profile visual evidence (screenshot or storybook capture).

**Companion outcome — Findings batch triage (P1)**:
- Authors with N findings (target: 20+) can complete status triage or executor assignment in one multi-select action instead of N separate edits.
- Client-side CSV export of the currently filtered list produces a file with the documented columns (id, title, status, kind, severity, target_executor, created_at, rule_suggestion truncated).
- Bulk PATCH helper is additive, capped (≤100 IDs), creator-scoped, and covered by ≥1 Rust integration test that asserts exact count updated and error shapes for not-found/conflict.
- Single-finding edit path and existing list behavior are unchanged (regression bar).

## 6. Non-Goals (enforced)

- **No body editor / canvas write-boundary changes** — reading chrome is read-only presentational layer only. See §5 AC (read-only invariant) and P0 non-goals. Any diff that writes `body_path` or outline is out of scope and must be rejected.
- **No TLS/mTLS or remote bind hardening** — V1.90 scope; C direction explicitly out.
- **No standalone maturation dashboard** — BL-09 deferred.
- **No findings auto-generation, LLM suggestions, complex filter DSL, or full remediation workflow** — P1 is batch triage only (multi-select + two fields + client CSV).
- **No backend export jobs, scheduled reports, or server-side CSV** — export is purely client-side from the in-memory filtered list.
- **No breaking wire contract changes** — only additive schemas (2 new files for batch PATCH under `schemas/daemon-api/findings/`); no renames, no deletions, no schema_version bump.
- **No new HTTP routes beyond the one additive bulk PATCH helper** — P0 adds zero backend routes; P1 adds exactly one new handler. No middleware, TLS, or transport layer changes.
- **No new work profiles** — chrome limited to the four shipped profiles (`novel`, `essay`, `game-bible`, `script`).
- **No piggybacking** — P0 and P1 worktrees are isolated; shared `apps/web` components may be touched only for additive multi-select that does not alter reading chrome.
- **No findings state machine changes** — bulk PATCH reuses existing `update_finding` DAO validation (transition enforcement, enum membership). No new status values, no transition edge additions, no new validation rules.

All non-goals are repeated in the individual P0/P1 plans and cited in Assignments.
