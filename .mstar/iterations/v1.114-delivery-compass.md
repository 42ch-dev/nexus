# V1.114 Delivery Compass — Canvas & Compute Module Foundation

## Product story (why authors care)

Nexus promises authors two things that plain editors cannot: a **Canvas** that
is the steering surface for non-linear creative structure, and **Compute
Modules** that are the deterministic engine for world rules (combat, dice,
relationship math). Four canvas surfaces already ship (Strategy, Outline+Timeline,
World KB, Relationships) and the V1 compute ABI is real — but authors still
cannot fully *use* either pillar as intended.

What authors experience today:

1. **Steering costs too much layout work** — opening a 30-chapter outline or a
   50-entity World KB means dragging every node into a readable shape before
   thinking about story. The canvas feels like a whiteboard to tidy, not a
   cockpit to steer. Auto-layout is the #1 deferred canvas ask since V1.72.
2. **Trust in the write boundary is incomplete** — a few graph invariants (no
   self-loop edges, no duplicate transition rules) are enforced only in the UI.
   Authors who use desktop + multi-client, or future API clients, can create
   invalid Strategy graphs the daemon should never accept. Stability is part of
   product quality, not just engineering hygiene.
3. **The deterministic engine is a black box** — compute already mutates
   KeyBlock state (e.g. `current_hp`) and produces reports, but authors cannot
   answer: *What modules are installed? What do they do? What state did they
   leave on my characters?* Without visibility, compute cannot become a selling
   point or a trustable collaborator.

**V1.114 is a foundation iteration:** make Canvas easier to steer (layout +
shared surface recipe), harder to corrupt (server guards + residual honesty),
and make Compute *visible and inspectable* so future marketplace / composition /
canvas-intersection work has somewhere to land. Not a new author loop — the
floor under the two pillars.

## Scope

**Direction lock mode: autonomous** (code-first research → ranked candidates → locked).

Strengthen the two product pillars' foundation across four product dimensions:
**extensibility** (5th surface is a recipe, not a rewrite), **stability**
(daemon owns graph invariants), **usability** (auto-layout removes layout
chores), **comprehensibility** (authors can see and inspect compute).

### Must justification (all three plans)

L budget allows 3–4 business plans. All three are **Must** because they form
one coherent foundation bet — not three optional extras:

| Plan | Why Must (product) | What fails if deferred |
|------|--------------------|------------------------|
| **P0** Canvas Architecture | Auto-layout is the daily author pain; adapter recipe is the only honest way to add surfaces after four concrete use cases (STRATEGY: simplicity threshold crossed) | Next canvas feature iteration pays full boilerplate tax + authors keep dragging |
| **P1** Canvas Stability | Write-boundary trust is a product promise ("structured write, no silent corruption"); residual honesty keeps foundation claims credible | Invalid Strategy graphs can land via non-UI clients; residual slate stays noisy |
| **P2** Compute Visibility | Compute cannot be a pillar authors *choose* while it is invisible; state read unblocks every future compute UI | Marketplace / state editor / canvas-intersection all stay blocked on "see modules + state first" |

None is Stretch: each is necessary for the iteration story "Canvas steers, Compute is inspectable." If capacity forces a cut, cut depth *inside* a plan (e.g. migrate 2 surfaces not 4; ≥10 residuals not 15), not an entire plan.

1. **P0 - Canvas Architecture Foundation (Must, L):** Shared canvas adapter so
   a 5th surface is a recipe (~50% less boilerplate). **Dagre auto-layout** —
   authors get a readable graph on open + "Re-layout", with manual drag still
   winning until the next re-layout. Consolidate shared canvas hooks. Document
   the 4-surface pattern as the canonical surface-addition recipe.
2. **P1 - Canvas Stability & Validation Hardening (Must, M):** Close
   server-side validation gaps (self-loop guard `R-V1109-P1-QC2-W001`, duplicate
   transition dedup `R-V1109-P1-QC2-W002`). Command-registry collision detection
   (`R-V1111P0QC2-W002`). Harmonize conflict-modal a11y patterns across
   surfaces. Close ≥10 canvas-cluster open residuals from `status.json`.
3. **P2 - Compute Module Foundation & Visibility (Must, M):** Daemon API
   compute-module registry (list modules + manifests). Computable KeyBlock
   **state read** (the `state` compute mutates is no longer write-only).
   Minimal **Modules panel** in Control Room so authors discover installed
   modules and what they do. Consolidate compute onboarding docs.

### Autonomous direction lock rationale

Ranked by: deferred/roadmap next > STRATEGY alignment > product completeness > risk.

- **Deferred/roadmap next**: V1.113 compass `## Roadmap Position` names
  "Resume deferred canvas trajectory (graph layout engine dagre/elk; Strategy
  onConnect for inner-graph groups)" as the top next-iteration candidate.
  Canvas-spec §6 roadmap lists dagre/elk as a durable tracked item since V1.72.
  Compute-module-abi.md §9.3 defers "KB state → human-readable UI editor" to
  V2.0+, but the read-side foundation (state visibility) is V1-scope and blocks
  all future compute UI.
- **STRATEGY alignment**: "Simplicity over premature abstraction — don't
  abstract before there are three concrete use cases." Canvas now has **four**
  concrete surfaces with duplicated adapter patterns — the abstraction is
  overdue, not premature. "Local-first by default" — compute module
  visibility helps authors understand what runs locally.
- **Product completeness**: Canvas auto-layout is a daily author pain (manual
  node positioning). Compute invisibility means authors cannot trust or inspect
  what the engine does to their world state.
- **Risk**: All three plans are additive (new shared abstraction, new endpoints,
  new UI page) with contained blast radius. P0 is the largest (touches shared
  shell) but is refactoring, not new behavior. `wire_contracts_changed` expected
  true only on P2 (additive compute registry endpoints).

## Acceptance Criteria

**Iteration-level Done gate** — prefer author-observable outcomes; engineering
checks are evidence, not the story.

### Author-observable (product)

- [ ] **Open → readable graph:** On Strategy and at least one other migrated
  surface, opening a non-trivial graph (e.g. 20+ outline nodes or 30+ World KB
  entities) produces a readable auto-layout without the author dragging every
  node first
- [ ] **Manual control preserved:** After the author drags a node, that position
  sticks until they choose **Re-layout**; Re-layout restores an engine layout
- [ ] **Invalid Strategy graphs rejected at the source of truth:** Creating a
  self-loop edge or a duplicate transition rule fails with a clear error even
  when the client guard is bypassed (daemon 422 / equivalent)
- [ ] **Conflict UX feels consistent:** Across the four canvas conflict modals,
  focus trap, keyboard dismiss, and ARIA announcements behave the same way
  (surface-specific copy may differ)
- [ ] **Discover compute:** From Control Room, an author can open a Modules
  panel, see `basic-combat` (and any other installed module), and read name /
  version / description / required KeyBlock types
- [ ] **Inspect compute state:** For a computable KeyBlock, an author (or API
  client) can read the dynamic `state` the engine mutates — not only that the
  block exists

### Engineering evidence (supports the product gate)

- [ ] Shared canvas adapter exists and is consumed by ≥2 of 4 shipped surfaces
- [ ] Command registry detects id collisions (dev-mode warn at minimum)
- [ ] ≥10 canvas-cluster open residuals closed or accepted with rationale
- [ ] Additive compute registry + state-read contracts codegenerated; existing
  canvas + compute tests pass; new tests cover auto-layout, validation guards,
  registry, and state read
- [ ] `status.json` updated + `tech_debt_summary` refreshed; `wc -c` trending down

## Non-Goals

Honest freeze — do not let these creep into V1.114 "while we're here":

- **New canvas surface** (compute graph, session replay) — foundation only
- **New compute module** beyond proving `basic-combat` appears in the registry
- **Run / invoke compute from UI** — orchestration remains the runner; V1.114 is
  discover + inspect, not "press Play"
- **Computable-state editor** (write/edit `body.state` in UI) — read foundation
  only; V2.0+ "KB state → human-readable UI editor" stays deferred
- **Multi-module composition / chaining** (V2.0+ ABI, compute-module-abi.md §9.3)
- **CDN module distribution + signing** (V2.0+)
- **Module marketplace / public registry** (V3.0+)
- **Compute module authoring SDK / tooling** (separate future iteration)
- **Canvas ↔ compute intersection UI** (show battle reports / state deltas on
  canvas nodes) — needs this foundation first
- **Persisted layout positions** to the daemon (auto-layout is ephemeral this
  iteration; save-layout is a follow-on)
- **ELK / alternate layout engines** — dagre only; evaluate ELK only if dagre
  fails real novel/world graphs (record as residual if so)
- **Big-bang migrate all 4 surfaces** to the adapter (≥2 is the proof target)
- **Retiring any shipped canvas surface**
- **`preset` → `strategy` CLI/schema rename** (still deferred; UI terminology only)
- **Dynamic locale bundle splitting** (R-P0-003 — separate future iteration)
- **Closing the entire residual slate** (bounded ≥10 canvas-cluster closures)

## Roadmap Position

- **Current (V1.114):** Canvas & Compute Module Foundation — layout + surface
  recipe + write-boundary trust + first compute visibility so both pillars are
  *usable and inspectable*, not only *implemented*.
- **Immediate next (pick at next iteration-start; foundation enables all):**
  1. **Canvas trajectory resume** — Strategy `onConnect` for inner-graph groups;
     optional 5th surface (compute graph *or* session replay) using the new
     adapter recipe
  2. **Compute depth** — state editor / human-readable state views; or module
     authoring SDK; still no marketplace until visibility patterns prove out
  3. **Intersection** — surface compute outcomes on canvas (only after P2
     registry + state read exist)

  Trigger: V1.114 Done + author priority. Owner: PM at iteration-start.
  Do not open a 5th surface *and* marketplace in the same iteration.

- **North star:** Local-first AI-autonomous creative executor — **Canvas is the
  steering surface**, **Compute Modules are the deterministic engine** — both
  comprehensible, stable, and extensible without premature abstraction.
