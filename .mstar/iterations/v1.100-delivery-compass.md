# V1.100 — UI Completion: Desktop First-Launch, Form Fields, Guardrails

## Scope

V1.100 is a UI completeness iteration that closes the most important post-V1.99 user-facing and design-system gaps in one coordinated package.

- **SP-1: Desktop clean-state first-launch completion.** Remove the last known first-run blocker for a new author: a clean desktop install currently reaches the sidecar, then fails with `No active creator` because `.setup()` auto-starts before the wizard bootstraps creator/workspace state.
- **SP-2: UI guardrails and `cn` / Tailwind merge SSOT.** Turn the V1.99 promotion workflow into a repeatable product system by making wrapper drift and Design Studio boundary violations mechanically detectable, then consolidate duplicated class-merge configuration behind one approved SSOT.
- **SP-3: Form Field component slice.** Promote `Input`, `Label`, and `Textarea` only after locking form-field semantics: label/control association, invalid and described-by behavior, helper/error ownership, required/optional copy, and app-owned validation/composition boundaries.

## Product Story

This is not three unrelated cleanup tracks. V1.100 makes the local desktop experience credible for a first-time author and makes the design-system promotion path credible for contributors. P0 closes the author-visible launch failure; P1 prevents the package/studio drift that would make every future UI promotion fragile; P2 proves that the next component promotion slice is semantics-first, not a mechanical copy of app-local shadcn wrappers.

The iteration should leave Nexus with one clear user promise: a new author can open the desktop app from a clean state, and contributors can promote form controls through a guarded, accessible, package-owned presentational surface without smuggling app behavior into `@42ch/nexus-ui`.

## Acceptance Criteria

- Clean-state desktop first launch no longer auto-starts the daemon before creator/workspace bootstrap is complete, and the wizard can bring a new author from fresh local state to the main UI.
- Existing-install desktop launch preserves the prior behavior: setup-completed installs skip the wizard, the sidecar auto-start/attach path still works, and recovery copy remains actionable on failure.
- `R-V197-SMOKE-CLEAN-STATE` is closed by implementation plus interactive macOS clean-state smoke evidence; `R-V197-SMOKE-UI` is closed or explicitly re-scoped with user-approved evidence.
- V1.99 package hygiene residuals `R-V199QC1-S001`, `R-V199QC1-S002`, and `R-V199QC3-F001` are resolved or replaced with a narrower residual only if architect review finds full SSOT consolidation would create an unacceptable package cycle.
- Design Studio boundary checks and promoted-wrapper guardrails run in CI or an equivalent repository gate, not only by manual grep.
- `@42ch/nexus-ui` is the approved class-merge SSOT, and Web/Studio consumers either import/re-export that authority or carry a named temporary parity residual with failing drift checks.
- `Input`, `Label`, and `Textarea` are exported from `@42ch/nexus-ui`, consumed by Design Studio through package imports, and consumed by Web through the approved wrapper/direct-import strategy.
- Form-field accessibility semantics are explicit: label association, invalid state, helper/error description wiring, required/optional copy ownership, and app-owned validation boundaries.
- No app routing, daemon clients, Tauri IPC, product hooks, or layout shells enter `@42ch/nexus-ui` or Design Studio fixtures.
- Prepare gates remain complete for all three plans: product scope, decisions, dependencies, blocked_by relationships, and non-goals are documented before PM lock.
- `wire_contracts_changed: false`; desktop bootstrap uses Tauri IPC, UI guardrails use package/tooling checks, and form-field promotion changes npm package/app surfaces only. Any proposed `schemas/` change blocks implementation and returns to architect/PM review.

## Non-Goals

- No billing, platform sync, cloud platform, entitlement, or marketplace work.
- No full Web redesign or migration of every form call site to a new framework.
- No package-level form state manager, validation library integration, or React Hook Form/Zod adoption.
- No promotion of `Select`, dialogs, tabs, tables, app chrome, or daemon-aware controls.
- No signing, notarization, auto-update, Windows/Linux release hardening, or tray work.
- No daemon API schema change; if Tauri-side bootstrap is blocked, implementation returns to architecture review instead of expanding daemon wire contracts.

## Roadmap Position

- **Current iteration (V1.100)**: Close the UI completeness gaps left after V1.99: first-launch desktop reliability, design-system guardrails, and the first form-field promotion slice.
- **Relation to V1.99**: Builds directly on V1.99's component promotion workflow while addressing the post-V1.99 hygiene residuals before expanding the package surface.
- **Relation to V1.97**: Completes the desktop clean-state first-launch path that V1.97 made reachable but could not finish because creator/workspace bootstrap was still missing.
- **Next iteration**: If V1.100 lands cleanly, the next UI line can move from primitives into higher-order authoring surfaces or continue design-system promotion (`Select`, field groups, or app-local form composition) based on residuals. Trigger: P2 QA and smoke evidence complete.
- **Final target**: New authors can launch the desktop app cleanly, contributors can promote UI primitives without package drift, and form controls have one shared, accessible presentational foundation.
