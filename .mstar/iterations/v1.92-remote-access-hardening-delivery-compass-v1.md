# V1.92 — Remote-Access Hardening (TLS + Remote Connection Model) — Delivery Compass v1

**Status**: active (Review & Edit chain in progress — product-manager 5.1 done, architect 5.2 done, writing-specialist 5.3 next). `wire_contracts_changed: true` (additive fingerprint endpoint DTO). PR to `main` after Phase 3.

## 0. Context

V1.90 made the daemon **opt-in remote-bind capable** (`ensure_remote_bind_allowed`: non-loopback bind requires both `NEXUS42_DAEMON_API_KEY` and `NEXUS_DAEMON_REMOTE_BIND=1`). V1.86 closed the Daemon API (then called Local API) trust-boundary attack chain (Origin allowlist + `require_allowed_origin` + fs/* deny + component-wise path guard) but explicitly deferred CSRF tokens, Unix-socket-only, and transport security as non-goals pending threat-model growth.

V1.90's remote-bind is the threat-model growth V1.86 was waiting for, and it exposes two gaps the PM verified against source during grill-me:

1. **No transport security.** A `grep` for `rustls`/`TlsAcceptor` across `crates/` and `apps/` returns zero matches. The listener (`boot.rs` §10) is plain `tokio::net::TcpListener` + `axum::serve`. A remote bind therefore exposes the API key and manuscript data in cleartext on the wire — defeating the entire purpose of the V1.90 key gate.
2. **Remote bind is unusable by browser/desktop clients.** `BrowserClient` / `TauriClient` (`apps/web/src/lib/nexus/`) use **same-origin relative paths** and send **no `X-API-Key` header** — they rely on loopback keyless-localhost bypass. Remote bind requires the key, but the key cannot safely live in a public SPA bundle. So today only non-browser clients (CLI, `curl`, workers) holding the key can use remote bind.

**Product vision (grill-me locked)**: a trusted-network scenario — Machine A runs the daemon headless, Machine B (with a GUI) runs the web-ui or desktop app and connects to A's daemon, behaving identically to local, with a future UI affordance to switch daemon endpoints.

This iteration makes that vision work safely. It is a **dual-track security + remote-access** iteration: V1.90 opened the door; V1.92 puts the lock and the welcome mat on it.

## 0.1 Terminology conventions (writing-specialist glossary)

Consistent terms across the compass, plans, and V1.92 spec amendment. See also root [`CONCEPTS.md`](../../CONCEPTS.md).

| Term | Meaning in V1.92 |
|------|------------------|
| **Daemon** | The local background process (`nexus42 daemon start`) that owns the SQLite DB and serves the HTTP API. |
| **Daemon API** | The HTTP surface under `/v1/daemon/*` served by the daemon. (Historically "Local API" pre-V1.90 — do NOT use that name in new V1.92 prose.) |
| **Remote bind** | A daemon started on a non-loopback address, gated by `NEXUS42_DAEMON_API_KEY` + `NEXUS_DAEMON_REMOTE_BIND=1` (V1.90) + a usable TLS cert (V1.92). |
| **Certificate fingerprint** | Author-facing / user-facing full term for the SHA-256 of the DER-encoded TLS certificate. Used in the setup screen, spec, and any prose read by authors or contributors. |
| **Fingerprint** | Acceptable internal shorthand for "certificate fingerprint" once the full term has been introduced in the surrounding context (e.g. inside a technical block that already established the referent). Do NOT use bare "fingerprint" in first mentions of author-facing copy. |
| **TOFU** | Trust On First Use. Never used in author-facing UI copy without an immediate plain-English gloss; acceptable in specs and internal prose. |
| **Trust anchor** | The public value clients pin to verify future connections. The certificate fingerprint is the trust anchor in V1.92 (analogous to an SSH host key). |
| **Connection config** | The client-side stored `{ endpointUrl, apiKey, pinnedFingerprint?, label? }` object. NOT a wire contract. |
| **Setup screen** | The "Connect to Daemon" surface in the web-ui / desktop app that collects endpoint + key + performs the TOFU fingerprint confirmation and pins it. |

## 1. Locked Decisions (grill-me output)

| Decision | Resolution |
|---|---|
| Iteration direction | **C (remote-access hardening) + companion residual sweep.** Two headlines: TLS + remote client connection model. |
| Headline 1 — TLS | **Daemon auto-generates a self-signed certificate** on first boot (rustls + `rcgen`), stored under `~/.nexus42/tls/`. Loopback binds may stay plain HTTP (dev ergonomics, no threat). **Remote bind runs behind TLS** (the remote-bind gate integrates with the TLS listener). User chose auto self-signed to avoid short-term ops burden of supplying certs. Browser-direct-to-remote warnings are accepted; the **Tauri desktop app and web-app connection flow trust the cert via TOFU** (fingerprint confirm), not raw-browser-tab trust. |
| Headline 2 — Remote connection model | **web-ui / desktop app gain a "Connect to Daemon" setup screen**: endpoint URL + API key + TOFU cert-fingerprint confirm. `BrowserClient` / `TauriClient` are parameterised by base URL + `X-API-Key` header. Local same-origin mode (daemon-served SPA, loopback bypass) remains the backwards-compatible default. |
| CSRF posture | **Explicit CSRF token framework is a NON-GOAL.** The remote connection model authenticates via a custom `X-API-Key` request header. Cross-origin JS cannot set a custom header without triggering a CORS preflight, which the V1.86 Origin allowlist already gates. Header-key + Origin allowlist therefore constitute complete CSRF defence for this model. A separate cookie/session/token layer would be redundant and would add maintenance surface. |
| Certificate trust model | **TOFU (Trust On First Use).** Daemon logs its cert fingerprint at startup; the connection setup screen shows the fingerprint for first-use confirmation and pins it per-endpoint in client storage. Re-pinning on fingerprint change is an explicit user action with a clear warning. |
| Client key storage | Web: `localStorage` (same trust boundary as the SPA itself, local-first product). Desktop (Tauri): Tauri secure-store / OS keychain where available, fallback to app data dir. The key is a user-entered secret, not compiled in. |
| Contract impact | **YES — additive.** (a) One new read-only endpoint exposing the daemon cert fingerprint (`GET /v1/daemon/runtime/cert-fingerprint`, response schema `schemas/daemon-api/runtime/cert-fingerprint-response.schema.json` — no sensitive data, no mutation surface). (b) The client-connection-config DTO (`{ endpointUrl, apiKey, pinnedFingerprint?, label? }`) is a **frontend concern only** — stored client-side, never sent to the daemon, NOT a wire contract or schema artifact. `@42ch/nexus-contracts`: `0.19.1 → 0.20.0` (additive — new DTO, no breaking renames, no `schema_version` bump; pre-1.0 convention: bump MINOR for additive wire contracts). `wire_contracts_changed: true`. |
| Plan structure | **P-1 Prepare** (specs + TLS design + connection contract + DESIGN.md tokens + Origin allowlist evolution + R-V191P1-003 codegen folded in) → **P0 TLS backend** (`@fullstack-dev`) ‖ **P1 Remote connection frontend** (`@frontend-dev`) parallel worktrees → **P-last closure** (QC tri-review + QA + compound + Profile B + PR). P0 ‖ P1 share the P-1-locked fingerprint-endpoint contract; the rest is independent (backend crate vs `apps/web`). |
| Branch policy | `iteration_base_branch=main` (HEAD post-V1.91, PR #119); `spec_integration_branch=iteration/v1.92`; `target_branch=main`. Matches documented project convention (`.mstar/AGENTS.md` two-tier branch model) and V1.39–V1.91 history. |

R-V191P1-005 (nit, FindingsPage memoisation) stays deferred to "when list virtualisation lands" (unchanged). |

## 2. Scope

This iteration locks three delivery spec points plus closure:

- **SP-1: Prepare — Specs, Contracts, and Design Tokens (P-1).** Lock the TLS design (rustls + `rcgen`, cert lifecycle, remote/TLS gate integration, fingerprint exposure), the remote-connection contract (client config shape, TOFU flow, `BrowserClient`/`TauriClient` parameterisation boundary), the Origin-allowlist evolution for the remote-client case, and DESIGN.md tokens for the connection setup screen. Amend `knowledge/specs/daemon-runtime.md` with the transport-security + remote-connection section. Fold in R-V191P1-003 (codegen emits concrete `BatchUpdateFindingsRequest.patch` struct). Architect-owned contracts; product+frontend-owned setup-screen design; writing-owned terminology.
- **SP-2: TLS for Remote Bind — P0 (security-transport headline).** Daemon auto-generates a self-signed cert on first boot (`~/.nexus42/tls/`), persists it across restarts, logs the fingerprint. A TLS listener path (rustls via `tokio-rustls` wrapping the accepted `TcpStream`, or `axum-server` `bind_rustls` — architect's choice in Prepare) serves the daemon when a cert is present and the bind is non-loopback. Remote bind without a usable cert → the gate refuses to start remote (fail-closed, consistent with V1.90). Loopback HTTP stays plain. Expose the cert fingerprint via a read-only endpoint (no auth required — the fingerprint is public by design; it is the *trust anchor*, not a secret). Regression tests: cert generation idempotent, remote bind refused without cert, TLS handshake succeeds with the generated cert, fingerprint endpoint returns the pinned value. Fold in R-V191P1-004 (mid-batch internal-error partial-apply test on the findings batch handler, same backend crate).
- **SP-3: Remote Client Connection Model — P1 (product-access headline).** `BrowserClient` / `TauriClient` parameterised by base URL (default: same-origin relative, backwards compat) + optional `X-API-Key` header. A "Connect to Daemon" setup screen (endpoint URL + API key + TOFU fingerprint confirm) entry in the web-ui/desktop settings, with the connection config persisted to client storage. The setup screen consumes the P0 fingerprint endpoint to display the cert fingerprint for first-use confirmation and pin it. Desktop (Tauri) prefers OS keychain for the key; web uses `localStorage`. Origin allowlist on the daemon side is amended so the connecting client's origin is accepted (Tauri webview origins already allowlisted; the remote web-app / desktop-app origin needs handling per the Prepare-locked rule). Fold in R-V191P1-001 (split CSV toast not_found vs conflict) + R-V191P1-002 (extract CSV utilities from `findings-page.tsx`) — same frontend files.
- **SP-4: Closure.** QC tri-review (security lens via `qc-specialist-2`, transport lens via `qc-specialist-3`) + QA + compound + Profile B compaction + PR to `main`.

## 2.2 Product Success Criteria

- **Remote bind is encrypted by default.** A daemon started with `NEXUS_DAEMON_REMOTE_BIND=1` + `NEXUS42_DAEMON_API_KEY` on a non-loopback address serves over TLS using its auto-generated self-signed cert. Remote bind without a usable cert is refused at startup with a clear error.
- **The cert is observable and TOFU-pinnable.** The daemon logs the cert fingerprint at startup; a read-only endpoint returns it; the connection setup screen displays it for first-use confirmation and pins it per-endpoint in client storage. A fingerprint change on a pinned endpoint produces an explicit warning requiring re-confirmation.
- **A GUI client on a trusted network can connect to a remote daemon and operate identically to local.** After a successful connection via the "Connect to Daemon" screen (endpoint URL + API key + explicit TOFU fingerprint confirmation), every existing author-facing surface continues to function without modification, degradation, or new warnings:
  - Strategy canvas, Outline+Timeline canvas, and World KB canvas render, accept edits, and persist exactly as they do on localhost.
  - Reading chrome (V1.91: scroll progress, highlights, annotations) works with identical gestures and persistence semantics.
  - Findings triage — including the V1.91 batch status/target updates — completes the same workflows with the same toasts and partial-success handling.
  - Memory review loop, SOUL narratives, preset management, chapter editing, and all other Control Room surfaces behave identically.
  The only observable surface difference is a connection-status indicator reflecting the active remote endpoint label (or "Local"). Local same-origin mode (daemon-served SPA, loopback bypass, no key) remains the zero-config default and is unaffected. A fingerprint change on a previously-pinned endpoint produces an explicit blocking re-pin warning before any data flows.
- **CSRF remains closed without a token framework.** The remote connection authenticates via a custom header that cross-origin JS cannot forge without a CORS preflight the Origin allowlist already gates. Documented as the CSRF defence in the spec amendment; no separate token layer shipped.
- **The four V1.91 residuals are closed.** R-V191P1-001/002 (frontend), R-V191P1-003 (codegen), R-V191P1-004 (backend test) land within their host plans; R-V191P1-005 stays deferred to list-virtualisation (unchanged, recorded in §5 Risk Register and the deferred tracker).
- **No regression** in local / CLI / existing desktop / web-dev flows (`cargo test -p nexus-daemon-runtime`, `pnpm --filter web test`, desktop dev connect, Vite dev proxy).
- `cargo clippy --all -- -D warnings` and `cargo +nightly-2026-06-26 fmt --all --check` pass (CI gate).
- `knowledge/specs/daemon-runtime.md` carries a codified transport-security + remote-connection section.
- QC tri-review consolidated Approve (qc2 security lens: remote attack surface not widened; qc3 transport lens: TLS handshake + cert lifecycle sound); QA verifies the regression tests reproduce the pre-TLS cleartext exposure as failing-without-the-fix.

## 6. Non-Goals

- **Explicit CSRF token framework** (double-submit cookie, synchronizer token, SameSite session) — header-key + Origin allowlist cover CSRF for the connection model; a token layer is redundant and adds surface. Recorded in the spec amendment as the deliberate defence choice.
- **Deprecating keyless-localhost mode** or forcing an API key for local loopback (product-level UX; local-first default unchanged).
- **API key rotation / per-token scoping / `~/.nexus42/auth.json` hardening** beyond what the transport + connection model directly require (V1.86-deferred; separate auth-mode work).
- **Unix-socket-only listener** (architectural; `Transport::UnixSocket` already exists for those who want it; not promoted to default this iteration).
- **Auto Let's Encrypt / ACME** or any network-CA integration (the user chose self-signed to avoid ops burden; ACME is a future enhancement for internet-exposed remotes, out of scope for trusted-LAN).
- **Raw-browser-tab direct navigation to a remote daemon** as a supported UX. An author who types a remote daemon URL (e.g. `https://192.168.1.42:8420`) directly into a browser tab will encounter a self-signed certificate warning that is browser-native and non-bypassable without adding the cert to the OS trust store. The supported remote-access path is always the desktop app or the web-app "Connect to Daemon" setup screen inside the Control Room: those surfaces perform certificate-fingerprint TOFU confirmation and pin the cert, so authors never manually trust a browser security dialog. This is documented as an explicit non-goal so future contributors do not treat the browser warning as a bug to be "fixed" by exposing the daemon without TLS or by requiring a public CA.
- **A remote-endpoint switching UI beyond the single connection-config screen** — the data model supports multiple stored endpoints, but a full "endpoint manager" (add/edit/delete/list, active-endpoint switcher in the header) is a future iteration. This iteration ships the connection-config + single-active-endpoint.
- **Mid-iteration WebSocket / SSE changes** — no transport-protocol changes beyond TLS-wrapping the existing HTTP listener.
- **Unrelated residuals** — only the four named V1.91 residuals are swept; no other open items are pulled in.

V1.86's deferred CSRF posture is resolved-by-design (header-key model) rather than by adding a token framework.
- **Next iteration (V1.93) transition criteria**:

  - Selection input: PM reviews backlog against a now-remote-capable product. Candidates:
    - BL-09 standalone maturation dashboard (still deferred since V1.79; SOUL data infrastructure mature) — unchanged priority.
    - **Remote-endpoint manager UI** (multi-endpoint list, add/edit/delete, header switcher) — the natural follow-on only **after** real usage data shows authors maintain more than one remote daemon. Trigger signal: either (a) ≥3 distinct remote endpoints appear in client-storage telemetry (when we add lightweight opt-in analytics) or (b) explicit author requests / forum threads surface the pain of manually editing `localStorage` or the desktop config file.     - Deeper reading annotations (BL-11) or ACME/Let's Encrypt for internet-exposed remotes — only if trusted-LAN usage proves too narrow (i.e., authors explicitly request exposure beyond home networks).   - Output of V1.92 for V1.93: a daemon that is safe to expose on a trusted network and a GUI that can connect to it — the foundation for any future "remote author" or "headless daemon + laptop author" workflow.
- **Long-term goal**: Nexus gives authors a local-first creative workspace that **scales safely to a trusted network** without forcing cloud accounts — the daemon can live on a home server, the author's laptop connects to it over encrypted TOFU-trusted TLS, and the localhost trust boundary (V1.86) extends coherently to the LAN trust boundary (V1.92). STRATEGY Principle #1 ("local-first privacy") is preserved end-to-end.
