# V1.99 — Design System Deepening — Delivery Compass v1

## Scope

This iteration turns the V1.98 Design Studio from a read-only mirror into the front door for maturing Nexus UI composition.

### Product Problem

V1.98 made Nexus' visual source of truth visible, but it did not make UI work faster or more coherent yet. Reusable primitives still live under app ownership, `/surfaces` does not yet sell the quality bar of the product experience, and contributors still lack a validated path for trying visual ideas without paying the `apps/web` / Tauri / daemon integration cost too early.

V1.99 solves that product and developer-experience problem: visual decisions should be easy to test in Design Studio, stable primitives should graduate into a shared package, and accepted UI should then enter `apps/web` with real behavior instead of being redesigned a second time.

- **SP-1: Reusable UI component boundary.** Re-evaluate the V1.98 "brand layer only" package boundary and define which pure presentational primitives can move from `apps/web/src/components/ui/*` into `@42ch/nexus-ui` without importing daemon state, app routes, layout shells, or web-only logic.
- **SP-2: `@42ch/nexus-ui` component promotion.** Promote a focused first batch of reusable, token-driven, presentational components so `apps/web` and `apps/design-studio` consume the same implementations instead of maintaining a transitional `@web-ui/*` dependency for those components.
- **SP-3: Surfaces visual direction.** Redesign `http://localhost:5174/surfaces` from static, util-heavy fixtures into polished visual compositions that establish a calmer, more premium Nexus setup/shell direction with clear usability affordances.
- **SP-4: Studio-first UI workflow.** Validate and document the development path: compose pure View components in `apps/design-studio` first for rapid agent-driven visual iteration, then integrate accepted components into `apps/web` with real data and behavior.

## Acceptance Criteria

- `@42ch/nexus-ui` has a locked package-boundary update that permits only reusable, token-driven, presentational components and still forbids app routing/state/daemon imports.
- The first-batch package API decision is explicit: selected components, public export shape, dependency posture, asset rules, token consumption, and app wrapper strategy are all recorded before P0 starts.
- A focused first batch of shared UI primitives is exported from `@42ch/nexus-ui`, covered by package tests, and consumed by both `apps/design-studio` and `apps/web` where appropriate.
- `apps/design-studio` `/surfaces` has redesigned setup and shell compositions that feel coherent in light/dark themes, use registered design-token scale steps only, and pass keyboard/focus/contrast smoke checks.
- `/surfaces` remains a daemon-free View proving ground with studio-local shell/setup fixtures; any Web integration work is tracked separately through explicit fixture-to-product decisions.
- The studio-first workflow is validated on at least one promoted component and one surface composition: studio visual iteration first, then `apps/web` integration with real behavior.
- Product/developer stakeholders can trace each accepted UI decision through the chain `apps/design-studio` fixture → promoted package primitive when reusable → `apps/web` integration or explicit non-promotion decision.
- Durable workflow guidance lands in the appropriate surface: project rules/specs during the iteration; knowledge promotion at iteration-close; skill creation is only a later, conditional option if the workflow proves reusable beyond this repo and passes `mstar-skill-authoring` checks.
- `wire_contracts_changed: false` unless implementation discovers a necessary public package API versioning note; no `schemas/` changes are expected.

## Non-Goals

- No daemon, Rust, Tauri sidecar, or desktop clean-state first-launch work in this iteration.
- No migration of app layout shells, page components, `NexusClient`, daemon hooks, or data-aware components into `@42ch/nexus-ui`.
- No full Storybook adoption or external visual tooling.
- No broad redesign of every `apps/web` screen; `apps/web` integration is limited to components and surfaces validated by the iteration plans.
- No automatic YAML write-back or live token editor in Design Studio.
- No new Morning Star skill unless the validated workflow proves reusable across projects and is not better captured in project `AGENTS.md` or `.mstar/knowledge`.

## Roadmap Position

- **Current iteration (V1.99)**: Deepens the V1.98 design-system foundation by promoting reusable UI components, making `/surfaces` a meaningful visual proving ground, and establishing a studio-first development path.
- **Relation to V1.98**: V1.98 intentionally stopped at a safe read-only Design Studio and brand-only `@42ch/nexus-ui`. V1.99 is the next product slice for that same design-system line, not a harness/process cleanup iteration.
- **Relation to prior desktop clean-state deferral**: V1.97/V1.98 left desktop clean-state first-launch as an important deferred product gap. The user has explicitly superseded that as the active V1.99 direction; it remains deferred and should not leak into these UI package or visual-direction plans.
- **Next iteration**: Desktop clean-state first-launch completion remains the default next candidate unless superseded again by user direction; trigger: V1.99 lands and the design workflow no longer blocks UI iteration.
- **Final target**: Nexus UI work can be designed and validated quickly in `apps/design-studio`, promoted through stable shared packages, and integrated into `apps/web` without Rust/Tauri packaging friction or token drift.
