## 2. Scope

This iteration locks three delivery specs plus closeout:

- **SP-1: Nexus UI asset package foundation.** Organize `packages/nexus-ui` as a publishable npm workspace package under `@42ch/nexus-ui`. Enable Git LFS for binary brand source assets. Define the asset layout, package metadata, README usage, and future component-library boundaries. Initial public exports are limited to logo assets, token data, CSS/theme entry points, and documentation; no React component exports in V1.83. Future `nexus-platform` use is an API-shape constraint only; this iteration does not integrate or test the private platform.
- **SP-2: Brand design system contract.** Create root `DESIGN.md` and `DESIGN.dark.md` as the cross-application brand token SSOT using the provided VI palette, with accessible light/dark token values, logo usage rules, asset selection guidance, and package/Web mapping notes. Update `apps/web/DESIGN*.md` to consume/extend this brand layer without losing existing app-specific canvas/SOUL/findings component tokens; Web files may map and specialize, but must not redefine shared brand token values.
- **SP-3: Web app application pass.** Apply the refreshed brand to `apps/web` shell and base UI primitives: Tailwind theme, CSS custom properties, layout navigation/header/sidebar surfaces, buttons/cards/inputs/badges, and initial logo placement. Keep business-page redesign, information architecture changes, full visual overhaul, and feature-flow reshaping out of this slice.
- **SP-4: Closure and verification.** Run focused web checks, package build/typecheck, asset usage validation, QC/QA, and closeout documentation.

## 2.1 Architecture Hierarchy and Ownership

The architecture hierarchy for V1.83 is: root `DESIGN.md` / `DESIGN.dark.md` -> `@42ch/nexus-ui` package exports -> `apps/web/DESIGN*.md` consumption mapping -> `apps/web` implementation.

- Root `DESIGN.md` / `DESIGN.dark.md` own shared brand token names, values, accessibility intent, logo rules, and voice guidance. These files are the normative token source for cross-application consumption.
- `packages/nexus-ui` owns reusable brand artifacts derived from the root contract: source PNG provenance under Git LFS, canonical SVG variants, token data, CSS/theme entry points, package metadata, and usage documentation. It must not import from `apps/web`, depend on Web routing/state, or export React components in this iteration.
- `apps/web/DESIGN.md` / `apps/web/DESIGN.dark.md` own Web-specific consumption mapping: Tailwind keys, CSS custom properties, shadcn-style primitive mappings, and app-only component tokens. They derive from root tokens and document any Web-only aliases rather than becoming a second brand source.
- `apps/web` implementation owns token application in shell/base primitives only. P2 may consume package exports and DESIGN mappings, but it must not reshape `@42ch/nexus-ui` package APIs without first updating P0/P1 plan notes.
- Cross-plan dependency order: P0 defines asset/package export names before P1 finalizes package mapping notes; P1 locks token names before P2 applies them; P-last reviews the integrated `iteration/v1.83` HEAD. Parallel edits are allowed only when ownership does not overlap these files or exported names.

## 5. Acceptance Criteria

- `packages/nexus-ui` is a valid pnpm workspace package and publishable npm package shape under `@42ch/nexus-ui`.
- Binary source logo PNGs are tracked through Git LFS, while canonical app-consumable logo SVGs are committed as text assets.
- Logo assets include at least: color/default, dark-mark, light/white-mark, monotone, and usage documentation for light/dark surfaces.
- Root `DESIGN.md` and `DESIGN.dark.md` exist with machine-readable YAML frontmatter and body guidance matching the provided VI direction.
- `apps/web/DESIGN.md` and `apps/web/DESIGN.dark.md` map the brand tokens into existing web-specific component tokens without orphaning current canvas/SOUL/findings token consumers.
- `apps/web` visibly applies the brand in shell/navigation/header/base primitives and passes focused typecheck/test/build gates.
- Product acceptance confirms a visible author-facing improvement: logo presence, palette, focus states, and base primitives feel coherent in both light and dark modes without changing task flows.
- No new backend routes, schemas, or wire contracts are introduced.

## 6. Non-Goals

- Full React component-library migration into `packages/nexus-ui`.
- Full redesign of every product page, canvas inspector, findings workflow, memory workflow, or SOUL workflow.
- Private `nexus-platform` integration work.
- Any implementation work inside `nexus-platform`; references to it only constrain public package names, export stability, and documentation wording.
- New daemon/local API behavior.
- Logo generation that changes the brand concept beyond faithful vector refinement of the supplied PNG references.
